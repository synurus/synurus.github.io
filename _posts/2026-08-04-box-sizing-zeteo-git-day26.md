웹개발 수업 26일차. 코드리뷰 주제는 `box-sizing`이다. `width: 100%`인데 왜 박스가 삐져나올까. 그리고 팀 프로젝트 **Zeteo의 Day 1은 하루에 두 번, 파일이 조용히 사라지는 사고**를 겪은 날이었다. 인수인계 문서 자체가 오늘 하루의 "배운 것" 아카이브가 됐다.

## 1. 코드리뷰 ⑤ · width: 100%인데 왜 넘칠까

`.wrap`(폭 400px) 안에 `.card`(`width: 100%`)를 넣었는데, 한쪽 코드는 딱 맞고 한쪽은 오른쪽으로 넘친다.

```css
.wrap { width: 400px; border: 2px solid #333; }

/* A */
.card { width: 100%; padding: 20px; }

/* B */
.card { width: 100%; padding: 20px; box-sizing: border-box; }
```

**Q1. 딱 맞는 쪽은? → B** **Q2. 왜?**

### box-sizing이 "폭"의 정의를 바꾼다

| | `content-box` (기본값) | `border-box` |
|---|---|---|
| `width`가 가리키는 것 | **콘텐츠 영역만** | 콘텐츠 + padding + border **전부** |
| 실제 차지하는 폭 | `width` + padding + border | `width` 그대로 |

`box-sizing`을 안 적으면 **`content-box`가 기본값**이다.

### A 코드 계산 · 40px가 바깥에 더해진다

1. `.wrap`의 콘텐츠 폭 400px → `width: 100%` = **400px**
2. `content-box`니까 이 400px는 **콘텐츠 영역만**
3. `padding: 20px` 좌우 40px가 **그 바깥에 추가**

```
실제 폭 = 400(콘텐츠) + 20 + 20(패딩) = 440px  →  40px 넘침 ❌
```

### B 코드 계산 · 400px 안에서 역산

1. `width: 100%` = **400px**
2. `border-box`니까 padding이 **이 400px 안에 포함**
3. 브라우저가 콘텐츠 영역을 역산: `400 - 20 - 20 = 콘텐츠 360px`

```
실제 폭 = 400px  →  딱 맞음 ✅
```

### 헷갈리는 이유 · 100%는 "부모의 콘텐츠 영역"

`width: 100%`의 기준은 **부모가 화면에서 차지하는 크기가 아니라, 부모의 콘텐츠 영역 크기**다. `.wrap`도 기본값이 `content-box`라 콘텐츠 폭은 그대로 400px지만(border 2px는 바깥으로 붙어 `.wrap`의 실제 폭은 404px), `.card`가 계산하는 기준은 그 400px이다. `height`도 같은 규칙.

### 함정 하나 더 · margin은 border-box에 안 들어간다

`border-box`가 포함하는 건 **content+padding+border까지**. **margin은 포함되지 않는다.**

```css
.card {
  width: 100%;
  padding: 20px;
  margin: 0 10px;      /* 좌우 20px 추가 → 다시 넘침! */
  box-sizing: border-box;
}
```

margin까지 감안해야 하면 `calc()`를 쓰거나, **애초에 `width`를 지우는 게 낫다.**

### 실무 권장 · 전역 리셋 + width를 아예 안 쓰기

```css
*, *::before, *::after { box-sizing: border-box; }
```

5일차 CSS 리셋 때 이미 배운 세 줄인데, 오늘 **왜** 이걸 넣는지 원리를 알게 됐다. 더 나은 대안도 있다. `div` 같은 블록 요소는 폭 선언이 없으면 부모 폭을 꽉 채우되 padding/border가 있으면 **콘텐츠를 줄여서 알아서 맞춘다.**

```css
.card { padding: 20px; }   /* width 선언 없음 → 결과는 B와 동일 */
```

`width: 100%`는 블록 요소에서 대부분 불필요하고, 오히려 이런 버그를 만든다. (단 `inline-block`, `position: absolute`, flex 아이템처럼 폭이 자동으로 안 늘어나는 경우엔 필요할 수 있다.)

### 검증은 F12 Box Model

개발자도구 Computed → Box Model에서 실제 수치를 바로 볼 수 있다:

```js
document.querySelector('.card').getBoundingClientRect().width
// A → 440, B → 400
```

23일차부터 F12는 "구경하는 도구"에서 "검증하는 도구"로 쓰임새가 넓어지고 있다.

## 2. 팀 프로젝트 · Zeteo Day 1, 사고와 대응

Day 0에 계약 구멍 6개를 찾은 다음 날. Day 1은 **하루에 두 번, 파일이 조용히 사라지는 사고**를 겪었다. 인수인계 문서가 그 자체로 오늘의 기록이라, 사건 순서대로 남긴다.

### 사건 R5 · 봇 코드 275줄이 사라졌다

작업 중 다른 브랜치의 변경을 확인하다가, **파트 B(봇)의 코드 275줄이 사라진 걸 발견**했다. 구두로 알렸지만, 인수인계 문서에도 이렇게 남겼다:

> 구두로 말했지만 **스레드에 글로도 남긴다. 병합 때 잊으면 그대로 사라진다.**

### 사건 R8 · 그날 저녁, 27개 파일 전부

같은 브랜치의 커밋 하나가 **`apps/frontend` 폴더 27개 파일을 통째로 삭제**했다. 더 무서웠던 건 이거였다:

> **삭제는 충돌로 안 뜬다.** 27개 중 **3개만** 충돌이었다: 내가 고친 파일만 git이 묻고, 나머지 24개는 묻지 않고 삭제를 적용한다.

`git merge`는 양쪽이 같은 파일을 고쳤을 때만 "충돌"이라고 알려준다. **한쪽이 지우고 한쪽이 안 건드린 파일은 조용히 지워진 채로 병합이 끝난다.** 이걸 몰랐으면 병합 버튼 한 번으로 27개 파일이 사라졌을 것이다.

### 발견 방법 · 시험 병합

실제로 병합하기 전에 **가짜로 먼저 합쳐보는 절차**를 세웠다:

```bash
git checkout -b trial origin/feat/game-ui
git merge --no-commit --no-ff origin/feat/server

git diff --cached --diff-filter=D --name-only   # ★ 조용히 삭제되는 파일
git diff --name-only --diff-filter=U            #   충돌로 뜨는 파일
npm run build -w frontend

git merge --abort   # 다 확인했으면 취소 — 진짜 병합 아님
```

**`--diff-filter=D`가 핵심.** 충돌 목록만 보면 조용히 사라지는 파일을 놓친다. 이 절차 하나로 R5·R8과 다른 문제 두 개(`name→label` 필드명 변경, 신규 필드 하나)를 **병합 전에** 전부 찾아냈다.

12일차에 `git status` 정도만 배웠는데, 팀 규모가 커지니 **"병합해보고 문제 생기면 되돌리기"가 아니라 "병합 전에 미리 열어보기"**가 되어야 한다는 걸 알았다.

### 되돌리는 법도 상황에 따라 다르다

```
혼자 쓰는 브랜치, 아직 아무도 안 봄  → git reset --hard + push --force
PR이 열려 있거나 남이 볼 수 있음     → 새 커밋으로 되돌린다 (git revert)
```

`git revert`도 커밋을 하나 더 만든다는 걸 처음 알았다. 완전히 안 남기려면 강제 push뿐인데, **남이 보고 있으면 그건 못 쓴다.** 실제로 토큰 이름을 잘못 바꿨다가 되돌린 적이 있었는데(`e321066` → `5224861`), PR에 "이 두 커밋이 상쇄되며 순변화는 X뿐"이라고 적어뒀다. 커밋 로그는 지우는 게 아니라 **설명을 남기는 것**이라는 감각.

### 남의 소유 파일을 따라가면 안 되는 이유

토큰 이름을 D(디자인 담당)의 파일에 맞춰 한 번 바꿨다가 도로 되돌린 일이 있었다. 이유:

> D의 **라이트(초안) 파일에만** 있던 이름이었다. **남의 소유 파일에서 확정 전 이름을 따라가면 안 된다.**

Day 0에 합의한 토큰 이름 11개가 있는데, 상대의 작업 중 파일을 보고 "저게 최신인가?" 싶어 따라갔다가 잘못된 판단이었던 것. **합의된 계약과 남의 진행 중 파일은 다르다**는 교훈.

### DNS 문제 · git 문제가 아니었다

푸시가 안 됐는데 `Could not resolve host: github.com`. git이 고장난 줄 알았지만 진단해보니:

```
ping 1.1.1.1 성공          → 회선은 살아있다
nslookup github.com 1.1.1.1 성공  → 네트워크로 나가는 질의는 정상
Resolve-DnsName github.com 실패   → Windows DNS 클라이언트 계층 문제
```

`Set-DnsClientServerAddress -ResetServerAddresses`로 해결됐다. **수동으로 DNS를 박기 전에 자동으로 되돌리는 것부터** 시도하는 순서를 배웠다.

### 가장 중요한 깨달음 · "dev만 보면 팀 상태를 오판한다"

인수인계 문서 마지막 절의 제목 그대로다.

> Day 1 오전까지 "R2(서버 로직)가 비어 있어 파트 C가 당길 게 없다"고 적혀 있었으나 **이미 구현돼 있었다.** 오후에 다시 보니 또 달랐다. 그 사이 다른 브랜치들에 커밋이 계속 쌓였다.

그리고 한 겹 더:

> 원격만 봐서는 남의 **로컬** 작업을 못 본다. "이 문제 없다"고 단정했는데, 이미 로컬에서 처리 중이었다. 이 팀은 로컬에 쌓아두고 늦게 push한다.
>
> **→ "없습니다"가 아니라 "원격 기준으로는 안 보입니다"로 말한다.**

이게 오늘 배운 것 중 가장 마음에 남았다. **정보가 없다는 것과, 내가 볼 수 있는 곳에 없다는 것은 다르다.** 그런데도 "말은 한다"고 되어 있다. 확인 한 줄의 비용은 작고, 정말 빠졌으면 4명이 동시에 멈추니까. **최종 안전망은 결국 시험 병합 + 빌드**라는 것.

### 오늘도 이어진 것 · "받으면 다시 그린다"

혼란 속에서도 어제 정한 원칙들은 그대로 지켜졌다. `feat/server`가 신규 필드 5개를 전부 "result-only로 게이팅"했다는 게 확인됐는데, 이게 **파트 C의 설계 판단(★7 폐기 등)을 서버가 그대로 지킨 것**이다. 계약이 한번 확정되면 양쪽이 거기에 맞춰 움직인다는 걸 직접 봤다.
