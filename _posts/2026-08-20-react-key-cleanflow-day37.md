웹개발 수업 37일차. 4주차 React 코드리뷰는 목록에서 항목 하나를 지웠는데 체크 표시가 엉뚱한 곳으로 옮겨가는 코드였다. 팀 프로젝트는 이번 주 평가 항목인 클린 코드에 맞춰, 코드에 읽는 순서를 만드는 시스템 cleanflow를 기획했다.

## 1. 코드리뷰 ⑬: 우유를 지웠는데 왜 계란이 사라질까

체크박스가 달린 할 일 목록. 실행 전에 예상부터 적고 시작했다.

```jsx
function Row({ name, onDelete }) {
  const [checked, setChecked] = useState(false);

  useEffect(() => {
    console.log('mount  ', name);
    return () => console.log('unmount', name); // 이 Row 가 사라질 때 찍힌다
  }, []);

  return (
    <li>
      <input
        type="checkbox"
        checked={checked}
        onChange={(e) => setChecked(e.target.checked)}
      />
      {name}
      <button onClick={onDelete}>삭제</button>
    </li>
  );
}

// items: [{ id: 1, name: '우유' }, { id: 2, name: '빵' }, { id: 3, name: '계란' }]

{items.map((it, index) => (
  <Row key={index} name={it.name} onDelete={() => 삭제(it.id)} />
))}
```

기대: 맨 위 우유만 체크한 뒤 우유를 지우면 그 체크박스도 같이 사라지고, 콘솔에는 unmount 우유가 찍힐 거라 예상하기 쉽다.

실제: 체크는 사라지지 않고 빵으로 옮겨간다. 목록 맨 위(원래 우유 자리)에 체크 표시가 그대로 남아 있다. 콘솔에 새로 찍히는 줄은 unmount 계란이다. 지운 건 분명 우유인데, React 내부적으로는 목록 맨 아래 계란 컴포넌트가 없어진 것으로 처리된다.

### Q1·Q2: key가 없으면 React는 "누구"가 아니라 "몇 번째"만 본다

원인은 렌더링 줄이다.

```jsx
<Row key={index} name={it.name} onDelete={() => 삭제(it.id)} />
```

React가 리스트의 각 항목을 구분하는 유일한 방법은 key다. 리렌더링할 때 이전 렌더링의 어떤 요소가 새 렌더링의 어떤 요소와 같은 것인지 판단해야 컴포넌트를 재사용할지 새로 만들지 정하는데, 그 판단 기준이 key뿐이다. 지금 코드는 배열 인덱스를 key로 쓰고 있고, 인덱스는 이 항목이 누구인지가 아니라 지금 몇 번째 자리에 있는지만 나타낸다.

삭제 전: index 0(key=0) 우유(checked: true), index 1(key=1) 빵, index 2(key=2) 계란.

우유를 지우면 배열은 [빵, 계란]이 되고 map이 다시 인덱스를 매긴다. index 0(key=0) 빵, index 1(key=1) 계란. key=2는 더 이상 존재하지 않는다.

React는 key=0이 렌더링 전후로 계속 존재하니 같은 컴포넌트라고 착각하고 그 Row 인스턴스와 그 안의 checked state를 그대로 재사용한다. 실제로는 그 안의 name만 우유에서 빵으로 바뀐 것뿐이다. 반대로 key=2는 더 이상 매칭되는 자리가 없으니 React는 이 컴포넌트가 사라졌다고 판단해 언마운트하는데, 그게 실제로 지운 우유가 아니라 맨 끝의 계란이다.

### 수정: 자리가 아니라 정체성을 key로 쓴다

```jsx
{items.map((it) => (
  <Row key={it.id} name={it.name} onDelete={() => 삭제(it.id)} />
))}
```

인덱스 대신 각 항목이 가진 고유하고 안정적인 값, 여기서는 id를 key로 쓰면 된다. 우유(id: 1)를 지웠을 때 React는 key=1이 사라졌다는 걸 정확히 인식하고 그 Row 컴포넌트만 언마운트한다. 빵(key=2)과 계란(key=3)은 key가 그대로 유지되니 각자의 state도 보존된다.

배열 끝에 추가나 삭제만 하는 경우엔 index를 key로 써도 문제가 안 생긴다. 인덱스와 항목의 대응 관계가 안 흔들리기 때문이다. 하지만 중간이나 앞쪽 항목을 삭제, 삽입, 순서 변경 하는 순간 그 뒤에 있던 모든 항목의 인덱스가 한 칸씩 밀리면서 React가 재사용해도 되는 컴포넌트에 대한 판단이 완전히 틀어진다.

### 35일차와 같은 자리를 가리킨다

| | 35일차 | 37일차(오늘) |
|---|---|---|
| React가 놓친 것 | state가 바뀐 사실 자체 | 어떤 컴포넌트가 "같은 것"인지 |
| 원인 | `let`으로 선언해 React가 감시하지 못함 | index를 key로 써서 자리와 정체성을 혼동 |
| 공통점 | React는 값이 아니라 자기가 추적하는 신호만 본다 | 자리가 아니라 이름표만 본다 |

35일차는 React가 리렌더 여부를 무엇으로 판단하는지였고, 오늘은 React가 컴포넌트의 정체성을 무엇으로 판단하는지다. 둘 다 내가 보는 값과 React가 보는 신호가 다른 자리에서 어긋났다.

## 2. 팀 프로젝트: 파일에 읽는 순서를 만드는 cleanflow

4주차 평가 항목은 클린 코드다. 이번 주 기획한 답은 cleanflow, 코드를 파일 단위로 재배치하고 주석을 붙여서 처음 읽는 사람이 위에서 아래로 한 번 훑기만 해도 이해되게 만드는 시스템이다.

### 지금 코드에서 관찰한 것

| 파일 | 증상 |
|---|---|
| `bot/index.ts` | 진입점이 파일 맨 끝에 있는 배치는 맞는데, 그 앞이 정리돼 있지 않다. 서로 부르지 않는 함수가 붙어 있고 부르는 함수는 떨어져 있다. 상수 60줄이 성격 구분 없이 앞에 몰려 있고, 발화 검사도 두 군데로 나뉘어 있다 |
| `hooks/useGameState.ts` | 반대 경우. 짧고 순서도 맞는데, 왜 이 방식인지가 코드 어디에도 안 적혀 있다 |

큰 파일과 작은 파일은 다른 이유로 안 읽힌다는 게 여기서 나온 관찰이다.

### 왜 린터로는 안 되는가

이미 ESLint와 Prettier를 쓰고 있는데도 위 문제가 남아 있다. 린터는 줄 단위로 세미콜론이나 안 쓰는 변수, 들여쓰기를 본다. 우리 문제는 파일 단위, 무엇이 어디에 있는가다. 모든 줄이 규칙을 지켜도 순서가 뒤죽박죽이면 못 읽고, 반대로 순서가 완벽해도 왜 하필 이 방식인가는 코드만 봐서는 알 수 없다. 둘 다 린터의 사정거리 밖이라고 정의했다.

### 클린 코드의 정의를 하나로 좁혔다

처음 읽는 사람이 위에서 아래로 한 번 훑어서 이해할 수 있는 코드. 이 정의를 고른 이유는 판정이 가능해서다. 좋은 코드나 유지보수하기 쉬운 코드는 확인할 방법이 없지만, 이 문장은 사람 하나를 앉혀놓고 시켜보면 바로 답이 나온다. 여기서 두 조건이 나온다. 순서가 흐름을 따를 것(배치의 문제), 흐름만으로 알 수 없는 것이 적혀 있을 것(주석의 문제). 배치는 한 번 정리하면 끝나지만 규칙이 안 보이면 다음 사람이 또 파일 끝에 붙이므로, 주석의 구분선이 배치를 눈에 보이게 고정해서 그걸 막는 구조로 잡았다.

### 배치 규칙과 판정

작은 것부터 쌓아 올려 마지막에 조립하는 방식을 기본으로 했다. 파일 머리에 이 파일이 무엇을 책임지는지 적고, 그 아래 각 구역의 함수와 상수를 두고, 진입점은 맨 끝에 둔다. 구역 이름은 유틸이나 헬퍼 같은 기술 용어 대신 이 코드가 게임의 어느 순간에 작동하는가로 짓기로 했다. 기술 용어는 아무 프로젝트에나 붙는 이름이라 새 함수를 어디 넣을지 다시 애매해지기 때문이다. 구역은 3~5개를 넘지 않게 크게 나눈다.

파일마다 손댈지 말지는 줄 수가 아니라 증상으로 판정한다. 스크롤 없이 윤곽이 잡히는가, 선언 하나를 찾을 때 파일을 훑어야 하는가, 이 파일이 무엇을 책임지는지 한 문장으로 말할 수 있는가, 그렇게 만든 이유 중 코드에 안 드러나는 것이 있는가. 하나도 안 걸리면 이 파일은 됐다로 끝내고 PR도 열지 않는다. 규칙은 고쳐라보다 이 파일은 됐다를 더 자주 말할 수 있어야 한다는 걸 원칙으로 세웠다.

### 커밋을 둘로 쪼갠다

리뷰어가 커밋 1만 보면 안전 확인이 끝나도록 설계했다. 커밋 1은 이동만, 선언을 재배치하고 구분선을 넣되 함수 본문은 한 글자도 안 바꾼다. 커밋 2는 주석만, 코드 변경 없이 파일 머리와 각 구역의 설명을 적는다. 테스트가 없는 저장소라 diff 자체를 증거로 쓰기로 했다. 커밋 1은 구분선을 뺀 줄들을 정렬해서 이전과 비교해 순서만 바뀌었는지 확인하고, 커밋 2는 diff의 추가·삭제 줄이 전부 주석인지 확인한다.

### 통보이지 허락이 아니다

디스코드에 파일 경로를 남기면 시작되고, 정리가 끝나면 PR을 열어 소유자에게 통보한다. 작업 중이시냐고 먼저 묻지 않는다. 물어보면 답을 기다리는 동안 진도가 멈추고 대부분은 안 겹치기 때문이다. 대신 통보에 아직 시작 전이면 PR 머지 후 작업, 이미 고치는 중이면 git stash 후 머지, 많이 고쳤으면 머지하지 말고 알려달라는 세 가지 받아쓰는 법을 같이 적는다. 다만 주석만은 예외로 확인을 받는다. 배치는 틀려도 읽기 불편할 뿐이지만 틀린 주석은 없는 주석보다 나쁘기 때문에, 추정으로 쓴 주석에는 확인 필요 표시를 붙여 따로 뽑아 보낸다.

이 겹침 처리가 가정이 아니라는 걸 오늘 직접 겪었다. `room.ts`를 정리해서 PR을 열었는데, 소유자가 지금 반쯤 갈아엎는 중이라 머지하면 충돌난다고 알려왔다. 그래서 PR을 닫고 브랜치도 지웠다. 정리는 재실행이 쉬워서 겹치면 그냥 버리고, 그쪽 작업이 dev에 들어간 뒤에 다시 돌리기로 했다. 버리는 비용이 싸다는 성질 덕분에 허락 없이 먼저 하는 방식이 감당 가능한 선택이 된다.

### 3주차 코드북과는 반대 방향

| 시스템 | 하는 일 |
|---|---|
| ESLint, Prettier | 줄 단위 규칙을 본다. cleanflow는 파일 단위 배치를 보므로 겹치지 않는다 |
| 3주차 코드북 | 어려운 코드를 그대로 두고 읽는 법을 만든다 |
| cleanflow | 안내서가 덜 필요하도록 코드 자체를 읽히게 바꾼다 |

코드북과는 반대 방향이다. 바꿀 수 없는 복잡함은 코드북이 맡고, 바꿀 수 있는 순서는 cleanflow가 맡는 쪽으로 역할을 나눴다.

## 3. 다음에 할 것

- 기획만으로는 안 끝난다. 실제 파일 하나(예: `bot/index.ts`)에 파이프라인을 돌려보고 새 코드를 넣을 자리가 자명한지까지 확인해야 한 바퀴다
- `room.ts`는 소유자 작업이 dev에 머지되면 최신 코드 기준으로 다시 정리
- 판정 4문항을 몇 개 파일에 먼저 손으로 적용해보고 신호가 실제로 걸러지는지 확인
- `/cleanflow` 스킬로 고정하기 전에, 어느 구역에도 안 들어가는 선언이 나왔을 때 그걸 구조 문제로만 보고하고 손대지 않는 경계가 실제로 지켜지는지 점검
