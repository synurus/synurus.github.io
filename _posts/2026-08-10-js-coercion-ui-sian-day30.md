웹개발 수업 30일차, 3주차가 시작됐다. 코드리뷰는 JS로 돌아와 **문자열+숫자 타입 강제변환**의 함정. 팀 프로젝트 Zeteo는 이번 주 모바일 UI를 잡기 위해 **시안 두 개를 나란히 만들어보고 하나를 채택**했다 — 코드보다 화면을 두 벌 만들어 비교하는 게 더 빠른 결정 방법이었다.

## 1. 코드리뷰 ⑧ — '12000' + 3000이 왜 120003000이 될까

장바구니 계산 코드. 실행 전에 결과를 먼저 예상해보라는 문제였다.

```js
const price = '12000';  // 폼에서 입력받은 상품 가격
const delivery = 3000;  // 배송비

const total = price + delivery;

console.log('상품 가격:', price);   // 12000
console.log('최종 금액:', total);   // 기대: 15000
```

**실제 출력:**
```
상품 가격: 12000
최종 금액: 120003000
```

### Q1. 어느 줄이 예상과 다른가

**두 번째 줄.** 기대값은 `15000`인데 실제로는 `120003000`. 첫 줄은 `12000`으로 정상처럼 보이지만, 이 값은 사실 숫자가 아니라 **문자열** `'12000'`이다. `console.log`는 따옴표를 안 보여주기 때문에 눈으로는 구분이 안 된다.

### Q2. 왜 이런 값이 나왔나 — `+`는 두 가지 일을 한다

```js
const price = '12000';   // ← 숫자가 아니라 '문자열'
const total = price + delivery;   // 문자열 + 숫자 → 문자열 이어붙이기
```

| 피연산자 | `+`의 동작 | 결과 |
|---|---|---|
| 숫자 + 숫자 | 덧셈 | `12000 + 3000 → 15000` |
| **문자열이 하나라도 있으면** | **문자열 연결** | `'12000' + 3000 → '120003000'` |

JS는 숫자 `3000`을 문자열 `'3000'`으로 바꾼 뒤 이어붙여 `'120003000'`(길이 9의 문자열)을 만든다. `typeof total`은 `'number'`가 아니라 `'string'`이다.

> 참고로 `-`, `*`, `/`는 문자열 연결 기능이 없어서 **반대로** 동작한다. `'12000' - 3000 → 9000`, `'12000' * 1 → 12000`. **`+`만 유일하게 이런 함정이 있다.**

### Q3. 어떻게 해결할까 — 입구에서 변환한다

```js
// 해결책 1 — Number() (권장)
const price = Number('12000');   // 12000

// 해결책 2 — 단항 + 연산자 (짧은 표현)
const total = +price + delivery;

// 해결책 3 — 폼 입력값을 받는 지점에서 즉시 변환 (실무에서 가장 흔함)
const price = Number(document.querySelector('#price').value);
if (Number.isNaN(price)) { /* 처리 */ }
```

원칙은 **계산 직전이 아니라, 값이 들어오는 입구에서 숫자로 바꾸는 것.**

### Number()와 parseInt(), 뭘 쓸까

| 입력값 | `Number(v)` | `parseInt(v, 10)` |
|---|---|---|
| `'12000'` | `12000` | `12000` |
| `'12000원'` | `NaN` | `12000` |
| `'12,000'` | `NaN` | **`12`** ⚠️ |
| `''`(빈 문자열) | `0` ⚠️ | `NaN` |

`Number()`는 이상한 값을 `NaN`으로 확실히 걸러줘서 **검증에 유리**하다. `parseInt()`는 앞에서부터 읽다가 숫자가 아니면 멈추는데, `'12,000'`이 `12`가 되어버리는 **조용한 오류**가 위험하다. → 금액 계산에는 **`Number()` + `Number.isNaN()` 검사** 조합을 권장.

### 이 버그가 진짜 무서운 이유

> **에러가 나지 않아서 더 위험하다.** `120003000`은 예외 없이 그대로 화면에 표시되거나 결제 요청에 실릴 수 있다.

그리고 위험 지점은 생각보다 넓다 — **폼(`input.value`), `localStorage`, URL 쿼리스트링, JSON 등에서 온 값은 전부 문자열**이다. 7일차에 localStorage를 배우고, 12일차에 쿼리스트링을 배우고, 17일차에 API 응답을 JSON으로 파싱했는데, **그 모든 경로로 들어온 숫자처럼 보이는 값이 사실은 전부 문자열**이었다. 오늘 이 사실이 한 줄로 정리됐다: 값이 들어오는 모든 입구에서 타입을 의심하는 습관.

## 2. 팀 프로젝트 — 모바일 UI 시안 두 벌

3주차부터 UI를 다듬는 단계. **채팅과 투표를 한 화면에서 어떻게 배치할지**를 두고 시안을 코드로 두 벌 만들어 비교했다.

### 공통 전제 — 결정된 것들

두 시안 모두 같은 조건 위에서 출발한다:

- **헤더는 상시 고정** — 라운드, 진행 단계, 제시어(카테고리/단어)가 항상 보임
- 같은 대화 로그, 같은 후보 목록(A·B·C·D·E), 같은 투표 현황
- 팝업이 뜨는 순간 **채팅 입력이 잠긴다** — "팝업이 떠 있는 동안에는 발언할 수 없습니다"

**다른 것은 딱 하나 — 채팅과 투표를 동시에 볼지, 탭으로 나눌지.**

### 시안 1 — 하단 접이식 (동시에 보임)

```
[헤더: 고정]
[채팅 로그]
[투표 패널 — 하단에서 접었다 폈다]
[요약 바: "B 2표(내 선택) · D 1표 · ⏱1:30 ▼" — 항상 보임]
[입력창: 항상 맨 아래]
```

- 투표 패널은 **화면 하단에서 슬라이드로 접고 펼 수 있다.** 접혀 있어도 요약 바가 항상 떠 있어서 "지금 누가 몇 표인지"를 놓치지 않는다
- 팝업은 **채팅 영역만 덮는다** — 우상단 X로 닫으면 뒤의 채팅이 그대로 보임
- 투표 그래프에 규칙 하나가 있다: **0표는 막대를 안 그린다.** "표를 안 받았다"는 신호가 없다는 뜻이므로 그냥 생략

### 시안 2 — 탭 전환 (한 번에 하나만)

```
[헤더: 고정]
[상단 스트립: 참가자 칩 A·B·C·D·E + 각자 표수 — 채팅 탭에도 항상 보임]
[채팅 탭] ↔ [투표 탭]  (하단 탭바로 전환)
[팝업: 전체화면 스크림 — 탭이 뭐든 위를 통째로 덮음]
```

- 채팅과 투표를 **완전히 분리된 화면**으로 만들고, 하단 탭바로 오간다
- 대신 채팅 탭 위에 **참가자 칩 스트립**을 얹어서, 투표 탭에 안 가도 표 현황을 한눈에 볼 수 있게 보완했다
- 팝업은 **전체화면을 덮는 모달(scrim)** — 어느 탭에 있든 최상위로 뜬다
- 안내 문구도 다르다: *"투표는 언제든 바꿀 수 있습니다. 채팅 탭으로 돌아가도 선택은 유지됩니다."* — 탭을 오가도 상태가 안 사라진다는 걸 명시

재밌는 건 두 시안 모두 **같은 문제(팝업 4종 → 5종 확장)**를 주석으로 남겨뒀다는 점이다. *"v3.0에서 봇 지목(botVote)이 채팅 안으로 들어오며 팝업이 4종에서 5종이 됐다"* — 팝업 내용은 역할 배정·생사투표·결과·제시어 추측·봇 지목까지 공용으로 써야 한다는 제약이 두 시안 모두에 이미 반영돼 있었다.

### 채택 — 시안 1

동시 노출(시안 1)이 채택됐다. 이유를 정리하면:

**① 정보를 잃지 않는다.** 시안 2는 채팅 탭에 있으면 투표 상세(누가 무슨 이유로 몇 표인지)가 안 보인다. 상단 스트립으로 표수는 보완했지만, **어떤 후보가 왜 표를 받는지의 맥락**은 탭을 넘어가야 확인된다. 라이어 게임은 **토론 중 투표 흐름을 실시간으로 살피는 게 게임의 핵심**인데, 탭 전환은 그 흐름을 끊는다.

**② 조작이 한 단계 짧다.** 시안 1은 요약 바를 탭하면 바로 펼쳐지고, 발언과 투표를 같은 화면에서 오갈 수 있다. 시안 2는 "투표하려면 먼저 탭을 눌러 화면을 바꿔야" 한다 — 이 게임처럼 시간제한이 있는 상황에서는 조작 한 번의 비용이 크다.

**③ 요약 바가 "접혀도 정보가 죽지 않는" 설계.** 시안 1의 요약 바(`B 2표(내 선택) · D 1표 · ⏱1:30`)는 패널이 닫혀 있어도 핵심 정보를 계속 보여준다. **완전히 숨기는 것과 요약해서 보여주는 것은 다르다**는 설계 판단이 여기 있었다.

시안 2가 나쁜 설계는 아니었다 — 오히려 화면이 더 넓게 쓰이고 각 영역에 집중할 수 있다는 장점이 있다. 다만 **이 게임의 특성(짧은 시간 안에 채팅과 투표를 동시에 참고해야 함)**에는 정보 손실이 적은 시안 1이 맞았다.

### 왜 코드로 두 벌을 만들었나

기획 단계에서 말로 논의할 수도 있었지만, **실제 HTML/CSS로 두 벌 다 만들어서 비교**했다. 이유는 명확하다 — 레이아웃 판단은 문장으로는 잘 안 잡힌다. "동시에 보이면 좋겠다"와 "탭으로 나누면 깔끔하다"는 둘 다 말로는 그럴듯하지만, **실제 화면에서 손가락으로 눌러보고 요약 바가 얼마나 자주 필요한지** 체감해야 알 수 있는 것들이었다.

9일차에 배운 "React는 데이터만 바꾸면 화면이 알아서 바뀐다"는 이번엔 반대 방향으로 쓰였다 — **화면(레이아웃) 자체가 결정해야 할 데이터**였던 것. 두 시안 모두 같은 mock 데이터(참가자 A~E, 라운드 2, 고양이)를 썼기 때문에 **레이아웃 변수 하나만 바꾼 A/B 비교**가 가능했다.
