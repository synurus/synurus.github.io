웹개발 수업 38일차. 오늘은 코드리뷰 소재가 없었다. 대신 이번 주 팀 프로젝트로 기획해온 cleanflow를 room.ts에 실제로 돌려보고 그 결과를 발표했고(발표는 팀원이 진행), Zeteo 쪽에서는 방 목록 화면 시안 6개를 검토해 그중 하나를 골랐다.

## 1. cleanflow: room.ts로 실제로 돌려봤다

37일차에 room.ts를 정리해서 열었던 PR #22는 그날 바로 닫혔다. 소유자가 반쯤 갈아엎는 중이라 머지하면 충돌난다고 알려왔기 때문이다. 정리는 다시 돌리는 비용이 싸다는 게 cleanflow 설계 원칙이라, 그때는 버리고 소유자 작업이 들어간 뒤에 다시 하기로 했다. 이번 주에 그 작업이 dev에 머지됐고, 최신 코드 기준으로 room.ts를 다시 정리했다. 그 결과가 오늘 발표에서 실제 사례로 쓰였다.

### 로직은 그대로, 순서와 주석만 바뀌었다

수정 전에는 코드가 쓴 순서 그대로였다. joinRoom, deleteRoom, createRoom 순으로 뒤섞여 있었다. 수정 후에는 실제 로비가 진행되는 흐름 순서로 재배치했다. createRoom부터 시작해 getRoom을 거쳐 removePlayerFromLobby로 끝난다. 함수 본문은 한 글자도 안 건드렸고, 정렬해서 비교하면 코드 줄이 그대로 일치한다.

주석도 성격이 바뀌었다. 수정 전 주석은 `// 라벨 뽑기`, `// 완료 플래그`처럼 코드가 하는 일을 그대로 반복하는 수준이었다. 수정 후에는 왜 그렇게 했는지를 적었다. 라벨을 무작위로 뽑는 이유는 참가 순서를 역산해서 정체를 추측하지 못하게 막기 위해서고, finalized 가드는 웹훅이 중복으로 나가는 걸 막기 위해서라고 명시했다.

markReady와 unmarkReady 두 함수는 파일 안에서 132~134번째 줄과 110~112번째 줄로 멀리 떨어져 있었다. 정리 후에는 나란히 붙여놓고 위에 왜 두 함수로 나뉘어 있는지를 적었다.

```ts
// add/delete로 나뉜 건 index.ts의 case 'ready'가 같은 액션을 토글로 쓰기 때문이다
// (재클릭하면 준비 해제, index.ts:508-512).
export function markReady(room: RoomInternalState, playerId: string) {
  room.readyIds.add(playerId);
}
export function unmarkReady(room: RoomInternalState, playerId: string) {
  room.readyIds.delete(playerId);
}
```

토글처럼 보이는 두 함수가 왜 각각 따로 존재하는지는 room.ts만 봐서는 알 수 없고, 이걸 호출하는 index.ts 쪽 사정이다. 흩어진 함수를 묶는 것만으로는 안 끝나고, 그 이유가 다른 파일에 있다는 것까지 주석에 남겨야 다음 사람이 또 두 함수를 하나로 합치려는 시도를 안 한다.

### 정리하다가 진짜 버그를 하나 잡았다

room.ts를 옮기고 주석을 다는 과정에서 웹훅이 중복으로 발송되는 문제를 발견했다. finalized 가드로 막아뒀다. 원래 cleanflow는 로직을 안 건드리는 게 원칙인데, 이번엔 정리하려고 파일을 처음부터 끝까지 훑는 과정 자체가 버그를 찾아낸 셈이다. 배치를 다시 하려면 각 함수가 왜 지금 자리에 있는지를 하나하나 따져야 하고, 그 질문을 던지다가 원래는 그냥 지나쳤을 코드에 걸린 것이다.

### 오늘 확인한 것들

발표에 담긴 배운 점을 정리하면 이렇다.

- 정의 단계를 건너뛰고 배치부터 하면 무엇을 기준으로 옮기는지가 사라지고 취향 싸움이 된다
- 틀린 주석은 없는 주석보다 나쁘다. 추정으로 쓴 주석은 확인 표시를 따로 남겨야 한다
- 겹침을 완전히 막을 방법은 없다. 막는 대신 버리고 다시 하는 비용을 낮추는 쪽을 택했고, 오늘 그 판단이 그대로 맞아떨어졌다
- 순서 정리 자체는 목적이 아니라 탐지 도구다. 어디에 놓을지 답이 안 나오는 함수가 곧 구조 문제라는 신호다

발표는 내가 아니라 팀원이 맡았다. 34일차 코드북 발표 때와 같은 모양이다. 만든 사람이 아니어도 결과물만 보고 설명할 수 있는지가 그때도 이번에도 같은 시험대였다.

## 2. Zeteo 팀 프로젝트: 방 목록 화면, 시안 6개 중 A3

지금은 방에 들어가려면 아이디와 방번호를 같이 입력해야 한다. 문제는 방번호를 미리 알고 있어야 한다는 점이다. 아이디만 입력하면 지금 입장 가능한 방을 화면에서 골라 들어가는 방식으로 바꾸기로 하고, 방향을 두 갈래로 나눠 각각 세 개씩 시안을 그렸다.

| 구분 | 방식 | 특징 |
|---|---|---|
| 옵션 A | 아이디 입력 후 별도 목록 화면으로 이동 | 화면이 분리돼 목록에 쓸 공간이 넉넉하다. 탭이 한 번 더 늘어난다 |
| 옵션 B | 입력 화면 안에 목록을 같이 띄움 | 화면 전환이 없다. 좁은 모바일 폭에 입력폼과 목록을 같이 넣어야 한다 |

A 안에서는 세 개를 그렸다. A1은 목록에서 방을 탭하면 그대로 입장하는 가장 단순한 구조라 빠르지만 잘못 탭했을 때 되돌릴 방법이 없다. A2는 탭하면 선택만 되고 입장하기 버튼을 눌러야 확정되는 구조라 오탭 위험은 줄지만 단계가 하나 늘어난다. A3는 필터와 정렬을 넣은 목록으로, 방이 많아질 상황을 가정해서 그렸다.

베이스로 고른 건 A3다. 전체와 대기중으로 거르고 인원 적은순이나 방번호순으로 정렬할 수 있고, 방마다 정원이 얼마나 찼는지 진행바로 보여준다. 방번호를 이미 아는 사람을 위한 직접입력 링크도 목록 맨 아래에 남겨뒀다. A1과 A2는 방 개수가 지금처럼 적을 때는 문제가 없지만 방이 늘어나면 그 사이에서 원하는 방을 찾는 기준이 없다. A3는 그 기준을 필터와 정렬로 미리 만들어둔 셈이라, 지금 당장 필요해서라기보다 방 개수가 늘어날 걸 가정하고 먼저 고른 안이다.

## 3. 다음에 할 것

- A3 시안을 실제 화면으로 옮기고, 필터·정렬 로직이 붙을 위치를 파트 D 쪽과 맞춰본다
- cleanflow를 room.ts 말고 다른 파일에도 돌려보고 판정 4문항이 실제로 걸러내는지 계속 확인한다
- `/cleanflow` 스킬로 고정하기 전에, 어느 구역에도 안 들어가는 선언이 나왔을 때 구조 문제로만 보고하고 손대지 않는 경계가 지켜지는지 점검한다

**오늘의 한 줄 정리:** cleanflow는 room.ts의 코드를 새로 안 만들고 순서와 주석만 바꿔서 버그를 찾아냈고, 방 목록 화면은 이미 있는 방 정보를 새로 안 만들고 필터와 정렬로 늘어놓아 고르기 쉽게 만들었다. 둘 다 없던 걸 만든 게 아니라 있던 걸 어떻게 늘어놓느냐의 문제였다.
