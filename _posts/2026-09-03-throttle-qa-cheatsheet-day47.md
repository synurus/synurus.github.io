## 1. 코드리뷰 ⑳: Throttle, 몰려와도 통과는 주기당 한 번

Throttle은 호출이 아무리 많이 들어와도 정해진 주기당 최대 한 번만 함수를 실행하도록 제한하는 기법이다. 사람이 아무리 몰려도 일정 간격으로만 통과시키는 개찰구와 같다.

이름은 엔진의 스로틀에서 왔다. 연료 조절 밸브다. 흐름을 막는 장치가 아니라 유량을 일정하게 조절하는 장치라는 게 이름에 이미 들어 있다.

`scroll`, `mousemove`, `resize` 같은 이벤트는 초당 수십에서 수백 번 발생한다. 여기에 DOM 측정이나 상태 업데이트를 그대로 붙이면 매 프레임마다 레이아웃 계산과 리렌더링이 일어나면서 스크롤이 끊긴다. 그렇다고 어제 배운 Debounce를 붙이면 안 되는 자리가 있다. 스크롤 진행률 표시줄을 debounce로 만들면 사용자가 스크롤을 멈출 때까지 막대가 움직이지 않는다. 여기서 필요한 건 최종 값이 아니라 중간 과정이다.

Debounce와의 차이 자체는 어제 표로 정리했으니 다시 그리지 않는다. 오늘 새로 본 건 그 안쪽이다.

가장 단순한 구현은 마지막 실행 시각 하나만 들고 있으면 된다.

```js
function throttle(fn, limit) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= limit) {
      last = now;
      fn.apply(this, args);
    }
  };
}
```

`last`를 클로저에 가둬 호출 사이의 상태를 유지하는 것이 전부다. 어제 debounce에서 `timer`를 가둔 자리에 오늘은 시각이 들어간다.

문제는 이렇게 쓰면 마지막 호출이 버려진다는 것이다. 주기가 시작될 때 한 번 실행하고 나면, 그 주기 안에 들어온 이벤트는 아무리 많아도 전부 무시된 채 주기가 끝난다. 그래서 무한 스크롤에서 바닥에 닿는 마지막 순간을 놓쳐 다음 페이지가 로드되지 않는 버그가 나온다. 주기 끝에 마지막 값을 한 번 더 실행하는 처리를 붙여야 사라진다.

```js
function throttle(fn, limit) {
  let last = 0;
  let timer = null;

  return function (...args) {
    const now = Date.now();
    const remaining = limit - (now - last);

    if (remaining <= 0) {          // 주기가 지났으면 즉시
      if (timer) { clearTimeout(timer); timer = null; }
      last = now;
      fn.apply(this, args);
    } else if (!timer) {           // 주기 끝에 마지막 값 한 번
      timer = setTimeout(() => {
        last = Date.now();
        timer = null;
        fn.apply(this, args);
      }, remaining);
    }
  };
}
```

이 둘 중 무엇을 켤지가 실무의 판단 지점이라고 한다.

| 설정 | 첫 호출 | 주기 안의 마지막 호출 | 맞는 자리 |
|---|---|---|---|
| leading만 | 즉시 실행 | 버려진다 | 마우스 좌표 전송처럼 최신값이 곧 또 오는 경우 |
| trailing만 | 주기 끝에 실행 | 반영된다 | 입력 중에는 조용하다가 결과만 보내는 경우 |
| 둘 다 | 즉시 실행 | 반영된다 | 무한 스크롤, 진행률 표시처럼 시작도 끝도 필요한 경우 |

한 가지 더 배운 건 setTimeout이 항상 최선은 아니라는 점이다. 스크롤 진행률이나 드래그 위치처럼 값이 곧장 화면에 그려지는 경우에는 `requestAnimationFrame`이 더 정확하다. 브라우저 렌더링 주기에 맞춰 돌기 때문에 화면에 그려지지도 않을 계산을 하지 않고, 백그라운드 탭에서는 알아서 멈춘다. 반대로 네트워크 요청이나 로깅처럼 시간 기준이 필요한 일은 setTimeout 쪽이다.

```js
function rafThrottle(fn) {
  let ticking = false;
  return function (...args) {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => {
      ticking = false;
      fn.apply(this, args);
    });
  };
}
```

React에서 걸리는 지점은 어제와 똑같다. 렌더링마다 함수가 새로 만들어지면 `last`도 매번 0으로 돌아가서 throttle이 아예 동작하지 않는다. `useMemo`로 참조를 고정하고, 리스너를 뗄 때 대기 중인 타이머까지 정리해야 한다. 스크롤 리스너라면 `{ passive: true }`도 사실상 기본값이다.

마지막 주의점이 오늘 제일 남는 문장이었다. Throttle은 부하를 없애주지 않는다. 콜백 안에서 `getBoundingClientRect()` 같은 강제 리플로우를 부르고 있으면 주기를 아무리 늘려도 여전히 무겁다. 실행 빈도를 줄이는 것과 한 번의 실행을 가볍게 만드는 것은 서로 다른 일이다.

## 2. 장표가 22장이 됐다

어제 21장에서 한 장이 늘었다. 사업성에 "언제 흑자가 되나"를 새로 만들었다.

어제 만든 원가 자립 지점 장이 결론만 말하고 있었다는 게 이유다. 하루 125판, 교육기관 2곳, 개인 유료 8명이라는 숫자는 있는데 그 숫자가 어디서 나왔는지가 없었다. 새 장에서는 축을 광고 단가로 잡았다. 광고 노출 수는 판당 사람 수 곱하기 광고 화면 수라서 4명에 1화면이면 노출 4회, 5명에 2화면이면 10회가 된다. 여기에 국내 RPM 1달러에서 2달러, 영어권 2달러에서 6달러 구간을 얹으면 판당 마진이 마이너스 20원에서 플러스 90원 사이에서 움직인다. 국내 구간에서는 광고 화면이 2개는 돼야 0원을 넘는다는 게 그래프로 바로 보인다.

봇 원가는 판당 25원 실측값을 썼다. 알리바바 콘솔에서 두 판에 1만 토큰이 나간 걸 잰 수치다.

나머지 셋은 고쳐 쓴 쪽이다.

| 바꾼 곳 | 전 | 후 |
|---|---|---|
| 02 기획 배경 | 페르소나 이서준의 불편 세 가지에서 기능 세 가지로 | 인터넷에서 본 "AI와 마피아게임을 하면 티나는 이유"에서 출발해 개선 루프 3단계로 |
| 04 시스템 설계도 | 화살표마다 라벨(화면 6개·상태 1개, GameState 전체 등) | 라벨을 걷어내고 덩어리와 경로만 |
| 대본 1~12쪽 | 어제 작성한 초안 | 장표에 맞춰 문장 정리, 총 6분 8초 배분은 유지 |

기획 배경을 갈아엎은 이유는 대본을 소리 내어 읽어보니 페르소나에서 시작하면 봇 얘기가 나오기까지 너무 오래 걸려서다. 이 프로젝트가 만들고 싶었던 건 게임이 아니라 봇이고, 라이어 게임은 그 봇을 관찰하려고 고른 그릇이다. 그렇다면 첫 장면도 "이런 사람이 불편해한다"가 아니라 "AI는 이 게임을 할 때 티가 난다"로 시작하는 편이 짧다. 50초짜리 장인데 페르소나까지 넣으면 어느 쪽도 제대로 못 한다.

설계도 라벨은 어제 대본을 쓰면서 이미 알고 있었다. 6쪽에서 네 곳만 짚기로 규칙을 정해놨는데, 정작 장표에는 짚지 않을 라벨이 열 개 넘게 붙어 있었다. 말하지 않을 걸 그려두면 듣는 사람은 그걸 읽느라 설명을 놓친다.

## 3. 질의응답 8분에 쓸 치트시트

파이널 프로젝트는 팀당 20분인데 그중 발표가 12분이고 질의응답이 8분이다. 발표 12분은 어제까지 대본으로 초 단위까지 통제했지만 8분 쪽은 아무 준비가 없었다. 그래서 오늘 A4 한 장짜리 Q&A 치트시트를 만들었다.

문항은 19개를 6개 묶음으로 나눴다.

| 묶음 | 문항 | 대표 질문 |
|---|---|---|
| 기술 선택 | 6 | 왜 SSR이 아니라 CSR인가, 왜 Vercel이 아니라 Railway인가 |
| 데이터와 DB | 3 | 왜 PostgreSQL인가, Supabase는 뭔가 |
| 봇과 자가개선 루프 | 5 | 봇이 진짜 스스로 개선되나, 개선됐다는 걸 어떻게 증명하나 |
| 보안과 안정성 | 3 | F12를 열면 제시어가 보이지 않나 |
| 프론트엔드 구현 | 2 | 페이즈가 8개인데 화면은 왜 1개인가 |
| 한 줄로 잇기 | 1 | 막혔을 때 돌아갈 문장 |

답은 전부 두세 문장으로 잘랐다. 8분에 19문항이 다 나올 리는 없지만, 길게 적어두면 그 자리에서 요약하느라 시간을 쓴다. 왜 Vercel이 아니냐는 질문에는 "WebSocket 연결 상한이 5분인데 저희 한 판은 그보다 깁니다" 한 줄이면 끝난다.

숫자가 들어가야 하는데 지금 확정할 수 없는 칸은 분홍색으로 칠해두고 발표 직전에 채우기로 했다. 테스트 판 수, 설문 응답 수, 발언 수 세 개다. 커밋 수와 파일 수도 8월 19일 기준 값이 아직 노트에 남아 있어서 같은 취급이다.

마지막 줄에는 규칙 세 개를 적었다. 모르는 건 "확인해 보고 말씀드리겠습니다"가 지어내는 것보다 낫다는 것, 숫자는 발표 직전에 다시 재는 것, 그리고 답이 막히면 돌아갈 문장 하나. "게임이 봇을 재고, 그 결과가 다시 게임으로 돌아갑니다."

## 4. 치트시트가 드러낸 어긋남

문항을 채우다 보니 자료끼리 말이 다른 자리가 나왔다.

첫째는 모델 비교다. 대본 11쪽에는 개발 중에 ChatGPT와 알리바바 API를 바꿔가며 테스트해서 유의미한 성능 차이를 확인했다고 적어뒀는데, 치트시트를 쓰면서 "여러 모델을 비교한 결과가 있나요"라는 문항에는 아직 없다고 적었다. 실제로는 둘 다 반쯤 맞다. 모델을 바꿔 돌리면서 봇이 말하는 게 확실히 달라지는 건 봤고 원가도 실측했지만, 봇 색출 정답률이나 티가 난 사유 분포를 수치로 재서 남긴 기록은 없다. 문제는 발표에서 "유의미한 성능 차이"라고 말하면 다음 질문이 반드시 "어떻게 측정하셨나요"라는 것이다. 체감으로 봤다고 말하고 벤치마크는 활용 방안이라고 말하는 편이 안전하다.

둘째는 어제 이미 적어둔 사업성 0단계 문구다. 교육기관 문의 4곳 발송 완료, 교원 커뮤니티 게시 완료로 적혀 있지만 실제로 한 건 애드센스 심사 신청 하나뿐이다. 오늘도 그대로 남아 있다.

셋째는 발표자 노트다. 기획 배경 장표를 통째로 바꿨는데 그 장의 노트에는 페르소나 이서준 설명이 그대로 남아 있다. 어제 대본을 별도 파일로 빼면서 노트를 갱신하지 않았고, 그러다 보니 장표 한 장에 서로 다른 두 벌의 설명이 붙어 있는 상태가 됐다.

오전에 배운 게 마침 이거였다. leading만 구현한 throttle은 주기 안에 들어온 마지막 호출을 버린다. 장표는 계속 고쳤는데 노트와 대본이 그 마지막 상태를 따라오지 않았으니 모양이 정확히 같다.
