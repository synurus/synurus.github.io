웹개발 수업 40일차. 5주차 코드리뷰는 처음으로 버그 있는 코드가 아니라 개념을 설명하는 문제였다. SPA가 무엇인지 정리했고, 팀 프로젝트 Zeteo는 38일차에 골라둔 방 목록 화면 시안(A3)을 실제로 만들어 서버에 연결했다.

## 1. 코드리뷰 ⑭: 이번 주는 버그가 아니라 정의였다

지금까지 다섯 번의 코드리뷰는 전부 코드를 실행해보고 기대와 실제가 왜 어긋나는지 추적하는 방식이었다. 이번 주 문제는 "SPA가 무엇인지 설명하시오"였다. 코드도, 기대도, 실제도 없다. 정의를 정확히 알고 있는지를 묻는 문제였다.

SPA(Single Page Application)는 최초 접속 시 브라우저가 HTML 문서 한 장을 받아온 뒤, 이후의 화면 전환을 서버에서 새 HTML을 다시 받지 않고 자바스크립트가 DOM을 직접 조작해서 처리하는 구조다. 화면을 바꿀 때 서버에 요청하는 건 완성된 페이지가 아니라 필요한 데이터뿐이고, 그 데이터를 받아서 다시 그리는 건 브라우저 쪽 몫이다. MPA와 나란히 놓으면 이 차이가 분명해진다.

| 구분 | MPA | SPA |
|---|---|---|
| 페이지 전환 | 매번 서버에 새 HTML 요청, 전체 새로고침 | 클라이언트 라우팅으로 URL만 바꾸고 부분 갱신 |
| 서버 역할 | HTML 렌더링까지 담당 | API 응답(JSON)만 담당 |
| SEO | 완성된 HTML이라 유리 | 초기 HTML이 비어 있어 불리 |

SEO는 SSR이나 프리렌더링으로, 초기 로딩 속도는 코드 스플리팅으로 보완한다는 게 이번 정리의 결론이다. 그런데 여기서 정리한 "서버는 데이터만 주고 화면은 클라이언트가 그린다"는 문장이, 오늘 마무리한 방 목록 화면 작업에 그대로 적혀 있었다.

## 2. 팀 프로젝트: Zeteo 방 목록 화면, 서버에 연결했다

38일차에 시안 6개 중 A3(필터·정렬이 있는 목록)를 베이스로 골랐다. 오늘은 그 시안을 실제 컴포넌트로 옮기고 서버(listRooms)에 연결했다.

### 목록의 모양은 서버 것을 그대로 쓴다

RoomStatus, RoomSummary 타입을 이 화면에서 새로 선언하지 않고 shared-types에서 가져왔다. 방 목록은 서버가 내려주는 데이터라, 이 화면이 임의로 모양을 정의하면 서버 응답과 어긋날 위험이 생긴다. 코드리뷰에서 정리한 것과 같은 이야기다. 데이터의 출처는 서버고, 화면은 그 모양을 그대로 따라야 한다.

```tsx
type RoomStatus = RoomSummary["status"];
```

props도 같은 원칙으로 짰다. nickname은 이 화면이 받지 않는다. 방장 이름은 서버가 목록에 담아 내려주고, join할 때 실어보낼 내 닉네임은 App.tsx가 이미 쥐고 있어서 여기엔 쓸 데가 없다. rooms, onRefresh, error 세 개만 props로 받는다. 목록의 출처는 서버, 이 화면은 요청하고 받은 걸 그리기만 한다.

### 한 번만 받아오고, 나머지는 사용자가 새로고침

```tsx
useEffect(() => onRefresh(), []);
```

화면에 들어올 때 딱 한 번 목록을 요청한다. onRefresh는 App.tsx가 렌더할 때마다 새로 만드는 함수라 의존성 배열에 넣으면 매번 다시 도는데, 그게 실제로 원하는 동작이 아니라서 진입 시 1회만 실행하도록 비워뒀다. 서버가 방 변화를 밀어주는 구조가 아니라 요청할 때만 응답하는 구조라, 목록은 진입한 순간과 새로고침 버튼을 누른 순간에만 최신이다. 실시간으로 안 맞을 수 있다는 걸 알고 쓰는 임시 타협이다.

### 없는 방 안내를 팝업으로 옮겼다

방번호를 직접 입력했는데 없는 방이면 서버가 에러를 돌려준다. 원래 이 에러는 App.tsx 상단에 빨간 배너로 떴는데, 방번호 입력칸에서 화면 높이만큼 떨어져 있어서 눈에 잘 안 들어왔다. 그래서 error를 이 화면이 props로 받아 팝업으로 다시 띄운다.

```tsx
const [prevError, setPrevError] = useState(error);
const [errorOpen, setErrorOpen] = useState(error !== null);
if (error !== prevError) {
  setPrevError(error);
  setErrorOpen(error !== null);
}
```

error 자체는 App.tsx가 쥐고 있어서 이 화면이 지울 수는 없다. 그래서 "이 사유를 닫았다"는 상태만 로컬에 따로 두고, 새 에러가 오면 다시 연다. 렌더 도중에 이전 값과 비교하는 이 패턴은 components/Modal.tsx에서 이미 쓰던 방식을 그대로 가져왔다. useEffect로 처리하면 리렌더가 한 번 더 끼어들기 때문이다.

### 방번호는 아직 클라이언트가 정한다

서버가 방번호를 발급하는 기능은 아직 없다. 그래서 방을 만들 때 클라이언트가 임의로 4자리 번호를 뽑는데, 이미 목록에 있는 번호를 뽑으면 join 로직상 그 번호로 그대로 들어가버려 남이 만든 방에 합류하는 사고가 난다. 그래서 현재 목록에 없는 번호만 뽑도록 걸러둔다. 서버가 번호를 발급하게 되면 이 로직은 통째로 사라질 임시 코드라는 것도 주석으로 남겨뒀다.

### A3 시안 그대로: 필터, 정렬, 진행바

전체/참여 가능 필터, 인원 적은순부터 과거순까지 정렬 네 가지, 방마다 정원이 얼마나 찼는지 보여주는 진행바까지 시안에 있던 요소를 그대로 옮겼다. 방번호를 이미 아는 사람을 위한 직접입력 토글도 목록 아래 남겨뒀다.

돌아보면 이 화면이 하는 일은 결국 서버가 준 rooms 배열을 필터링하고 정렬해서 다시 그리는 것뿐이다. 서버에 새 페이지를 요청한 적은 한 번도 없다. 오늘 코드리뷰에서 정리한 SPA 정의를 그대로 옮겨놓은 화면이었다.
