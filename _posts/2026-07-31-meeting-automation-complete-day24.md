웹개발 수업 24일차. 어제 기획·설계까지 만들었던 **회의록·채널 요약 자동화 시스템을 완료**했다. 오늘의 작업은 **유저 시나리오 문서 작성**, 즉 만든 기능을 "누가, 언제, 왜 쓰는가"로 다시 쓰는 일이었다. 그리고 시나리오를 쓰다가 이 시스템에서 가장 중요한 게 뭔지 다시 알게 됐다.

## 1. 완성된 산출물

| 산출물 | 내용 |
|---|---|
| Skill 문서 2종 | `channel-summarize`(즉시 요약 답장) · `meeting-minutes`(파일 저장 + 커밋·푸시) |
| `team-map.json` | Discord 핸들·사용자ID·실명, 채널명·채널ID 매핑 |
| 플러그인 확장 코드 | 서버(길드) 단위 접근 확장, 참여자ID 노출 |
| 회의록 결과물 | 저장소 `회의록/` 폴더에 `날짜_주제_회차_회의록.md` 형식으로 누적 |
| 문서 | 기획서 · 시스템 설계도(와이어프레임) · **유저 시나리오** ← 오늘 |

## 2. 유저 시나리오: 기능을 "순간"으로 다시 쓰기

기능 목록은 *"무엇을 만들었나"*를 말하지만, 시나리오는 *"이게 왜 필요한가"*를 말한다. 네 가지 **순간**으로 정리했다.

### ① 회의록을 놓치지 않고 남기고 싶은 순간

논의는 30분간 이어졌고 결론도 났는데, 아무도 정리해 문서로 남기지 않은 상태다. 채널에 한 줄만 치면 된다.

```
@봇 회의록 작성해줘 PT
```

채널 ID는 메시지에 자동으로 포함되므로 따로 입력할 필요가 없다. 시스템은 대화 수집 → 실명 매핑 → 3단 구조(현재 주제 / 논의 내용 / 다음 목표) 작성 → git 안전장치 통과 후 커밋·푸시를 거치고, 참여자 전원에게 `@멘션`으로 알린다. 논의가 끝난 그 순간의 맥락이 사라지기 전에, 사람이 다시 읽고 요약할 필요 없이 문서로 고정되는 게 핵심이다.

### ② 잠깐 자리를 비운 사이의 논의를 따라잡고 싶을 때

다른 채널에서 논의가 오갔는데 메시지가 많아 처음부터 읽기엔 부담스러운 상황. 이때는 파일로 남길 필요 없이 결론만 알면 된다.

```
@봇 여기 요약해줘
```

화자별로 정리하고 Discord 마크다운으로 구조화한 뒤 결론까지 붙여 그 자리에 바로 답장한다. "다시 읽기" 대신 "결론만 확인"으로 대화 추적 비용을 없앤 셈이다. 저장소에 남기지 않아도 되는 가벼운 확인 용도에 맞춘 기능이다.

①과 ②를 나누길 잘했다는 생각이 들었다. 둘 다 "요약"이지만 하나는 기록이고 하나는 확인이라, 결과물이 파일이냐 채팅이냐가 달라진다.

### ③ 새 채널을 만들자마자 봇이 바로 반응하는 순간

팀원이 새 채널을 개설했을 때, 기존 방식이라면 봇 접근 권한을 수동으로 다시 등록해야 하는 상황이다. 어제 만든 서버 단위 폴백이 여기서 눈에 보이는 가치가 된다: 채널 개별 등록이 없어도 서버가 등록돼 있으면 자동 허용되고, 스레드는 부모 정책을 상속받는다. "새 채널이 생길 때마다 수동 등록"이라는 운영 부담이 사라지는 셈이고, 팀 구조가 계속 바뀌는 프로젝트 환경엔 이 편이 맞는다.

기능 설명("guilds 필드 신설 + 폴백 로직")은 코드 이야기지만, 시나리오로 쓰면 "별도 설정 없이 그냥 된다"는 사용자 경험이 된다. 같은 작업을 두 언어로 번역한 느낌이었다.

### ④ 예상과 다른 상황에서 시스템이 스스로 멈추는 순간 ★

이 시나리오를 넣은 게 오늘 가장 잘한 선택이라고 생각한다.

다른 팀원이 아직 커밋하지 않은 작업물을 남겨뒀거나, 원격에 새 커밋이 먼저 올라와 충돌 가능성이 있는 상태를 가정해보자. 사용자는 평소와 똑같이 회의록 작성을 요청한다.

이때 git 안전장치가 순서대로 확인한다: ① 새 회의록 파일 외 다른 변경 사항 ② `main` 브랜치 여부 ③ pull 시 충돌 ④ 새 파일 1개만 선택 반영 ⑤ push 거부·실패. 하나라도 예상과 다르면 즉시 중단한다.

회의록 파일 생성 자체는 끝나지만 저장소에는 반영되지 않고, 정확한 중단 사유와 함께 사람에게 보고된다. 다른 팀원 작업물을 임의로 덮어쓰거나 강제 push하지는 않는다.

"정상 상황에서는 끝까지 자동으로, 조금이라도 예상과 다르면 반드시 멈추고 사람에게 알린다"는 설계 원칙이 실제로 작동하는 걸 보여준다. 자동화를 믿을 수 있는 이유가 여기 있다.

보통 유저 시나리오는 잘 되는 경우(happy path)만 쓴다. 그런데 자동화 도구에서 사용자가 진짜로 알고 싶은 건 "이게 언제 사고를 치는가"다. 안 치고 멈춘다는 걸 보여주는 것 자체가 기능이었다.

### 네 시나리오가 각각 증명하는 것

| 구분 | ① 회의록 작성 | ② 채널 요약 | ③ 신규 채널 커버 | ④ 안전장치 발동 |
|---|---|---|---|---|
| 트리거 | 논의 종료 후 기록 필요 | 논의를 놓쳐 따라잡기 | 새 채널·스레드 개설 | 저장소 상태 이상 |
| 결과물 | GitHub 파일 + 멘션 | 채팅 즉시 답장 | 등록 없이 즉시 반응 | 중단 + 사유 보고 |
| 보여주는 가치 | **기록의 자동화** | **탐색 비용 제거** | **운영 확장성** | **자동화의 신뢰성** |

표로 정리하고 나니 각 시나리오가 서로 다른 축의 가치를 증명하고 있어서, 네 개면 충분하다는 확신이 생겼다. 발표에서도 이 표 한 장이면 될 것 같다.

## 3. 시나리오를 쓰며 배운 것

**⑴ 기능 목록과 시나리오는 방향이 반대다.** 기능 목록은 만든 사람 시점(무엇을 구현했나)이고, 시나리오는 쓰는 사람 시점(어떤 순간에 필요한가)이다. 같은 작업물을 두 번 쓰는 게 낭비 같았는데, 실제로 써보니 시나리오를 쓰다가 기능의 존재 이유가 정리됐다. ①과 ②의 차이(기록 vs 확인)도 시나리오를 쓰다 명확해진 것이다.

**⑵ 페르소나가 있으면 문장이 구체적이 된다.** "사용자가 요약을 요청한다"보다 "메시지가 많아 처음부터 읽기 부담스러운 팀원이 결론만 알고 싶어 한다"가 훨씬 잘 읽힌다. 21일차 팀 기획서에서 페르소나를 쓸 때는 형식인 줄 알았는데, 직접 써보니 문장을 구체적으로 만드는 장치였다.

**⑶ 실패도 설계의 일부로 보여줄 수 있다.** ④가 그렇다. 리스크 표에 "충돌 시 중단"이라고 적는 것과, 시나리오로 "이럴 때 이렇게 멈추고 이렇게 알려준다"를 보여주는 건 설득력이 다르다.

## 4. 미니프로젝트 회고

이번 자동화는 내 불편함에서 출발해 팀의 도구가 된 첫 사례였다.

- 18일차: 내 `.md` 파일이 안 열려서 → **스킬** 제작 (혼자 쓰는 도구)
- 19일차: 스킬을 까먹어서 → **훅** 제작 (혼자 쓰는 도구)
- 23~24일차: 팀 논의가 흩어져서 → **스킬 2종 + 플러그인 확장** (팀이 쓰는 도구)

혼자 쓸 때는 고장 나도 나만 불편하면 끝이었는데, 팀 저장소에 푸시하는 순간 남의 작업물이 걸린다. git 안전장치 5개와 시나리오 ④가 나온 이유가 그것이다. 자동화의 난이도는 기능이 아니라 영향 범위에서 온다는 걸 배웠다.
