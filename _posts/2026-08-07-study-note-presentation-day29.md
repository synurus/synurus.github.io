웹개발 수업 29일차. 어제 기획서·시나리오·설계도까지 완료한 **스터디 시스템**을 오늘 `SKILL.md` 하나로 실제 구현하고, 발표까지 마쳤다. 기획이 코드가 되는 과정에서 어제 문서엔 없던 디테일이 여럿 추가됐고, 발표 준비를 하며 이 시스템이 "왜 특별한지"가 세 문장으로 정리됐다.

## 1. 기획 → 코드: SKILL.md에서 새로 생긴 것들

어제 기획서의 절차를 그대로 옮기면서도, **실제로 짜다 보니 기획서엔 없던 안전장치 몇 개가 추가**됐다.

### 도구 권한을 명시적으로 선언

```yaml
allowed-tools:
  - mcp__plugin_discord_discord__reply
  - Read
  - Write
  - Grep
  - Glob
  - Bash(git *)
  - Bash(ls *)
  - Bash(mkdir *)
```

이 스킬이 **정확히 무엇을 할 수 있는지**를 앞머리에 못 박았다. 18일차에 만든 markdown-reader 스킬은 이런 선언이 없었는데, 이번엔 **팀 저장소에 쓰기를 하는 스킬이라 권한 범위를 좁혀 명시**했다. `Bash(git *)`처럼 허용 명령을 패턴으로 제한하는 것도 눈에 띄었다: "뭐든 다 해도 됨"이 아니라 "이 셋만 됨".

### 두 저장소를 헷갈리지 않게: 경로를 문서 맨 위에

```
코드 조사 대상: .../Project/Zeteo   (읽기만, 모든 원격 브랜치)
결과물 저장 위치: .../Frontend/TeamB/2주차/배운개념/   (main만 쓰기)
```

19일차 회의록 시스템 때 이미 겪었던 "조사 대상과 저장 위치는 다른 저장소"라는 함정을, 이번엔 **스킬 문서 맨 위에 굵게 박아뒀다.** 같은 실수를 반복하지 않으려고 이전 시스템에서 배운 교훈을 문서 구조 자체에 반영한 것.

### git grep 명령이 구체적인 문법으로 완성됨

어제 기획서는 "모든 원격 브랜치를 grep으로 검색"이라는 아이디어였는데, 오늘 실제 명령이 이렇게 확정됐다:

```bash
git fetch origin --quiet
git branch -r                                    # origin/HEAD 제외
git grep -n -i -e <키워드1> -e <키워드2> ... -- $(모든 origin/* 브랜치)
git show <브랜치>:<파일경로>
```

- `-n`(줄번호) `-i`(대소문자 무시) `-e`(키워드 여러 개 OR 검색), 주제 하나에 관련어를 여러 개 준비해서(예: 웹소켓 → `websocket`, `socket.io`, `ws`) 검색 범위를 넓혔다
- **어느 브랜치에서 찾았는지도 기록해둘 것**을 명시, 나중에 활용처 서술에 브랜치명이 근거로 들어가야 하니까

### git 안전장치 7단계: 실패 조건이 더 촘촘해졌다

23일차 회의록 시스템의 5단계 안전장치가 오늘은 **7단계**로 늘었다. 추가된 것:

```
1. git status --porcelain      — 새 파일 외 변경사항 있으면 중단
2. git branch --show-current   — main 아니면 중단
3. git pull --ff-only          — 실패하면(충돌) 중단, 강제 병합 금지
4. git add "2주차/배운개념/<파일명>"  — 새 파일 하나만, add -A/. 금지
5. git status로 스테이징이 그 파일 하나뿐인지 재확인   ← 신규
6. git commit
7. git push — 실패하면 중단, --force 절대 금지
```

**5번(재확인)이 새로 붙었다.** `add`로 파일 하나만 넣었다고 믿지 말고, **커밋 직전에 한 번 더 확인**하는 절차. 26일차에 "삭제는 충돌로 안 뜬다"를 겪었던 경험이, 이번엔 "add도 의도대로 됐는지 눈으로 재확인한다"는 습관으로 이어진 것 같다.

## 2. 발표: 스스로 만든 것을 다시 설명하며 알게 된 것

발표자료(14슬라이드)를 준비하면서, 만들 때는 몰랐던 것들이 문장으로 정리됐다.

### AS-IS/TO-BE로 문제를 다시 보다

발표에서 기존 방식의 문제를 세 줄로 정리했다:

| AS-IS (수작업) | TO-BE (스터디 시스템) |
|---|---|
| 한 줄 선언으로 끝남: "웹소켓 배웠어요" | 명령 한 줄이면 문서가 나옴, 항상 같은 형식 |
| 활용처가 본인 진술뿐, 검증 불가 | 활용처를 코드에서 직접 조사 |
| 매번 형식이 제각각, 팀에서 다시 읽기 어려움 | 팀 저장소에 그대로 누적 |

기획할 때는 "활용처를 검증 가능하게 만들자"는 것만 생각했는데, 발표를 준비하며 보니 **"형식이 통일된다"는 것도 독립된 가치**였다. 사람마다 정리 형태가 다르면 팀이 다시 읽는 비용이 생긴다. 이건 처음 설계할 땐 명시적으로 안 짚었던 부분이다.

### 기각한 안까지 슬라이드에 넣은 이유

발표자료 9번 슬라이드는 **채택한 방법 옆에 기각한 방법 4개를 나란히** 뒀다: Discord 아티팩트, 새 스레드, 로컬 grep, GitHub API. 그리고 이렇게 마무리했다:

> **설계 결정에는 근거가 있습니다. 기각 사유까지 기획서에 함께 남겼습니다.**

20일차 조사 보고서의 `미검증` 표기, 22일차 기획서의 "최초라고 주장하지 않는다"에 이어, **이번엔 "안 한 것도 보여준다"**는 형태로 같은 태도가 이어졌다. 뭘 했는지만 말하면 반론에 약하지만, 뭘 안 했고 왜 안 했는지까지 말하면 판단 과정 자체가 근거가 된다.

### 발표에서 정리된 세 가지 배움

결론 슬라이드에서 스스로 정리한 문장들이 이 프로젝트를 가장 잘 요약한다.

> **1. "배웠다"를 증명하려면 근거의 출처를 바꿔야 했다.** 본인 진술 대신 코드에서 찾게 하는 것만으로 기록의 신뢰도가 달라졌다.
>
> **2. 로컬 저장소는 팀 전체의 현재 상태가 아니다.** 브랜치로 나눠 일하면 내 작업 트리에는 팀의 절반이 안 보인다는 걸 이번에 알았다.
>
> **3. 못 찾았다고 쓰는 것도 기능이다.** 지어내지 않게 막는 규칙이 정확도를 지키는 가장 큰 장치였다.

2번은 26·27일차에 Zeteo 본작업에서 이미 겪은 것이었다. *"dev만 보면 팀 상태를 오판한다", "원격만 봐서는 남의 로컬 작업을 못 본다"*. 그날은 **사고를 막기 위한 방어 지식**이었는데, 오늘은 그 지식이 **새 시스템을 설계하는 재료**가 됐다. 같은 배움이 "조심할 것"에서 "만들 수 있는 것"으로 자리를 옮긴 셈이다.

3번도 다시 보면 낯익다. 17일차에 "AI 출력은 검증 대상"이라고 배웠고, 22일차 봇 프로젝트 기획의 "프롬프트 인젝션 방어가 구조적"이라는 설계와 같은 계열이다. **"정직하게 실패를 보고하는 것"**이 이 팀의 반복되는 설계 원칙이 되어가고 있다.

### 소개하고 싶은 내용: 학습 기록을 넘어선 범용성

발표 마지막에 이 문장을 넣었다:

> 체크아웃하지 않고 모든 원격 브랜치를 한 번에 검색하는 방법: **학습 기록뿐 아니라 코드 리뷰·구조 파악에도 그대로 쓸 수 있는 방식입니다.**

`git fetch` → `git grep` → `git show` 세 줄이 처음엔 "학습 근거를 찾는 도구"로 만들어졌는데, 발표를 준비하며 보니 **범용 조사 도구**였다는 걸 스스로 발견했다. 도구의 진짜 쓸모는 만들 때보다 설명할 때 더 잘 보이는 것 같다.

## 3. 이번 주를 돌아보며: 1주차와 2주차의 차이

| | 1주차 (회의록 자동화) | 2주차 (스터디 시스템) |
|---|---|---|
| 만든 이유 | 내 불편함 (md가 안 열림 → 팀 논의가 흩어짐) | **과제 요구사항** (학습 의지 증빙) |
| 저장 패턴 | 새로 설계 | **1주차 패턴 재사용** |
| git 안전장치 | 5단계, 이번 주 처음 설계 | 7단계, **재확인 단계 추가** |
| 조사 방법의 배경 지식 | - | **26·27일차 병합 사고 경험이 재료가 됨** |

한 주 사이에 "새로 만드는 것"에서 "이미 아는 것을 재사용하고 다듬는 것"으로 무게중심이 옮겨갔다. 이게 아마 3주차부턴 더 뚜렷해질 것 같다.
