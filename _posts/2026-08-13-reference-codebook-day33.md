웹개발 수업 33일차. 코드리뷰는 `const`로 선언한 배열을 백업했는데 원본이 같이 바뀌는 사고. 팀 프로젝트 Zeteo는 이번 주 "코드를 이해할 수 있는가?" 평가 항목에 맞춰, 팀원 4명이 서로 자기 파트만 아는 문제를 푸는 [코드리뷰 시스템](분기형 코드북)을 기획했다.

## 1. 코드리뷰 ⑪: 백업했는데 왜 원본이랑 같이 바뀔까

메뉴 개편 시나리오. "백업은 개편 전 상태로 남아 있어야 한다"는 의도로 짠 코드.

```js
const menu = ['김치찌개', '된장찌개', '비빔밥'];

const backup = menu;        // 개편 전 메뉴 백업

menu.push('냉면');           // 여름 신메뉴 추가
menu[0] = '김치찜';          // 김치찌개 → 김치찜으로 교체

console.log('개편 후 메뉴:', menu);
console.log('개편 전 백업:', backup);
```

**기대:** `개편 전 백업: [ '김치찌개', '된장찌개', '비빔밥' ]`
**실제:** `개편 전 백업: [ '김치찜', '된장찌개', '비빔밥', '냉면' ]`. `menu`와 완전히 동일하다.

### Q1·Q2: `const`는 "재할당 금지"지 "복사"가 아니다

원인은 백업하는 그 줄이다.

```js
const backup = menu;
```

배열은 객체 타입이라, 자바스크립트에서 대입은 값이 아니라 참조(메모리 주소)를 복사한다. `backup`은 별도의 새 배열이 아니라 `menu`가 가리키는 것과 동일한 배열을 가리키는 또 하나의 이름표일 뿐이다. `const`는 "변수 자체를 다른 값으로 재할당하지 못하게" 막는 것이지, 그 변수가 가리키는 객체의 내부 내용을 얼려주지는(freeze) 않는다. 그래서 이후 `menu.push('냉면')`, `menu[0] = '김치찜'`처럼 배열 내부를 바꾸는 코드는 `menu`가 가리키는 원본 자체를 수정하고, `backup`도 같은 배열을 보고 있으니 똑같이 바뀐 것처럼 보인다.

정리하면, 배열·객체를 `=`로 대입하는 건 "복사"가 아니라 "같은 실체를 가리키는 이름표를 하나 더 만드는 것"이다.

### 수정: 새 배열을 명시적으로 만든다

```js
const backup = [...menu];   // 스프레드 문법으로 새 배열 생성
// 또는: const backup = menu.slice();
// 또는: const backup = Array.from(menu);
```

요소가 문자열 같은 원시값뿐이면 이 얕은 복사로 충분하다. 배열 안에 객체가 들어 있어 깊은 복사까지 필요하면 `structuredClone(menu)`(모던 환경) 또는 `JSON.parse(JSON.stringify(menu))`를 고려해야 한다. 다만 `[...menu]`나 `.slice()`로는 내부 객체까지는 못 떼어낸다.

### 나흘째 이어지는 "JS의 기본 동작을 의심하라"

30일차(`+`가 문자열이면 연결로 돌변)부터 31일차(`replace()`는 원본을 안 바꿈), 32일차(`sort()`의 기본값은 문자열 비교)에 이어 오늘까지, 나흘 연속 "당연히 이럴 것"이라 믿은 기본 동작이 실제와 달랐던 사고다.

| | 착각한 것 | 실제 |
|---|---|---|
| 30일차 | `+`는 항상 덧셈 | 문자열이 섞이면 연결 |
| 31일차 | `replace()`가 원본을 바꿔줌 | 새 문자열을 반환만 함 |
| 32일차 | `sort()`는 숫자 크기로 정렬 | 기본은 문자열 비교 |
| 33일차 | `const`로 선언하면 안전함 | 재할당만 막을 뿐, 내부 변경(mutate)과 참조 공유는 못 막음 |

네 사고 모두 원시값과 객체를 구분하지 않고 "값이 어련히 이렇게 다뤄지겠지"라고 가정한 지점에서 났다. `const`가 안전망처럼 느껴지는 게 특히 위험한데, **재할당 금지 ≠ 불변(immutable)** 이라는 걸 이번에 확실히 정리했다.

## 2. 팀 프로젝트: 분기형 코드북으로 푸는 [코드리뷰 시스템]

3주차 평가 항목 "코드를 이해할 수 있는가?"에 대한 답을 만드는 주간 과제. 4명이 파트를 나눠 개발하면서 각자 자기 코드만 아는 상태가 됐다는 문제에서 출발했다.

### 실제로 있었던 일

| 언제 | 무슨 일 |
|---|---|
| 8/11 | 박진이 "뭔가 없어서 공용 컴포넌트를 못 만들겠다"고 함. 실제로는 테마 결정권이 자기에게 있다는 걸 몰랐던 것 |
| 8/12 | 유민성이 `knowledge.ts`를 독립적으로 만듦. 봇 쪽에서 같은 기능을 이미 검토하고 보류한 걸 몰랐던 것 |
| 8/12 | PR 12개 중 리뷰가 달린 것은 **1개뿐** |

"리뷰를 안 한 게 아니라, 남의 코드를 읽을 진입로가 없었다." PR 리뷰는 바뀐 줄(diff)만 보여주는데, 우리가 겪은 문제는 *"이 파일이 애초에 뭘 하는 파일인지"*를 모르는 것이었다. diff만 봐서는 그게 안 채워진다. 게다가 팀원마다 밝은 영역이 다르다: 이현우는 프론트, 유민성은 DB·서버, 박진은 화면, 김정현은 봇·계약. 한 줄짜리 설명 문서는 한 명을 지루하게 하고 다른 한 명을 놓친다.

### 해결책: 게임북처럼 갈라지는 문서

읽는 사람의 수준에 따라 경로가 갈리는 문서를 파일마다 하나씩 만든다.

```
1번  "봇이 서버 안에서 도는지 밖에서 도는지 아시나요?"
       예   → 6번 (구조부터)
       아니오 → 2번 (짧은 설명을 거쳐 6번으로)
```

아는 사람은 4단계, 처음인 사람은 12단계를 거치지만 도착점은 같다. 핵심 원칙 다섯 가지:

| 원칙 | 이유 |
|---|---|
| ZETEO 안에서만 성립하는 설명 | "SDK란 무엇인가"는 검색하면 나온다. 필요한 건 "이 함수가 게임의 어느 순간에 불리는가" |
| 연결을 설명한다 | 파일 하나를 이해하는 게 아니라, 다른 파일·전체 흐름과 어떻게 물리는지가 목적 |
| 도착점 명시 | 마지막 노드에 "이제 설명할 수 있는 것" 목록. 평가 항목과 직접 대응 |
| 깨지면 어떻게 되는가 | 그 코드가 없거나 잘못되면 게임에서 무슨 일이 벌어지는지 |
| 빠른 경로도 내용은 안 건너뛴다 | 건너뛰는 건 선행 개념 설명이지 코드가 아니다 |

### 첫 시안을 버린 이유

`llm.ts`로 만든 첫 코드북은 폐기했다. 노드·분기는 갖췄는데 내용이 **"SDK란 무엇인가" · "지연 초기화 패턴이란" · "환경변수를 쓰는 이유"**처럼, 이 파일이 없어도 성립하는 일반 프로그래밍 글이었다. 다 읽어도 *"이 코드가 ZETEO에서 무슨 역할인지"*는 여전히 모른다. 그래서 분기 질문의 기준부터 바꿨다.

```
❌ "SDK 써보셨나요?"                     일반 지식
✅ "봇이 서버 안에서 도는지 아시나요?"    ZETEO 지식
```

노드 구성도 "개념 설명 반복 → 마지막에 연결 표 한 줄"에서 "전체 그림에서의 위치 → 누가 언제 부르는가 → 핵심 함수들 → 깨지면 무슨 일이 → 바깥과의 계약 → 도착"으로 뒤집었다.

### 운영 방식과 자동화

```
① 디스코드 #code-book 채널 핀 메시지에 파일 트리(메뉴판)
② 읽고 싶은 파일 경로를 채팅에 적는다
③ 김정현이 모아서 코드북 생성 → TeamB 저장소에 커밋
④ 읽은 사람이 "이제 ___를 설명할 수 있습니다" 한 줄 남긴다
⑤ 막힌 노드 번호를 적으면 그 노드를 쪼개서 개선
```

④가 이 시스템의 증거다. 문서를 AI가 썼더라도, "A가 X를 몰랐는데 이제 설명할 수 있다"는 사람의 기록이기 때문이다. ③을 매번 손으로 하면 품질이 들쭉날쭉해지니, 생성 규칙을 `/codebook` 스킬에 고정했다. 설계에서 가장 어려웠던 지점은 "맥락 전달"이었다. 코드만 읽어서는 왜 그렇게 짰는지 알 수 없고, 그러면 첫 시안처럼 검색하면 나오는 글이 만들어진다. 그래서 스킬에 0단계(배경 지식을 먼저 채운다)를 넣었다.

| 넣은 것 | 없으면 못 쓰는 것 |
|---|---|
| 설계원칙 5 | `view.ts`가 왜 유일한 관문인지 |
| 파트 분담표 | 누가 왜 이 파일을 만들었는지 |
| 구조 요약(화면 5개·게임 흐름·루프 2개) | 이 파일이 게임의 어느 순간에 동작하는지 |
| 코드 모양을 결정한 실제 사건 6건 | 왜 이 방어 코드가 존재하는지 |

마지막이 특히 중요하다. 예를 들어 "프롬프트는 경향을 만들 뿐 보장하지 않는다". 봇의 제시어 유출을 프롬프트로 두 번 막았다가 두 번 다 뚫린 뒤 얻은 결론인데, 이 문장은 코드 어디에도 적혀 있지 않다. 그런데 이걸 모르면 `bot/index.ts`의 검사 4종이 왜 있는지 설명할 수 없다.

### 왜 이 방식을 골랐나

| 방식 | 문제 |
|---|---|
| 각자 문서 하나씩 작성 | 발표까지 6일. 팀원이 반나절씩 쓸 시간이 없다 |
| PR 리뷰만 강화 | 남은 PR이 적어 증거가 안 쌓인다. diff만으로는 파일 전체를 이해 못 한다 |
| 전체 아키텍처 문서 하나 | 수준 차이를 흡수 못 한다. 길면 아무도 안 읽는다 |
| **분기형 코드북 (채택)** | 팀원은 경로 한 줄만 적으면 된다. 수요가 있는 파일만 만들어 낭비가 없다 |
