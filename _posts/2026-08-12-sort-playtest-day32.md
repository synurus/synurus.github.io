웹개발 수업 32일차. 코드리뷰는 **`sort()`의 기본 정렬이 문자열 기준**이라는 함정. 팀 프로젝트 Zeteo는 시안 1을 실제 화면에 적용 완료하고 **첫 게임플레이 테스트**를 돌렸다. 실제로 사람들이 플레이해보니 화면만 봐서는 안 보이던 문제가 열 몇 개 쏟아졌다.

## 1. 코드리뷰 ⑩ — sort()는 왜 900을 맨 뒤로 보냈나

쇼핑몰 가격을 "낮은 가격순"으로 정렬하려는 코드.

```js
const prices = [12000, 900, 45000, 3500];
prices.sort();
console.log('낮은 가격순:', prices);
```

**기대:** `[900, 3500, 12000, 45000]` **실제:** `[12000, 3500, 45000, 900]`

### Q1·Q2 — sort()의 기본값은 "문자열 비교"

`Array.prototype.sort()`는 **비교 함수를 넘기지 않으면 각 요소를 문자열로 바꿔서 유니코드 순서로 비교한다.** 숫자 배열이라도 예외가 없다.

`[12000, 900, 45000, 3500]`을 문자열로 보면 `"12000"`, `"900"`, `"45000"`, `"3500"` — **첫 글자부터 비교**하면 `"1..." < "3..." < "4..." < "9..."`. 그래서 900이 맨 뒤로 밀린다. 크기가 아니라 **첫 자릿수**로 줄을 세운 것.

**수정:**

```js
prices.sort((a, b) => a - b);
```

두 값을 받아 "음수면 앞, 양수면 뒤, 0이면 그대로"라는 비교 규칙을 직접 알려주는 콜백. 이게 있어야 숫자 크기로 정렬된다.

### 덤으로 — sort()도 원본을 바꾼다 (mutate)

```js
// 원본을 보존하고 싶다면
const sortedPrices = [...prices].sort((a, b) => a - b);
const sortedPrices = prices.toSorted((a, b) => a - b);  // ES2023+
```

### 사흘째 이어지는 "JS의 기본 동작을 의심하라"

30일차(`+`가 문자열이면 연결로 돌변) → 31일차(`replace()`는 원본을 안 바꿈) → 오늘(`sort()`의 기본값은 문자열 비교). **셋 다 "이럴 것"이라고 믿은 기본 동작이 실제와 달랐던 사고**다. 세 버그의 공통점을 정리하면:

| | 착각한 것 | 실제 |
|---|---|---|
| 30일차 | `+`는 항상 덧셈 | 문자열이 섞이면 연결 |
| 31일차 | `replace()`가 원본을 바꿔줌 | 새 문자열을 반환만 함 |
| 32일차 | `sort()`는 숫자 크기로 정렬 | 기본은 문자열 비교 |

**JS의 배열·문자열 메서드는 "당연해 보이는 기본값"이 의외로 안전하지 않다.** `+`, `replace`, `sort` 셋 다 실무에서 가장 자주 쓰는 도구인데, 셋 다 함정이 있다는 게 이번 주 코드리뷰가 가르쳐준 것 같다.

## 2. 팀 프로젝트 — 첫 게임플레이 테스트, 그리고 피드백 폭탄

시안 1을 6개 화면에 실제로 적용하고, 오늘 처음으로 **사람이 직접 플레이**해봤다. 코드가 빌드되고 화면이 렌더된다고 "완성"이 아니라는 걸 확인한 날.

### 피드백을 세 갈래로 나눠서 본다

받은 피드백을 그대로 나열하지 않고, **원인이 겹치는 것끼리** 묶어봤다.

#### ① 디자인 토큰이 화면에 도착하지 못했다

> 파트D 지침이 제대로 적용 안됨 — 채팅입력창·전송버튼, 내 채팅 우측 정렬, 상단바(제시어·타이머), 전체적으로 크기 키우기(로고, 폰트 볼드체)

25·31일차에 그렇게 강조했던 `var(--토큰, fallback)` 패턴인데, **실제 화면에서는 D의 최신 지침이 안 보이는** 상태다. 원인 후보를 정리하면:

- fallback 값이 여전히 우선 적용되고 있을 가능성 (토큰 이름 불일치)
- 31일차 병합 가이드에서 처리한 `tokens.css`가 실제 배포 화면에는 아직 안 올라갔을 가능성
- 컴포넌트 단에서 CSS 변수가 아니라 **리터럴 값을 직접 쓴 부분**이 남아있을 가능성

병합 가이드에 있던 원칙 — *"리터럴 금지, 토큰만"* — 이 **문서로는 지켜졌지만 실제 렌더에는 아직 완전히 반영되지 않았다**는 게 드러난 셈. 코드가 옳아도 화면에서 확인 안 하면 모른다.

#### ② 봇 투표창 — "작동은 하는데 신뢰가 안 간다"

> 클릭이 제대로 되는지? 클릭 후 반응(선택된 항목 하이라이트) / 모바일에서 화면이 별로임 / 익명투표 안내문 삭제

**"작동하지 않는다"가 아니라 "작동하는지 확신이 안 든다"는 피드백.** 클릭이 실제로 됐는지 사용자가 판단할 근거(하이라이트)가 없으면, 기능은 있어도 신뢰가 안 생긴다. 21일차 코드리뷰에서 배운 "보이는 것과 동작하는 것은 다르다"의 반대 방향 문제다 — 이번엔 **동작은 하는데 보이지 않는 것.**

"익명투표 안내문 삭제"는 흥미로운 요청이다. 27일차 인수인계 문서에서 확인했듯 봇 지목은 **익명이 아니라 실명 후보 목록**으로 설계됐는데, 오래된 안내 문구가 남아 사용자에게 잘못된 기대를 준 것 같다. 21일차의 "형식이 통일되지 않으면 팀이 다시 읽기 어렵다"는 게 UI 문구에도 똑같이 적용된다.

#### ③ 스크롤과 팝업 — 실사용에서만 드러나는 문제

이게 가장 많고, 실제로 플레이해보지 않으면 절대 안 보였을 것들이다.

> - 화면이 내려갔을 때 팝업창 위치 → **스크롤을 따라다니게**
> - 새 채팅이 뜨면 화면이 아래로 내려가서 위 채팅을 계속 읽기 불편함 → 새 채팅은 로그 **아래에 표시**
> - 게임 중 스크롤바는 **채팅로그만** 뜨게
> - 팝업창이 뜨면 투표현황창이 안 나옴 (PC에서도 투표현황창 클릭 시 투표창 뜨게?)
> - 묘사(describe)-토론(debate) 사이에 **분리선 없음** — 가독성 문제

이 다섯 개를 하나로 묶는 문장이 있다: **"자동으로 움직이는 화면과 사용자가 보고 있는 지점이 어긋난다."** 팝업이 스크롤을 안 따라오고, 새 메시지가 오면 강제로 스크롤이 내려가고, 전체 페이지가 스크롤되는 바람에 채팅 로그만 스크롤돼야 할 게 다 같이 움직인다. **레이아웃 코드로는 안 보이고, 손가락으로 스크롤해봐야만 걸리는 문제들.**

30일차 시안 비교 때 "화면을 손가락으로 눌러보고 체감해야 아는 것들이 있다"고 썼는데, 오늘 그 말이 훨씬 더 무겁게 확인됐다. **시안 두 개를 비교한 것과, 실제 게임을 처음부터 끝까지 플레이해본 것은 다른 층위의 검증**이었다.

### 왜 지금까지는 안 보였을까

18일차부터 만든 mock 데이터 16개는 **각 화면의 "정지 스냅샷"**이었다. 스크롤이 어떻게 움직이는지, 새 메시지가 왔을 때 화면이 어떻게 반응하는지는 **정지된 mock으로는 검증되지 않는** 영역이다. `tsc`도 통과하고 `vite build`도 성공하고 Playwright 콘솔 에러도 0건이었는데, 이런 문제는 **자동화된 검증이 못 잡는 층**에 있었다.

18~19일차에 배운 스킬·훅, 26·31일차의 시험 병합·빌드 검증 — 전부 **"코드가 맞는지"**를 확인하는 도구였다. 오늘 나온 피드백은 **"경험이 맞는지"**를 확인하는 건 다른 방법(실제 플레이)이 필요하다는 걸 보여줬다.

## 3. 다음에 할 것

**우선순위 1 — 스크롤/팝업 (가장 많이 나온 불만)**
- 팝업을 `position: fixed`로 바꿔 스크롤에 안 따라가는 게 아니라 **뷰포트에 고정**
- 새 메시지 도착 시 자동 스크롤 로직 재검토 — 사용자가 위쪽을 보고 있으면 강제 스크롤하지 않기
- 페이지 전체가 아니라 **채팅 로그 컨테이너 안에서만** 스크롤되도록 구조 수정

**우선순위 2 — 토큰 재확인**
- 실제 렌더 화면에서 D의 최신 지침이 반영됐는지 하나씩 대조
- 리터럴 값이 남아있는 컴포넌트 색출

**우선순위 3 — 봇 투표 신뢰성**
- 클릭 시 하이라이트 추가
- 익명투표 안내문 제거 (실명 후보 목록으로 수정)
- 모바일 전용 레이아웃 재검토

**우선순위 4 — 가독성**
- describe-debate 사이 구분선 추가 (스터디 시스템 때 배운 "구분선 = 경계 신호" 패턴 재사용)
