웹개발 수업 35일차. 4주차 React 코드리뷰는 버튼을 세 번 눌러도 화면 숫자가 0에 멈춰 있는 코드였다. 팀 프로젝트 Zeteo는 내일이 중간발표라, 오늘 회의에서 게임 진행 순서를 네 구간으로 쪼개 발표자를 나눴다. 내가 맡은 건 최후변론부터 정체 공개까지, 서버가 결과를 정하는 구간이다.

## 1. 코드리뷰 ⑫: 콘솔은 올라가는데 화면은 0이다

버튼을 누를 때마다 숫자가 1씩 올라가게 만든 코드. 실행 전에 예상부터 적고 시작했다.

```jsx
const App = () => {
  let count = 0;                       // 화면에 보여 줄 숫자, 그냥 변수다

  const click = () => {
    count++;                           // 값을 1 올린다
    console.log('변수 값:', count);     // 콘솔로 값을 확인해 본다
  };

  return <button onClick={click}>클릭 {count}</button>;
};

export default App;
```

기대: 버튼을 세 번 누르면 콘솔에 1, 2, 3이 찍히고 화면도 `클릭 3`으로 같이 바뀐다.

실제: 콘솔은 정확히 1, 2, 3이 찍힌다. 그런데 화면의 버튼은 세 번을 눌러도 `클릭 0`에 그대로 멈춰 있다.

### Q1. 콘솔의 숫자와 화면의 숫자가 같을까

같지 않다. 콘솔은 정상적으로 올라가고 화면만 안 움직인다. 값이 안 바뀐 게 아니라, 바뀐 값이 화면에 반영되지 않은 것이다.

### Q2. 왜 그럴까

원인은 첫 줄이다.

```jsx
let count = 0;  // 이 줄이 원인
```

React가 화면을 다시 그리는 조건은 두 가지뿐이다. state가 바뀌거나 props가 바뀌거나. 컴포넌트 함수 안의 아무 변수나 값이 바뀐다고 알아서 다시 그려주지 않는다.

`count`는 `let`으로 선언한 평범한 지역 변수다. React 입장에서는 이런 변수가 있는지도 모르고 감시하고 있지도 않다. `count++`는 자바스크립트 레벨에서 분명히 실행되고 값도 바뀌니까 `console.log`는 정확한 값을 찍는다. 문제는 그 변경을 React에게 알리는 절차가 코드 어디에도 없다는 것이다. 컴포넌트 함수가 다시 실행되지 않으니, 화면에는 처음 렌더링될 때의 `count = 0`이 계속 남아 있다.

### 수정: React가 추적하는 값으로 만든다

```jsx
import { useState } from 'react';

const App = () => {
  const [count, setCount] = useState(0);  // state로 선언

  const click = () => {
    setCount(count + 1);                  // setter를 호출해야 리렌더가 예약된다
    console.log('변수 값:', count + 1);
  };

  return <button onClick={click}>클릭 {count}</button>;
};

export default App;
```

`setCount`를 호출하는 순간 React는 state가 바뀐 걸 인식하고 컴포넌트 함수를 처음부터 다시 실행한다. 새 `count` 값으로 화면이 갱신된다.

| | `let count = 0` | `useState(0)` |
|---|---|---|
| 값 변경 | JS 레벨에서는 됨 | React가 관리하는 저장소에 새 값 저장 |
| React가 감지 | 전혀 모름 | 변경을 감지하고 리렌더 예약 |
| 화면 갱신 | 안 됨 | 됨 |
| 리렌더 후 값 | 다시 0으로 초기화 | 유지됨 |

### 30일차부터 이어지던 축이 오늘 한 칸 옮겨갔다

30일차부터 33일차까지 나흘은 전부 "자바스크립트의 기본 동작을 잘못 알고 있었다"는 사고였다. `+`가 문자열이면 연결로 돌변하고, `replace()`는 원본을 안 바꾸고, `sort()`의 기본이 문자열 비교고, `const`가 내부 변경은 못 막는다는 것들.

오늘은 자바스크립트가 틀린 게 없다. `count++`는 완벽하게 동작했다. 틀린 건 "값이 바뀌면 화면도 바뀐다"는 쪽이었다. React를 쓰기 시작하면 의심해야 할 대상이 언어의 동작에서 프레임워크의 판단 기준으로 옮겨간다는 게 오늘의 소득이다. 값이 바뀌었느냐가 아니라, 그 사실을 React가 알고 있느냐가 기준이다.

## 2. 팀 프로젝트: 중간발표 전날 회의

내일이 Zeteo 중간발표다. 오늘 회의의 핵심은 발표를 어떻게 나눌 것인가였고, 결론은 개발 파트가 아니라 게임 진행 순서로 자르는 것이었다.

| 구간 | 범위 | 발표 | 내용 |
|---|---|---|---|
| ① | 입장 ~ 역할 배정 | 유민성 | 랜딩·대기실 화면, 방 생성, 준비완료, 라벨 배정 |
| ② | 묘사 ~ 토론 | 박진 | 발언이 오가는 구간. 봇이 말하는 유일한 구간 |
| ③ | 최후변론 ~ 정체 공개 | 이현우 | 지목, 생사 투표, 판정. 서버가 결과를 정하는 구간 |
| ④ | 제시어 추측 ~ 결과 ~ 설문 | 김정현 | 게임 종료, 정체 공개, DB 적재 |

이 분할의 성격이 지난주와 정확히 맞물린다. 34일차에 완성한 분기형 코드북의 질문이 "코드를 만든 사람이 아니어도 설명할 수 있는가"였는데, 게임 흐름으로 자르면 한 사람의 구간이 자기 파트 밖으로 반드시 삐져나간다. 내 구간만 해도 화면은 내 파트지만 판정 로직은 서버 쪽 파일이다. 발표를 준비하려면 남의 코드를 읽는 수밖에 없었다.

### 내 구간 정리: 화면은 선택만 올리고, 결과는 서버가 정한다

`MainScreen.tsx`, `LifeVote.tsx`, `Reveal.tsx`를 한쪽에 두고 `stateMachine.ts`, `vote.ts`, `index.ts`를 반대쪽에 두고 읽었다. 한 문장으로 줄이면, 화면은 "누굴 죽일까"라는 사람의 선택을 받아 서버로 올려보내기만 하고 결국 어떻게 되는가는 전부 `stateMachine.ts`가 정한다.

읽으면서 새로 알게 된 게 여섯 가지였다.

첫째, 이 구간은 항상 실행되지 않는다. 토론 투표에서 아무도 지목되지 않으면 라이어 승리가 예약되고 구간이 통째로 생략된다. 발표에서 "이 구간이 항상 있는 건 아니다"를 먼저 짚기로 했다.

둘째, 최후변론 페이즈의 전이 함수는 한 줄이다.

```ts
finalDefense: () => 'lifeVote'
```

조건도 계산도 없다. 60초가 지나면 그냥 넘어간다. 이름이 무겁지만 판정에는 아무 값도 만들어내지 않는, 순수하게 발언 기회를 주는 시간이었다.

셋째, "살린다"에는 횟수 제한이 없다. 살리기로 결정되면 `accusedId`, `votes`, `lifeVotes`가 전부 초기화되고 `round`만 올라간 채 토론으로 되돌아간다. 이론상 지목과 최후변론과 생사투표가 무한히 반복될 수 있다.

넷째, 조기 확정 로직이 있다. 남은 사람이 전부 한쪽에 몰아줘도 결과가 안 뒤집히면 미리 확정한다.

```ts

return kill > spare + remaining || spare >= kill + remaining;
```

그런데 확정돼도 바로 넘어가지 않고 `setPhaseTimer(room, 3000, ...)`으로 3초를 더 기다린다. 이미 진 투표라도 화면이 뚝 끊기지 않게 하려는 의도로 읽었다.

다섯째, 타이밍 트릭 하나. 처형이 확정되면 `revealedRole`을 reveal 페이즈에 들어갈 때(정확히는 lifeVote를 나가는 시점에) 미리 채워둔다. 나갈 때 채우면 정체 공개 화면이 뜨고도 첫 몇 초는 역할이 안 보이는 버그가 났다는 기록이 코드 주석에 남아 있었다. phase가 바뀌는 순간은 그 phase가 필요로 하는 값이 이미 채워져 있어야 하는 순간이라는 원칙이 코드에 그대로 박혀 있는 지점이다.

### 회의에서 받은 질문 두 개

내 자료에 "메시지 객체를 통째로 넘기면 최적화가 무효가 된다"는 문장이 있는데, 여기서 질문이 나왔다.

배경은 이렇다. 실제 폰에서 채팅 입력이 점점 느려지는 버그가 있었고, 원인은 채팅 로그가 서버 브로드캐스트마다(누가 투표하든, 봇이 말하든, 페이즈가 넘어가든) 전체 메시지를 통째로 다시 그리던 것이었다. 메시지 한 줄을 컴포넌트로 빼서 `React.memo`로 감쌌는데, 여기서 한 번 더 걸렸다. `memo`의 비교는 기본적으로 `===`이고, 객체의 `===`는 내용이 같은가가 아니라 같은 물건인가를 본다.

```js
{ text: '안녕' } === { text: '안녕' }   // false
'안녕' === '안녕'                       // true
```

소켓 데이터는 서버에서 JSON 문자열로 직렬화됐다가 브라우저에서 `JSON.parse`로 복원된다. 내용이 같아도 매번 완전히 새 객체다. 그래서 원시값으로 풀어 넘기는 방향으로 갔다.

첫 번째 질문은 `ChatLog` 자체는 여전히 브로드캐스트마다 다시 실행되는데 무시할 만한 수준이냐는 것이었다. 맞다, 다시 실행된다. `memo`는 "나를 부르지 마"가 아니라 "내 아래는 건드리지 마"라서 구조상 피할 수 없다. `memo(ChatLog)`로 한 겹 더 감싸도 modal은 JSX라 호출마다 새 객체고 messages와 players도 소켓 파싱이라 매번 새 배열이라, 얕은 비교에서 항상 다르다가 나온다. 지금 게임 길이 기준 실측으로 브로드캐스트 1회당 0.05ms 이하라 그대로 두기로 했다.

두 번째는 웹에서 안 보이던 모바일 지연이 파트 C 코드에서 재발할 위험이 없냐는 것이었다. 게임 길이에 비례해 커지는 배열이 messages 하나뿐이고 거긴 이미 고쳐져 있어서 지금은 재발 지점이 없다. 다만 이 수정이 주석으로만 지켜지고 있어서(린트도 테스트도 없다), 나중에 채팅에 반응이나 답장 같은 필드가 추가될 때 그걸 객체째로 넘기면 같은 문제가 다시 생길 수 있다고 답했다.

두 질문 다 오늘 코드리뷰와 같은 자리를 가리키고 있었다. 코드리뷰는 React가 안 그려주는 쪽이었고, 이건 React가 필요 없는데도 그리는 쪽이다.
