웹개발 수업 27일차. 코드리뷰는 **중앙 정렬의 두 방법 비교**. 화면 결과가 같아도 유지보수성은 다르다. 팀 프로젝트 Zeteo는 Day 2 아침, 어제 "사고"라고 단정했던 파일 삭제가 사실은 **의도된 것이었다**는 반전을 만났다. 오늘의 진짜 배움은 여기서 나왔다.

## 1. 코드리뷰 ⑥ · absolute+transform vs flexbox, 결과가 같아도

`.box`를 `.wrap` 한가운데 놓는 두 코드. **렌더링 결과는 완전히 동일**하다.

```css
/* A */
.wrap { position: relative; }
.box  { position: absolute; top: 50%; left: 50%; transform: translate(-50%, -50%); }

/* B */
.wrap { display: flex; justify-content: center; align-items: center; }
```

**Q1. 유지보수·견고성 면에서 어느 쪽? → B(flexbox)**

### Q2. 왜? · 화면이 같아도 "미래"가 다르다

**① 문서 흐름 처리가 다르다.** A는 `.box`를 `position: absolute`로 **문서 흐름에서 완전히 빼낸다.** 형제 요소가 하나라도 추가되면, 그 형제는 `.box`가 없는 것처럼 배치돼 겹칠 수 있다. B는 `.box`가 여전히 flex item으로 흐름 안에 있어서, 형제가 늘어나도 컨테이너가 알아서 배치한다.

**② 코드가 의도를 드러내는 정도가 다르다.** A는 `top: 50%; left: 50%; transform: translate(-50%, -50%)`라는 **수치 트릭의 조합**이다. 처음 보는 사람은 "왜 -50%인가"를 계산해봐야 의도(중앙 정렬)를 안다. B는 `justify-content: center`로 **의도가 코드 자체에 쓰여 있다.**

**③ 확장 시나리오에서 견고성이 다르다.**

| 상황 | A (absolute) | B (flex) |
|---|---|---|
| 형제 요소 추가 | 겹침 발생 가능 | 자동으로 배치 |
| 정렬 기준 변경 | `top`/`left`/`transform` 재계산 | 속성값만 교체 |
| 자식 간격 조정 | 개별 좌표 계산 | `gap` 한 줄 |

**지금은 자식이 하나뿐이라 안 보이지만, 늘어나는 순간 A는 깨지고 B는 자연스럽게 대응한다.**

### 그런데 A가 나은 경우도 있다 · 정답은 상황에 달렸다

공정하게 짚어야 할 게 있었다. A(absolute+transform)가 유리한 경우:

- 오버레이·뱃지·모달처럼 **의도적으로 다른 요소 위에 겹쳐야** 할 때
- `.wrap`이 이미 grid나 다른 flex 방향으로 쓰이고 있어 새로 flex를 걸 수 없을 때
- `transform`은 GPU 가속되어 reflow 없이 처리되니, **이 요소만 애니메이션**시킬 계획이면 성능 이점

25일차에 배운 "transform은 합성 단계만 거쳐 가볍다"는 지식이 오늘 정답의 예외 조건으로 다시 나왔다. **"항상 B가 정답"이 아니라 "일반적인 중앙 정렬 상황에서는 B"**라는 걸 놓치면 안 된다.

## 2. 팀 프로젝트 · Zeteo Day 2, "사고"가 아니었다

Day 1에 `apps/frontend` 27개 파일이 사라진 걸 어제 **사고(R8)**라고 판단했다. 오늘 아침 상황이 갱신됐다.

### 반전 · 관리자가 의도한 정리였다

> R8은 **관리자가 백엔드 정리를 위해 의도한 삭제**였다. 내가 처음에 "사고"로 단정한 건 틀렸다.

`feat/server` 브랜치는 이제 백엔드 전용으로 정리됐고, 그 과정에서 프론트엔드 폴더를 지운 것이었다. 어제 "27개 파일이 조용히 사라졌다"고 경보를 울렸던 게, 알고 보니 **상대방 입장에선 정상 작업**이었다.

### 그런데도 문제가 완전히 사라진 건 아니었다

여기서 오늘 배운 게 진짜 핵심이다:

> **의도가 결과를 바꾸지는 않는다.** 로컬 정리 목적이었다는 건 커밋에 안 담기고, merge-base에 파일이 있는 이상 git은 "삭제한 브랜치"로 읽어 **병합에 전파한다.**

내 실수 판단은 틀렸지만, **경보 자체는 여전히 유효했다.** 관리자가 지운 게 맞고 의도도 맞지만, 그 브랜치를 병합하면 내 쪽 27개 파일도 똑같이 사라진다는 사실은 변하지 않는다. "의도됨"과 "안전함"은 다른 질문이었다.

### 말하는 방식을 바꿨다

> **→ "이건 실수 같은데요"가 아니라 "의도는 알겠는데 병합하면 이렇게 됩니다"로 말한다.**
> 전자는 상대를 방어적으로 만들고, 후자는 같이 볼 사실을 준다.

"사고"라고 부르는 순간 상대는 방어부터 하게 된다. 반면 **"의도는 이해했고, 그 다음에 이런 일이 생긴다"**는 같은 사실을 두고 같이 판단하자는 말이 된다. 25일차 코드리뷰(A/B 둘 다 존재 이유가 있다)와 같은 태도다: **틀림을 지적하는 게 아니라 결과를 같이 보는 것.**

**해결책도 하나 배웠다.** 목적이 "내 작업 폴더에서 안 보이게"였다면 `git sparse-checkout`이 **저장소 자체는 안 건드리고** 같은 효과를 낸다. 파일을 지우지 않고도 로컬에서 안 보이게 하는 방법이 있었다.

### 진행 상황 · 안전망이 실제로 작동했다

병합 관련 사고 3건의 어제-오늘 비교:

| 사건 | 어제 판단 | 오늘 상태 |
|---|---|---|
| **R5** (봇 코드 275줄 소실) | 사고, 구두 전달 | **재확인 필요**: `feat/server`에 새 파일(`bot/scheduler.ts` 등)이 생겨 구조가 바뀌었을 수 있음 |
| **R8** (frontend 27개 삭제) | 사고 | **의도된 정리로 정정.** 단, 병합 시 전파 문제는 미해결 |
| **R9** (신규, `view.ts`의 `reasons` 누락) | - | 관리자께 전달함, 다음 확인 대기 |

`feat/game-ui`는 오늘 아침 `dev`와 무사히 병합됐다: **충돌 0건**, `packages/shared-types` 24줄 추가만 반영됐고, `apps/frontend`는 dev가 손대지 않은 덕에 내 작업이 전부 보존됐다. 어제 만든 시험 병합 절차가 오늘 진짜 병합에서 안전하게 통과된 것.

### PR 코멘트도 "사실 나열" 방식으로

병합 결과를 알리는 코멘트 초안을 준비했는데, 판단이나 감상 없이 **사실만 나열**했다:

```
- 3a51aa6: 계약 확정 반영 — PublicPlayer.label 대응 8개 파일, mock에 S6/S7 필드 추가
- 659e624: origin/dev 병합, 충돌 0건 (packages/shared-types 24줄 추가만 반영)
- npm run build -w frontend: 0 오류
```

"의도는 알겠는데 결과는 이렇습니다"로 말하는 방식이, 코멘트 작성에도 그대로 적용됐다. **누가 봐도 같은 결론에 이르는 문장.**

### 이번 사이클의 배운 것 · 리스트가 자라고 있다

인수인계 문서의 "배운 것" 절이 어제보다 늘었다:

- **삭제는 충돌로 안 뜬다** (어제와 동일, 재확인)
- **의도된 것과 잘못된 것을 구분한다. 다만 결과는 따로 본다** (오늘 신규, 이 글의 핵심)
- **통합 누락은 조용히 일어난다** → "작업분을 넘길 땐 파일이 아니라 브랜치로"
- **dev만 보면 팀 상태를 오판한다.** 반나절이면 낡는다
- **원격만 봐서는 남의 로컬 작업을 못 본다** → "없습니다" 대신 "원격 기준으론 안 보입니다"
- **남의 소유 파일에서 확정 전 이름을 따라가지 않는다** → *"위험을 인지했으면 그 위험이 해소될 때까지 기다린다"*

마지막 항목이 뼈아팠다. 토큰 이름을 D의 초안에 맞췄다가 되돌린 그 사건에서, **당시 스스로 "헛돌 위험이 있다"고 경고까지 해놓고 진행한 게 문제**였다고 적혀 있다. 위험을 인지하는 것과 위험을 감수하지 않는 것은 다른 일이었다.
