웹개발 수업 25일차. 오전 코드리뷰는 **CSS 애니메이션 성능**: 결과가 똑같은 코드 두 개 중 어느 쪽이 가벼운가. 오후부터는 팀 프로젝트 주제가 확정돼 본격 착수했다. 프로젝트명은 **Zeteo**, 나는 **파트 C(게임 화면)** 담당이다.

## 1. 코드리뷰 ④: 애니메이션은 "무엇을 바꾸느냐"로 갈린다

화면 결과가 **완전히 동일한** 두 코드가 주어졌다.

```css
/* 공통 */
.box {
  position: relative;
  left: 0;
  width: 200px;
  height: 100px;
  transform-origin: left center;
  transition: all 0.3s;
}

/* A */
.box:hover { left: 30px; width: 300px; }

/* B */
.box:hover { transform: translateX(30px) scaleX(1.5); }
```

**Q1. 어느 쪽이 가벼울까? → B(transform)**

### Q2. 왜? (브라우저 렌더링 3단계)

브라우저가 화면을 그리는 과정은 크게 셋이다:

1. **레이아웃(Layout / Reflow)**: 요소의 위치·크기 계산
2. **페인트(Paint)**: 픽셀을 실제로 그림
3. **합성(Composite)**: 그려진 레이어들을 합침

**어떤 속성을 바꾸느냐에 따라 이 파이프라인의 어디서부터 다시 계산할지가 달라진다.**

| | A (`left`, `width`) | B (`transform`) |
|---|---|---|
| 성격 | 문서 **레이아웃에 직접 영향** | 레이아웃에 영향 **없음** |
| 다시 하는 일 | Reflow → Repaint → Composite **전부** | **Composite만** |
| 범위 | 해당 요소 + **주변 요소까지** 재계산 | 이미 그려진 레이어를 GPU가 이동·확대 |

`transition: all 0.3s`니까 A는 0.3초 동안 **매 프레임마다 이 전체 파이프라인이 반복**된다. B는 레이아웃·페인트를 건너뛰고 대부분 GPU 가속을 받는다.

> `opacity`도 같은 이유로 가벼운 속성이다. 그래서 실무에서 **`left`/`top`/`width`/`height` 대신 `transform`을, `visibility` 대신 `opacity`를** 쓰라고 권장한다.

### 4일차에 쓴 코드의 이유를 이제야 알았다

4일차에 hover 회전·확대, 카드 3D 뒤집기를 만들면서 `transform: rotate() scale()`을 썼다. 그땐 "모양을 바꾸는 속성"이라고만 배웠는데, **왜 하필 transform이었는지**의 답이 오늘 나왔다. 같은 결과를 `left`/`width`로 만들 수도 있었지만 그건 매 프레임 레이아웃을 다시 계산하는 코드였을 것이다.

**"결과가 같은 코드가 여러 개일 때, 무엇을 기준으로 고를 것인가."** 코드리뷰 4연작이 매번 다른 기준을 하나씩 알려주고 있다: 접근성(21), 전송(22), 동작(23), 그리고 오늘은 **성능**.

## 2. 팀 프로젝트 착수: Zeteo

### 주제 확정

후보 6개를 놓고 고민하다 결국 **봇 게임** 방향으로 결정됐다. 22일차에 기획했던 봇 마피아가 **라이어 게임**으로 형태를 바꿔 확정됐다.

> **Zeteo**: 라이어 게임 안에 봇 1명을 섞어두고, 게임이 끝나면 *"이 중 누가 사람이 아니었나"*를 지목하는 웹 게임.

| 항목 | 값 |
|---|---|
| 착수 / 1차 MVP / 완성 | 8/3 → 8/9 → 8/23 |
| 인원 구성 | 5인 게임 = **사람 4 + 봇 1** |
| 스택 | TypeScript · React + Vite · Node + Express + raw `ws` · 서버메모리→SQLite · LLM API |
| 파트 | A 서버 / B 봇 / **C 게임 화면(나)** / D 공통·랜딩·결과 |

22일차 기획서의 "봇은 두 정체를 동시에 숨긴다"는 핵심 설계가 그대로 살아있다.

### 내 파트 한 줄 정의

> **서버가 내려준 `GameState` 하나를 받아, 지금 무엇을 보여주고 무엇을 잠글지 결정해 그린다.**

이 한 줄을 정하고 나니 **하지 않을 것**이 명확해졌다:

- 게임 로직 판단(승패·과반·다음 페이즈) → 서버 담당
- 카운트다운 계산 소유 → 서버가 `deadlineAt`(절대 시각)만 준다
- 증분 상태 관리 → 상태는 바뀔 때마다 **전체가** 온다. **"받으면 다시 그린다"**

마지막 원칙이 React를 배운 이유 그 자체다. 9일차에 *"데이터만 바꾸면 화면은 React가 알아서"*를 배웠는데, 서버-클라이언트 관계에도 같은 구조를 적용한 것.

### 오늘의 산출물: mock 16개

담당은 화면 6개(S0 역할공개 → S1 묘사 → S2 토론 → S3 최후변론 → S4 생사투표 → S5 공개)와 공통 컴포넌트 4개(Chat·VotePanel·PlayerList·Timer).

**서버 없이 화면부터 만들 수 있게** mock 상태 16개를 준비했다.

```bash
npm run dev
# /                              → mock 16개 목록
# /?mock=debate-round2-spared    → 해당 화면 직행
```

- `tsc --noEmit`(strict) 통과, `vite build` 성공
- **mock 16개 전부 렌더 확인, 콘솔 에러 0건** (Playwright 자동 검증)

8일차 미니프로젝트 때 "작게 시작해서 하나씩"을 배웠는데, 팀 작업에선 **"남을 기다리지 않고 시작할 수 있는 형태로 잘라두는 것"**이 그 역할을 한다.

### 오늘 가장 중요했던 일: 계약 구멍 6개 발견 ★

`shared/types.ts`(서버↔클라이언트가 주고받는 데이터 형식)를 보다가 **화면을 그릴 수 없는 지점 6개**를 찾았다. 이게 오늘의 핵심 작업이었다.

| ★ | 없던 것 | 왜 화면이 못 그리나 |
|---|---|---|
| **★1** | `myId` | **클라이언트가 자기 id를 알 방법이 계약에 아예 없었다.** "지금 내 차례인가"(입력 잠금), "지목당한 게 나인가"(화면 분기)를 판단할 수 없음 |
| ★2 | `round` | 재투표·복귀 시 페이즈가 그대로라 화면이 몇 라운드인지 모름 |
| ★3 | `myLifeVote` | 기존 `myVote`는 지목용(문자열)이라 kill/spare를 담을 자리가 없음 |
| ★4 | `lifeVoteCounts` | 기존 `voteCounts`는 플레이어별 득표라 두 값(죽인다/살린다)이 안 들어감 |
| ★5 | `revealedRole` | "○○님은 시민이었습니다"를 그릴 근거가 없음 |
| ★6 | `speakerId: 'system'` | 시스템 안내가 참가자 목록에서 이름 매칭 실패 |

특히 ★1이 뼈아프다. **자기 id를 모르면 거의 모든 화면이 분기를 못 한다.** 서버 담당자도 "기획서 초안의 실수"로 인정했고, 오늘 회의에서 확정 처리하기로 했다.

**언제 발견했는지가 중요했다.** 작업계획서 리스크 표에 이렇게 적어뒀는데:

> 계약 구멍이 Day 3 통합에서야 발견 → **Day 0 오전에 전부 제기.** 통합 후 발견하면 화면 재작업.

mock 데이터에 `: GameState` 타입을 붙여둔 덕에 **컴파일러가 빈 자리를 먼저 알려줬다.** TypeScript를 쓰는 이유를 첫날에 체감한 셈이다.

### 필드를 추가하지 **않기로** 한 결정 (★7 폐기)

*"동점 재투표와 '살린다' 복귀를 화면에서 구분할 건가?"*라는 질문이 왔다. `returnReason: 'tie' | 'spared'` 같은 필드를 만들 수도 있었지만 **필요 없다**고 결론 냈다.

1. 필드로 만들면 화면이 그걸 문구로 번역해야 해서 **카피가 프론트에 하드코딩된다.** 시스템 메시지는 서버가 문장까지 만들어 보내니 한 곳에서 관리된다
2. *"○○님이 살아남았습니다"*처럼 **이름이 들어간 문장은 필드로 표현 불가**

실물 렌더로 검증해보니 더 확실했다. '살린다' 쪽은 최후 변론 단계를 거쳐왔기 때문에 **로그의 모양 자체가 다르다.** 구분선 사이에 변론 발언이 들어간다.

**"필드를 추가하는 것"만이 해결이 아니라는 것.** 이미 있는 것(시스템 메시지)으로 되면 계약을 늘리지 않는 게 낫다.

### 병렬 작업을 가능하게 한 두 가지 설계

**⑴ CSS 변수 fallback으로 D를 기다리지 않기**

디자인 토큰은 D 담당인데, 아직 안 나왔다. 그래서 내 CSS는 이렇게 썼다:

```css
color: var(--color-text, #eaeaea);
```

토큰이 없어도 **fallback 값으로 일단 렌더된다.** 나중에 토큰이 나오면 fallback만 지우면 끝이다. **되돌릴 코드가 없다.** 5일차에 배운 CSS 변수가 여기선 "의존성 없이 병렬 작업하는 장치"가 됐다.

**⑵ 단일 진입점으로 충돌 줄이기**

화면 6개를 `GameScreen.tsx` 하나로 감쌌다. D는 `App.tsx`에서 **이것 하나만 마운트**하면 되고, 내 화면 6개를 몰라도 된다. 공유 폴더 충돌도 줄어든다.

21일차 시니어 프로젝트 기획 때 *"B가 JSON 스키마를 정하면 C는 속성만 심으면 된다"*는 인터페이스 설계를 봤는데, 이번엔 그걸 직접 하고 있다. **팀 작업의 핵심은 코드가 아니라 경계선을 긋는 일**인 것 같다.

### 남은 구멍: 룰북에 없는 화면

작업 중에 룰북의 빈 구멍도 하나 찾았다. **제시어 추측 "결과" 화면이 없다.**

- 라이어가 아니었을 때 → 판정 결과까지 보여줌
- 라이어였을 때 → **입력 화면에서 끝남.** 맞혔을 때/틀렸을 때 화면이 없음

규칙엔 *"추측 성공 → 라이어 승 / 실패 → 시민 승"*이 있는데 **대응 페이즈 자체가 없다.** 결과는 마지막 화면에서 나오지만 그 사이에 봇 지목이 통째로 끼어서, 라이어 게임이 끝났다는 감각 없이 봇 지목을 하게 된다.

제안은 **기존 공개 페이즈를 한 번 더 거치게** 하는 쪽으로 냈다. 타입 변경 없이 서버 상태머신 전이 하나만 추가하면 되니까. (답변 대기 중)
