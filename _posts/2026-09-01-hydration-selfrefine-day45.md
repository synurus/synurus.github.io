웹개발 수업 45일차. 코드리뷰는 Hydration이었다. 40일차 SPA, 41일차 CSR, 42일차 SSR, 44일차 SSG에 이어 다섯 번째 개념 문제인데, 앞의 넷이 "HTML을 언제 만드느냐"를 나눈 것이었다면 오늘은 그렇게 만들어진 HTML을 언제 동작시키느냐다. 오후에는 최종발표 자료에서 핵심 코드 리뷰 파트를 통째로 갈아 끼웠다. 44일차에 임시로 넣어뒀던 중간발표 내용을 버리고 봇 자가개선 루프로 다시 채웠다.

## 1. 코드리뷰 ⑱: Hydration, 껍데기에 동작을 붙이는 일

Hydration은 서버에서 미리 그려 보낸 HTML에 클라이언트에서 JavaScript를 붙여 동작하는 페이지로 만드는 과정이다. 마른 스펀지에 물을 붓는다는 뜻의 이름이다.

SSR이나 SSG로 내려온 HTML은 화면은 보이지만 아무 동작도 하지 않는다. 버튼을 눌러도 반응이 없고 상태도 없다. 42일차 SSR 글에서 이걸 "보인다와 눌린다는 다르다"로 한 줄 적어뒀는데, 오늘 그 한 줄이 문제로 나왔다.

동작 순서는 이렇다. 서버가 완성된 HTML 문자열을 응답하고, 브라우저가 즉시 그려 사용자가 화면을 보고, JS 번들이 도착해 실행되면 React가 같은 컴포넌트 트리를 다시 렌더링해 기존 DOM과 대조한다. 그리고 DOM을 새로 만들지 않고 재사용하면서 이벤트 핸들러와 상태만 연결한다.

```jsx
// 서버
renderToString(<App />)         // HTML 문자열 생성

// 클라이언트
hydrateRoot(container, <App />) // 있는 DOM에 붙이기
createRoot(container).render()  // DOM을 새로 만들기
```

`createRoot`와 `hydrateRoot`의 차이가 여기 다 들어 있다. 하나는 만들고 하나는 붙인다.

### 어긋나면 버리고 다시 그린다

오늘 제일 크게 남은 건 Hydration Mismatch다. 서버가 만든 HTML과 클라이언트의 첫 렌더 결과가 다르면 React가 경고를 내고 그 부분을 버린 뒤 다시 그린다. 화면이 깜빡이고, 미리 만들어 둔 이득이 사라진다.

| 원인 | 예시 |
|---|---|
| 매 렌더마다 값이 바뀜 | `new Date()`, `Math.random()` |
| 브라우저 전용 API | `window`, `localStorage` |
| 서버와 클라이언트의 환경 차이 | 타임존, 로케일 포맷팅 |
| 잘못된 HTML 중첩 | `<p>` 안의 `<div>`, 브라우저가 자동 교정하면서 구조가 틀어진다 |

해결은 클라이언트 전용 값을 `useEffect`에서 세팅하거나 그 부분만 마운트 후에 렌더하는 것이다.

```jsx
const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);
return mounted ? <ClientOnlyStuff /> : null;
```

Zeteo에는 hydration 단계가 없다. Vite로 빌드한 CSR이라 `createRoot`로 빈 `<div id="root"></div>`에 처음부터 그린다. 44일차에 SSG 실사례로 든 이 블로그도 마찬가지로 hydration이 없는데 이유는 정반대다. Jekyll이 만든 HTML에는 나중에 붙일 동작이 애초에 없어서 물을 부을 필요가 없다. 한쪽은 붙일 껍데기가 없고 다른 한쪽은 붙일 물이 없다.

그래서 넷을 정리하던 표에 hydration을 한 행으로 넣을 수는 없었다. 이건 방식이 아니라 방식들 사이의 이음새다. 미리 만들어 두는 쪽(SSR, SSG)과 그 자리에서 그리는 쪽(CSR)을 하나의 화면에서 이어 붙이려는 순간에만 생기고, 어느 한쪽만 쓰면 아예 등장하지 않는다.

## 2. 발표 자료도 같은 지점에서 어긋나 있었다

44일차에 18장짜리 골격을 세우면서 핵심 코드 리뷰 자리에 중간발표 때 쓴 "여덟 개의 화면을 하나의 페이지에"를 임시로 넣어뒀다. 오늘 처음부터 대사를 붙여가며 넘겨보니 그 자리가 어긋나 있었다. 앞뒤 장표는 이 프로젝트가 봇을 관찰하기 위한 게임이라고 말하는데 정작 몸통에서는 화면 합치기를 설명하고 있었다.

그래서 그 부분만 버리고 다시 그렸다. 44일차에 짜둔 네 단계 틀(맥락, 대안, 선택과 근거, 효과)은 주제와 무관한 뼈대라 그대로 두고 내용만 갈아 끼웠다.

### 맥락: 한 판이 남기는 것

자가개선을 하려면 재료가 있어야 하는데, 그 재료를 게임이 스스로 만든다. 한 판이 끝나면 네 개의 표에 기록이 남는다.

| 표 | 남는 것 |
|---|---|
| games | 게임 결과, 적발한 사람 수 |
| game_messages | 발언 전량. 누가 언제 무엇을 |
| game_votes | 투표 전량. 라이어 지목과 봇 지목 |
| survey_responses | 어느 발언이 왜 봇 같았나 |

가장 중요한 건 마지막 표의 한 칸이다. `survey_responses.picked_message_runtime_id`가 `game_messages.runtime_id`와 이어져서, 설문 응답자가 고른 "이 발언이 봇 같았다"가 실제 발언 한 줄로 정확히 찍힌다. 사람이 어디서 걸렸는지를 직접 남긴 좌표다.

### 대안: 셋을 검토했고 셋 다 뺐다

| 안 | 내용 | 기각 이유 |
|---|---|---|
| 관전자 LLM | 판마다 별도 모델이 발언을 채점해 적재한다 | 채점자를 검증할 수단이 없다 |
| 설문 자동 주입 | 응답을 봇 프롬프트에 그대로 반영한다 | 사람 검토 없이 프롬프트가 바뀐다 |
| 수동 회귀 | 로그를 직접 읽고 어색한 지점을 고친다 | 판당 발언 40여 개, 재현이 안 된다 |

가운데 안은 구현까지 갔다가 접었다. 셋의 문제가 결국 하나로 모인다. 나온 결과를 그냥 믿어야 한다는 것이다.

### 선택과 근거: 다섯 판이 쌓이면 여섯 단계가 돈다

개발 세션이 응답을 끝낼 때마다 Stop 훅이 아직 쓰지 않은 판이 다섯 개인지 확인한다. 아니면 조용히 끝나고, 차면 `/selfRefine`이 여섯 단계를 돈다.

1. 사례: 지목된 발언에서 실패 장면을 고정한다
2. 기준선: 고치기 전 상태를 반복 측정한다
3. 수정: 봇 지침을 고친다
4. 재측정: 같은 장면 같은 횟수로 다시 재어 전후를 비교한다
5. 다음 문항: 이번 수정을 겨냥한 설문 문항을 갱신한다
6. 올리기: 변경 내용과 수치와 근거를 묶어 PR로 올린다

사람이 하는 일은 마지막 승인 하나다. 앞의 세 대안이 전부 "결과를 믿어야 한다"에서 걸렸으니, 믿지 않고 재는 단계(기준선과 재측정)와 사람이 끊는 지점(승인)을 넣는 게 설계의 전부였다.

## 3. 첫 실행에서 나온 것

루프를 구현하고 실제로 한 바퀴 돌렸다. 봇의 행동 목록 일곱 개 중 하나에만 조건이 빠져 있었다.

```
전   자기 발언을 해명하세요.
후   당신을 의심한 사람이 있으면, 자기 발언을 해명하세요.
```

아무도 묻지 않았는데 변명하고 있었던 것이다. 나머지 여섯 줄에는 언제 하라는 조건이 다 붙어 있었고 그 한 줄만 없었다. 사람이라면 의심받지 않을 때 굳이 해명하지 않는데, 조건이 없으니 봇은 매 차례 그걸 후보로 들고 있었던 셈이다.

이게 오늘 코드리뷰와 겹친 지점이다. React는 서버가 그린 것과 클라이언트가 그린 것이 다르면 스스로 안다. 트리를 대조하면 되니까 기계가 판정할 수 있는 문제다. 그런데 봇의 발언이 사람 같은지 아닌지는 대조할 정답이 없다. 그래서 어긋난 자리를 사람이 찍어줘야 하고, 설문의 그 한 칸이 하는 일이 정확히 그거다. mismatch를 감지하는 주체가 프레임워크가 아니라 그 판에 있던 사람이라는 것만 다르다.

그리고 고친 내용을 겨냥한 설문 문항이 같이 갱신된다. 다음 판 참가자들이 그 자리에서 또 걸리는지를 대신 확인해 준다. 재측정을 다음 판에 위임하는 구조다.

## 4. 설계도, 부록, 그리고 다시 재야 하는 12분

44일차에 다음에 할 일로 적어둔 시스템 설계도 단순화도 오늘 다시 그렸다. 브라우저와 서버와 외부 API를 세 덩어리로 나누고 화면 여섯 개와 상태 한 개로 줄였다. 봇 모듈 안에서 루프가 실제로 고치는 파일 하나(`prompts.ts`)에만 표시를 남겼다. 30초에 읽히는 그림이 목표였는데 아직 완전히 만족스럽진 않아서 더 손볼지 고민 중이다.

부록 장도 하나 만들었다. 색 토큰 열 쌍, 타입 스케일 열 단계, 카드와 배지와 스탯 타일과 도식 조각을 한 장에 모아뒀다. 발표에서는 숨기고, 새 장표를 만들 때 여기서 도형을 복사해 쓴다. 오늘 코드 리뷰 파트 네 장을 새로 만들면서 앞 장표들과 여백과 글자 크기를 맞추느라 계속 되돌아가 확인했던 게 계기다. 두 번 겪고 나서야 조각을 모아둘 생각을 했다.

남은 문제는 시간이다. 44일차에 12분을 초 단위로 나눠 11분 35초짜리 배분을 만들어뒀는데, 오늘 몸통이 통째로 바뀌었으니 그 배분은 더 이상 유효하지 않다. 새로 쓴 네 장에는 아직 타임코드를 안 붙였고, 앞뒤 장의 누적 시각도 전부 밀렸다. 44일차에 코드 리뷰에 2분 50초를 배정했는데 네 단계를 실제로 말해보면 그 안에 들어가는지 아직 모른다.

미리 만들어 둔 것은 만든 순간부터 낡는다고 어제 적었는데, 하루 만에 그 재빌드가 왔다. 다만 통째로 다시 만든 게 아니라 어긋난 한 덩어리만 갈아 끼웠고, 뼈대와 나머지 장표는 그대로 재사용했다. 하필 오늘 배운 게 그 방식의 이름이었다.

## 5. 다음에 할 것

- 발표 타임코드 전면 재산정. 새 코드 리뷰 네 장에 초를 배정하고 뒤 장표의 누적 시각을 다시 계산
- 11분 35초를 실제로 소리 내어 재보기. 44일차부터 미뤄둔 일이고 이제는 내용이 확정됐으니 더 미룰 이유가 없다
- 시스템 설계도 추가 정리 여부 결정. 지금 그림으로 갈지 한 번 더 덜어낼지
- 히스토리 장의 파일 수와 커밋 수를 발표 직전에 재집계. 노트에 8월 19일 기준이라는 메모가 아직 남아 있다
- 시연 녹화본 촬영. 라이브가 막혔을 때 즉시 전환할 4분짜리 백업
- 루프를 한 바퀴 더 돌려보기. 다음 다섯 판이 쌓이면 갱신된 설문 문항이 실제로 작동하는지 확인할 수 있다

---

**오늘의 한 줄 정리:** Hydration은 미리 그려둔 것과 나중에 붙는 것이 어긋나면 그 부분을 버리고 다시 그린다. 오늘 발표 자료에서 어긋난 한 덩어리를 갈아 끼운 것도, 봇의 조건 빠진 지침 한 줄을 고친 것도 같은 모양이었는데, 어긋났다는 걸 React는 스스로 알고 봇은 그 판에 있던 사람이 찍어줘야 안다는 것만 달랐다.
