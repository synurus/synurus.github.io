웹개발 수업 28일차. 코드리뷰는 **z-index가 한쪽만 먹지 않는 이유**. 그리고 2주차 주간 과제 **"스터디 시스템"** 기획을 완료했다. "다른 기술을 배우려는 의지가 있는가"를 증명하는 시스템을, 회의록에서 기획서·시나리오·설계도까지 하루 만에 만들었다.

## 1. 코드리뷰 ⑦ · z-index가 안 먹는 이유

겹친 두 박스에서 `.a`를 앞으로 꺼내려고 `z-index`를 줬는데, **한쪽 코드만 동작한다.**

```css
.a { background: #cde; }
.b { background: #334; margin-top: -50px; margin-left: 50px; }  /* .a 위로 겹침 */

/* A */
.a { z-index: 10; }

/* B */
.a { position: relative; z-index: 10; }
```

HTML 순서상 `.b`가 `.a`보다 뒤에 오므로, 기본 상태(둘 다 `static`)에서는 `.b`가 나중에 그려져 위에 겹친다.

**Q1. 어느 쪽에서 `.a`가 앞으로 나올까? → B만**

### Q2. 왜? · z-index에는 입장 조건이 있다

**`z-index`는 `position`이 `static`이 아닌 요소에만 적용된다.** CSS 요소의 기본 `position` 값은 `static`인데, `z-index`는 `relative`·`absolute`·`fixed`·`sticky`처럼 **"포지셔닝된 요소"에서만** 쌓임 순서를 결정한다. `static`인 요소에 `z-index`를 줘도 브라우저는 이를 **무시**하고, 문서 작성 순서(source order)대로만 쌓인다.

| 코드 | `.a`의 `position` | `z-index` 적용? | 결과 |
|---|---|---|---|
| A | `static`(기본값) | ❌ 무시됨 | `.b`가 나중에 그려져 위에 옴 |
| B | `relative` | ✅ 적용됨 | `.a`가 새 **쌓임 맥락(stacking context)**을 만들고 위로 |

**핵심 정리 세 줄:** ① `z-index`를 쓰려면 반드시 `position: relative`/`absolute`/`fixed`/`sticky` 중 하나를 함께 지정해야 한다 ② `position: static`에서는 `z-index`가 아무 효과가 없다 ③ 같은 쌓임 맥락 안의 `static` 요소들끼리는 z-index와 무관하게 **작성 순서대로** 뒤 요소가 위에 그려진다.

### 코드리뷰 7연작에 쌓인 패턴

오늘로 CSS 코드리뷰가 일곱 번째다. 되짚어보면 전부 같은 형태의 함정이었다:

| 회차 | 속성 | 안 먹히는 이유 |
|---|---|---|
| 25 | `left`/`width` | 성능은 되지만 **레이아웃을 통째로 다시 계산**해서 무거움 |
| 26 | `width: 100%` | **기준(부모 콘텐츠 영역)**을 착각 |
| 27 | `absolute` vs `flex` | 결과는 같아도 **문서 흐름 처리**가 다름 |
| 28 | `z-index` | **전제 조건**(`position` non-static)이 빠짐 |

CSS는 "속성 하나가 독립적으로 동작"하는 게 아니라, **다른 속성·문서 구조와의 관계 속에서 동작**한다는 걸 네 번 연속으로 확인했다. `z-index`를 이해하려면 `position`을 먼저 알아야 하는 것처럼.

## 2. 2주차 프로젝트 · 스터디 시스템 기획

오늘부터 팀은 Zeteo 본작업과 별개로 **2주차 주간 과제**를 병행한다. 강사 지침은 "**다른 기술을 배우려는 의지가 있는가**"를 평가하는 것: 필수 산출물은 기획서·유저시나리오·시스템설계도·GitHub 링크·발표자료·시연영상, 목요일(오늘) 16시까지 문서 제출, 금요일 15시30분 발표.

### 회의 · 30분 만에 골격이 잡히다

회의록을 보면 결정이 빠르게 수렴했다.

**김정현(진행자)이 시스템 골격을 정의했다:**

> 인풋 = 배우고 싶은 주제, 아웃풋 = 팀이 이해할 수 있는 형태

그리고 참고자료 형식으로 **퀴즈**를 채택해 "기본설명 + 퀴즈"를 기본 베이스로 확정했다. 저장 위치는 두 후보를 기각했다: Discord 아티팩트(권한 재설정 번거로움), 새 스레드(매번 이름-매칭 번거로움). **GitHub 2주차 폴더에 md로 쌓는 방식**을 채택했다.

이게 왜 빠르게 정해졌는지는 명확하다: **1주차에 이미 회의록 자동화 시스템을 만들어둔 팀**이라, "GitHub에 md로 쌓기"는 새로 발명할 필요 없이 **이미 검증된 패턴을 재사용**하는 결정이었다. 23·24일차에 만든 git 안전장치, front matter 구조가 오늘 그대로 다시 쓰인다.

### 핵심 설계 결정 · "활용처"는 사람이 쓰지 않는다

기획서에서 가장 중요한 판단은 이거였다:

> 처음엔 사용자가 주제·이유·활용처를 전부 인자로 넘기는 방식도 고려했다. 하지만 그러면 "실제로 활용했다"는 근거가 **본인 진술뿐**이라 증빙력이 약하다.

그래서 **활용처만은 사람이 서술하지 않고, 스킬이 Zeteo 코드베이스를 직접 검색해서 찾아내도록** 설계했다. 못 찾으면 지어내지 않고 **"찾지 못함"이라고 정직하게 기록**하도록 명시했다. 근거 없는 활용처를 만들어내는 게 가장 큰 리스크였기 때문이다.

**이유(reason)는 사람이 쓰고, 활용처(evidence)는 시스템이 검증한다.** 서술은 주관이라도 되지만, "실제로 썼다"는 사실 주장은 검증 가능해야 한다는 구분이다. 22일차 봇 프로젝트 기획에서 "프롬프트 인젝션 방어가 구조적"이었던 것과 닮았다: **믿을 수 없는 것(자기 진술)을 걸러내는 게 기능이 아니라 설계**로 되어 있다.

### 조사 방법의 세 번째 시도 · 두 번의 기각 끝에 나온 해법

Zeteo(팀의 실제 코드)를 조사하는 방법을 두 개 검토하고 둘 다 버렸다.

**시도 1: 로컬 폴더를 그대로 Grep/Read.** 두 가지 문제로 기각:
1. 로컬이 항상 최신이 아닐 수 있음 (팀원이 푸시해도 `pull` 안 하면 반영 안 됨)
2. 팀이 브랜치를 나눠 작업함(`main`/`dev`/`feat/bot`/`feat/server`/`feat/game-ui`/`feat/layout`). 로컬은 그중 **브랜치 하나만** 체크아웃되어 있어서, 다른 팀원 브랜치의 기능은 애초에 안 보인다

**시도 2: GitHub API/웹 검색.** 비공개 저장소 인덱싱 제약, 기본 브랜치 위주로만 검색되는 한계로 기각.

**채택: `git fetch`로 참조만 최신화하고, `git grep`으로 모든 원격 브랜치를 한 번에 검색.**

```
git fetch origin                    # 작업 트리는 안 건드리고 참조만 최신화
git grep "웹소켓" $(git branch -r)   # 모든 원격 브랜치를 한 번에 검색
git show <브랜치>:<경로>             # 체크아웃 없이 그 브랜치 시점 내용 확인
```

**작업 트리(체크아웃 브랜치)는 건드리지 않은 채로** 다른 팀원 브랜치의 코드까지 확인하는 방법이다. 26·27일차에 병합 사고를 겪으며 브랜치·원격·로컬의 차이를 몸으로 배웠는데, 그 지식이 여기서 "검색 도구를 설계하는 재료"로 전환됐다. **문제를 겪어본 사람만 낼 수 있는 해법**이라는 생각이 들었다.

### git 작업 안전장치 · 1주차 것을 그대로 가져왔다

> 1주차 회의록 자동화 시스템과 **동일한 원칙**을 그대로 적용함.

새 파일 외 변경사항 있으면 중단, `main` 아니면 중단, 충돌 시 자동 병합 안 함, 새 파일 하나만 반영, push 실패 시 강제 안 함. 다섯 가지 전부 19·23일차에 세운 원칙 그대로다. **한번 검증한 안전장치는 재사용한다.** 매번 새로 설계하지 않아도 되는 게 먼저 만들어둔 인프라의 값어치였다.

### 유저 시나리오 · 부수 효과가 진짜 가치였다

시나리오의 페르소나(팀원 B)는 웹소켓을 "개념으로만 알고 있었지 우리 프로젝트 어디에 어떻게 쓰이는지는 확인해본 적 없는" 상태로 시작한다. 명령을 실행하니:

> 스킬이 저장소 전체 브랜치를 뒤져서 실제로 웹소켓이 쓰인 파일을 찾아냈다. **몰랐던 브랜치의 코드였음.** 로컬에 체크아웃해둔 적도 없던 브랜치라, 직접 찾았으면 놓쳤을 부분.

시나리오 문서가 스스로 짚은 "얻는 것":

> 활용처를 직접 안 써도 되니, **스스로도 몰랐던 팀원의 코드를 이 과정에서 발견하게 됨** (부수 효과지만 실질적으로 유용함)

원래 목적은 "학습 의지 증빙"이었는데, 만들고 나니 **"내가 모르는 팀원의 작업을 찾아주는 도구"**라는 다른 쓸모가 붙었다. 24일차 회의록 시스템의 시나리오 ④(멈추는 순간도 가치다)에 이어, **의도한 기능 밖에서 가치가 생기는 두 번째 사례**다.

### 시스템 구조 · 저장은 1주차와 완전히 같은 모양

```
TeamB/2주차/
├── 개념학습_기록_시스템_기획.md
├── 시스템/
│   ├── 유저 시나리오.md
│   └── 시스템 설계도.md
└── 배운개념/
    └── 웹소켓.md   (주제별로 계속 누적)
```

파일 front matter도 1주차 회의록과 같은 패턴(날짜·주제·이유)을 그대로 따랐다. **같은 저장 패턴을 두 번째 프로젝트에도 그대로 쓰니, 팀 저장소 전체가 하나의 일관된 형식으로 쌓인다.** 나중에 발표 자료를 만들 때도 "우리는 이 패턴을 두 번 재사용했다"가 하나의 근거가 될 것 같다.

### TCP/UDP는 일부러 뺐다

회의록에 흥미로운 대목이 있다: 유민성이 "TCP만 사용" 확인 발언을 했는데, 진행자가 **"맥락 오염 우려"**로 이 논의를 다른 채널로 분리했다. 스터디 시스템 기획 회의에 TCP/UDP 세부 토론이 섞이면 회의록 자체가 늘어지기 때문. **한 회의는 한 주제만 다룬다**는 원칙이 실제로 지켜지는 걸 봤다.
