웹개발 수업 22일차. 어제에 이어 **HTML 코드리뷰 발표**를 하나 더 준비했고(이번엔 로그인 페이지), 팀 프로젝트 **기획안 2건**을 추가로 작성했다. 어제 코드와 오늘 코드가 정확히 반대되는 장단점을 갖고 있었던 게 오늘의 재미있는 발견이었다.

## 1. 코드리뷰 ②, 로그인 페이지 20줄

어제는 회원가입 폼 16줄, 오늘은 로그인 페이지 20줄. 대상은 HTML 입문자, 분량은 5분.

### 문서 뼈대: head는 세 가지 일을 한다

- `<!DOCTYPE html>`은 태그가 아니라 선언이다. "최신 HTML 규칙으로 읽어달라"는 뜻이고, 빠지면 브라우저가 옛 방식으로 해석해 레이아웃이 어긋난다
- `<html lang="ko">`는 화면상 변화는 없지만, 화면 낭독기가 한국어 발음으로 읽어준다
- `<head>` 세 줄 = **"글자 안 깨지게(charset), 모바일에서 잘 보이게(viewport), 이름 붙이기(title)"**

`viewport` 설명이 특히 와닿았다. 이 줄이 없으면 휴대폰에서 데스크톱 화면을 억지로 축소한 것처럼 글씨가 깨알같이 나온다. 3일차에 Emmet `!` 뼈대를 배울 때 스쳐 지나갔던 그 줄이다.

### 오늘 발표의 핵심: label과 input을 잇는 for/id

```html
<label for="userId">아이디</label>
<input type="text" id="userId">
```

`for`와 `id`가 **userId로 똑같은 게 우연이 아니라 둘을 연결하는 장치**다. 연결해두면:

1. "아이디" **글자를 클릭하면 커서가 입력칸으로 이동** (모바일에서 특히 편함)
2. 화면 낭독기가 "아이디 입력칸"이라고 읽어준다. 연결이 없으면 그냥 "입력칸"이라고만 읽는다

발표 팁도 여기에 뒀다. 브라우저에서 실제로 글자를 클릭해 커서가 옮겨가는 걸 보여주면 반응이 좋다고. **"이 습관 하나만 가져가도 오늘 발표는 충분하다"**를 맺음말로 잡았다.

### 한 걸음 더: 이 코드에 없는 것 세 가지

| 없는 것 | 결과 |
|---|---|
| `action` · `method` | 어디로 어떻게 보낼지 미정, 버튼 눌러도 **같은 페이지 새로고침으로 끝** |
| `name` | **id는 문서 안에서 요소를 가리키는 이름, name은 서버로 보낼 때의 이름표.** name이 없으면 값이 전송되지 않음 |
| `required` · `autocomplete` | 빈칸 제출 방지, 비밀번호 관리자 인식 등 속성 한두 개로 사용성이 꽤 올라감 |

### 어제 코드 vs 오늘 코드: 정반대의 장단점

두 발표를 나란히 놓으니 재밌는 그림이 나왔다.

| | 어제(회원가입 16줄) | 오늘(로그인 20줄) |
|---|---|---|
| label | ❌ `<p>`로 대체 (접근성 문제) | ✅ `for`/`id`로 정확히 연결 |
| action·method | ✅ POST `/signup` | ❌ 없음 (전송 안 됨) |
| name | ✅ 있음 | ❌ 없음 |

**어제 코드는 "보내지는데 접근성이 나쁘고", 오늘 코드는 "접근성은 좋은데 안 보내진다."** 둘을 합치면 비로소 완성된 폼이 된다. 우연히 좋은 교보재 한 쌍을 얻은 셈이라, 발표에서도 이 대비를 언급하기로 했다.

공통된 결론도 하나 있다. `type="password"`는 화면에서 가려줄 뿐, 전송을 안전하게 만드는 건 HTTPS의 역할이라는 것. 이틀 연속 같은 Q&A가 예상 질문 1번이다.

## 2. 팀 프로젝트: 기획안 2건 추가

주제 후보로 봇 기반 아이디어 두 개를 더 작성했다. 둘은 독립된 안이 아니라 **본안 + 대체안 짝**이다.

### ① 봇과 함께하는 마피아 (Bot Mafia)

사람과 봇이 섞여 마피아 게임을 하고, 마지막에 **누가 봇이었는지** 지목하는 웹 게임.

핵심 설계 원칙은 봇이 두 정체를 동시에 숨겨야 한다는 것이다.

1. 봇이라고 지목당하지 않을 것 (최우선)
2. 마피아 게임에서 이길 것

그런데 이 둘이 **정면충돌**한다. 봇 티를 안 내려면 조용한 게 안전한데, 마피아에서 조용하면 의심받아 죽는다. 마피아 역할이면 거짓말을 해야 하는데, 거짓말은 논리 파탄을 만들고 파탄은 곧 봇 티다. 이 충돌이 게임의 심장이자 발표 첫 슬라이드 문장.

가장 프론트엔드다운 부분은 발언 타이밍을 LLM 없이 결정한다는 점이다.

```
발언욕구 =
    (내가 직접 지목당함        ? 100 : 0)
  + (직전 메시지가 나를 언급    ?  60 : 0)
  + (내 마지막 발언 후 경과초 × 성격계수)
  - (최근 30초 내 내 발언 수 × 40)
  - (현재 생성 중인 봇이 있음   ?  50 : 0)
```

임계값을 넘은 봇 중 **최고 점수 1명만** 큐에 진입하고, 큐는 직렬 처리된다. 이게 곧 API 호출 제어 장치가 된다. 여기에 타이핑 위장(문장 길이 × 0.15~0.35초/글자 + 난수)까지 얹는다. "응답이 빨라도 티가 나고 느려도 티가 난다"는 말대로다.

부록의 **"봇 티 목록"**이 특히 흥미로웠다. 쉬운 것(반응이 0.1초, 말투가 일정)과 어려운 것을 나눴는데, 어려운 쪽이 진짜였다:

> 문체가 너무 완결됨(사람은 오타 내고 초성 쓰고 중간에 끊는다) · 논리가 과잉(사람은 "그냥 느낌인데"로 끝낸다) · **기억이 너무 정확**(3라운드 전 발언을 정확히 인용하면 그게 오히려 티) · 뒤끝이 없음 · 침묵을 못 견딤

### ② 봇 프롬프팅 아레나 (Bot Prompting Arena)

코드가 아니라 **프롬프트로 봇을 만들어** 겨루게 하는 플랫폼. 자연어로 전략을 쓰면 시스템이 **검증된 규칙(JSON DSL)으로 컴파일**하고, 컴파일된 봇들이 결정론적 시뮬레이션에서 대전한다.

관통하는 한 문장은 "LLM은 컴파일러다. 심판이 아니다."

| 구분 | LLM 개입 |
|---|---|
| 봇 등록 (프롬프트 → 규칙 변환) | **개입함, 1회** |
| 대전 시뮬레이션 / 리그 수천 판 / 리플레이 | 개입 안 함 |

따라오는 이점이 명확하다. 대전이 결정론적이고(같은 봇, 같은 시드면 항상 같은 결과이므로 리플레이가 입력 로그만으로 성립한다), 무료고 즉시 실행되며, 검증 가능하고(컴파일된 규칙을 사람이 읽을 수 있다), LLM 서비스가 죽어도 리그는 계속 돌아간다.

두 가지 설계가 특히 인상적이었다.

- 프롬프트 주입 방어가 구조적이다. 게임에 영향을 주는 건 오직 스키마 검증을 통과한 DSL뿐이다. LLM이 뭘 출력하든 엔진은 DSL만 읽으므로 주입 시도는 검증 단계에서 자동으로 걸러진다. 사후 필터링이 아니라 구조 자체가 방어인 셈이다.
- DSL 직접 편집 모드. 컴파일된 규칙을 사용자가 직접 고칠 수 있게 한다. 편의 기능이 아니라 "LLM 없이도 이 플랫폼이 성립한다"는 증명이자 "GPT 래퍼" 비판에 대한 반박이다.

## 3. 두 기획안을 관통하는 것: AI 프로젝트인데 AI를 덜 쓴다

기획서 둘을 나란히 놓고 보니 같은 철학이 흐르고 있었다.

| | 봇 마피아 | 아레나 |
|---|---|---|
| LLM 최소화 | 발언 **타이밍**은 로컬 규칙으로 계산 | 대전 전체가 **LLM 없이** 결정론 실행 |
| 호출 예산 | 1게임 **40회 이하**가 설계 목표 | 등록 시 **1회**뿐 |
| 개발 중 절약 | **3모드 구조**(모의/리플레이/실전), UI 담당자는 호출 0회 | 컴파일 캐싱, 사전 컴파일 봇 |
| 장애 대비 | 사전 녹화 게임 리플레이 | 사전 컴파일된 봇 5~6개 |

특히 봇 마피아 기획서의 이 문장이 핵심이다:

> **호출 횟수를 줄이는 설계가 곧 게임을 좋게 만드는 설계**여야 한다. 봇 전원이 매 턴 발언하면 호출이 폭발하는데, 그건 게임적으로도 나쁘다. 사람들은 동시에 떠들지 않기 때문이다.

**제약이 오히려 설계를 개선한다**는 것. 무료 티어 한도가 발언권 큐를 낳고, 그 큐가 자연스러운 대화를 만든다. 17일차에 HuggingFace 토큰이 부족해 Pollinations로 갈아탔던 경험이 있는데, 그때는 "막혀서 우회"였다면 이번엔 **"제약을 먼저 전제하고 설계"**하는 쪽이다.

공통점이 하나 더 있다. 두 기획서 모두 선행 사례를 조사하고 공백을 찾았지만, 끝에 같은 문장을 달았다:

> 학생 프로젝트는 검색 색인이 불완전하므로 **"최초"라고 주장하지 않는다.** 발표에서는 "조사 범위 내에서 확인하지 못했다"로 표현한다.

20일차 조사 보고서의 `미검증` 표기 원칙이 기획서에도 이어졌다. **모르는 걸 모른다고 적는 습관**이 팀 문서의 기본값이 된 것 같다.
