웹개발 수업 44일차. 코드리뷰는 SSG였다. 40일차 SPA, 41일차 CSR, 42일차 SSR에 이어 네 번째 개념 문제고, 이번에 렌더링 방식 네 개가 한 줄로 다 이어졌다. 오후에는 9월 8일 최종발표 자료 초안을 짰다. 18장짜리 골격을 오늘 처음부터 끝까지 세웠고, 발표는 내가 진행한다.

## 1. 코드리뷰 ⑰: SSG, 요청이 오기 전에 다 만들어 두는 쪽

SSG는 빌드 시점에 각 페이지의 HTML을 미리 다 만들어 정적 파일로 저장해 두고, 요청이 오면 그 파일을 그대로 내려주는 방식이다. 요청 시점에 만드는 일이 아예 없다.

지금까지 정리한 셋과 나란히 놓으면 축이 하나로 정리된다. HTML을 언제 만드느냐다.

| | HTML을 만드는 시점 | 사람마다 다른 화면 | 데이터가 바뀌면 |
|---|---|---|---|
| CSR | 브라우저에서, 요청을 받은 뒤 | 가능 | 그 자리에서 다시 그린다 |
| SSR | 서버에서, 요청이 올 때마다 | 가능 | 다음 요청부터 반영된다 |
| SSG | 빌드할 때, 요청이 오기 전에 | 불가능 | 다시 빌드해야 반영된다 |
| ISR | 빌드 + 주기적 재생성 | 불가능 | 재생성 주기가 돌아와야 반영된다 |

세 번째 열이 오늘 제일 크게 남았다. 장점 목록(빠르다, 서버 부하가 없다, SEO에 좋다, CDN에 뿌리기 쉽다)은 전부 "요청 전에 다 만들어 놨다"는 한 문장에서 파생된다. 그런데 요청 전에 만들려면 누가 요청할지 몰라도 되는 페이지여야 한다. 즉 모두에게 같은 화면이어야 한다. 단점 목록도 같은 문장에서 나온다. 데이터가 바뀌어도 재빌드 전까지는 옛날 HTML이 나가고, 페이지가 많아지면 빌드가 길어지고, 개인화 화면에는 쓸 수 없다.

Zeteo가 SSG를 못 쓰는 이유는 그래서 SSR 때와 다르다. SSR을 안 쓴 건 서버가 채워 보낸 HTML이 소켓 이벤트 한 번에 곧바로 낡기 때문이었다. SSG는 그보다 앞에서 걸린다. `view.ts`의 `buildGameStateFor(room, playerId)`가 사람마다 다른 화면을 만드는 게 이 게임의 핵심인데, 빌드 시점에는 그 playerId가 존재하지 않는다. 미리 만들어 둘 대상 자체가 없는 것이다. 중간발표에서 정보 격리를 "개발자 도구를 열어도 화면에 없는 값은 애초에 오지 않는다"로 설명했는데, 그 설계를 택한 순간 SSG는 선택지에서 빠져 있었다.

대신 오늘 SSG를 실제로 쓰고 있는 걸 하나 찾았다. 이 블로그다. GitHub Pages에 Jekyll로 올리고 있으니 글을 push하면 Actions가 `jekyll b`로 모든 글의 HTML을 미리 만들고, `htmlproofer`로 내부 링크를 검사한 뒤 배포한다. 런타임 렌더링이 없다는 성질이 실패 방식에도 그대로 나타난다. 33일차 글에서 대괄호 뒤에 괄호를 붙여 쓴 탓에 없는 링크가 하나 생겼는데, 그게 실행 중 404가 아니라 빌드 실패로 잡혀서 배포 자체가 안 됐다. 서버에서 죽을 일이 없는 대신 문제가 전부 빌드 시점으로 몰린다. 장점과 단점이 같은 성질의 앞뒷면이라는 게 여기서도 똑같았다.

## 2. 최종발표 자료 초안 18장

9월 8일 발표까지 8일 남았고, 기능 동결이 어제였으니 이제 만드는 일은 끝났고 설명하는 일만 남았다. 오늘 목차부터 발표자 노트 대사까지 한 번에 세웠다.

| 섹션 | 무엇을 말하나 |
|---|---|
| 01 팀원 소개 | 파일 단위로 소유자를 정해 병합 충돌 0건 |
| 02 기획 배경 | 페르소나가 겪는 불편 셋(사회자, 인원, 설치)을 기능 셋으로 |
| 03 유저 시나리오 | 한 판 10단계 약 6분. 게임 승패와 봇 색출은 독립 |
| 04 시스템 설계도 | 브라우저, 서버, LLM, DB. 화면은 상태를 소유하지 않는다 |
| 05 핵심 코드 리뷰 | 여덟 개의 화면을 하나의 페이지에 |
| 06 활용 방안 · 사업성 | 네 갈래 활용 + AdSense |
| 08 개발 히스토리 · 결론 | 기획 v1.0에서 최종까지 |
| 09 시연 | 사람 4 + 봇 1로 한 판 |

목차를 짜면서 가장 오래 잡고 있었던 건 무엇을 넣을지가 아니라 순서였다. 결론은 시연을 맨 뒤로 뺀 것이다. 중간에 넣으면 실패했을 때 남은 발표가 흔들리는데, 맨 뒤에 두면 그 앞은 이미 끝나 있다. 라이브로 하되 같은 판을 미리 녹화해 두고 네트워크가 막히면 즉시 전환한다.

결론 문장도 오늘 정했다. 오프라인에서 저절로 지켜지던 규칙은 코드로 옮기는 순간 전부 "어떻게 강제하지?"가 된다는 것. 표지 뒤부터 결론까지 이 한 문장으로 수렴하게 배치했다.

## 3. 12분을 초 단위로 나눠 봤다

공지의 기준은 발표 12분에 질의응답 8분이고, 초과도 조기 종료도 감점이다. 11분 30초 내외 스크립트를 권장한다고 별표까지 붙어 있어서, 장표마다 발표자 노트에 누적 타임코드를 박아 뒀다.

| 구간 | 배정 |
|---|---|
| 표지 · 목차 | 30초 |
| 01 팀원 소개 | 30초 |
| 02 기획 배경 | 50초 |
| 03 유저 시나리오 | 30초 |
| 04 시스템 설계도 | 30초 |
| 05 핵심 코드 리뷰 | 2분 50초 |
| 06 활용 방안 · 사업성 | 1분 5초 |
| 08 개발 히스토리 · 결론 | 30초 |
| 09 시연 | 4분 |

합이 11분 35초다. 나눠 놓고 보니 코드 리뷰 한 덩어리가 시연을 뺀 발표 시간의 3분의 1을 넘게 먹는다. 처음엔 너무 많은가 싶었는데, 평가 100점 중 기술성 25점과 논리성 25점이 여기에 걸려 있다. 기획성 15점과 사업성 10점을 합쳐도 코드 리뷰 쪽이 두 배다. 시간을 점수 배분에 맞춰 놓고 나니 나머지 장표에서 무엇을 뺄지가 저절로 정해졌다. 42일차에 "최종발표 항목 아홉 개 중 뺄 것 고르기"를 다음에 할 일로 적어뒀는데, 결국 항목을 빼는 게 아니라 항목마다 초를 깎는 방식으로 풀렸다.

발표는 내가 하고 시연은 팀원이 맡는다. 34일차에는 내가 만든 코드북을 팀원이 발표했으니 반대가 됐다.

## 4. 초안이 스스로 드러낸 두 개의 구멍

다 짜놓고 처음부터 넘겨보니 두 곳이 걸렸다. 둘 다 만들 때는 안 보이다가 이어서 보니까 보인 것들이다.

시스템 설계도가 한눈에 안 들어온다. 브라우저 쪽 화면 여섯 개, 토큰과 공용 컴포넌트, 서버의 게임 로직 코어, 외부 API 셋, DB까지 실제로 있는 걸 다 그려 넣었더니 30초 안에 짚을 수 있는 그림이 아니게 됐다. 노트에는 말로 짚을 곳을 셋으로 줄여 적어놨는데(상태를 소유하지 않는다, 화면 5 + 1, 키와 미공개 정보는 서버에만), 정작 그림은 셋을 안 도와준다. 정확한 그림과 30초에 읽히는 그림은 다른 물건이었다.

핵심 코드 리뷰가 내 파트로 들어가 있다. 여덟 개의 화면을 하나로 합친 이야기는 중간발표 때 쓴 것이고 지금 자리에는 임시로 넣어둔 것이다. 최종발표에서 대표로 보여줄 코드는 봇 담당 파트로 통째로 갈아야 한다. 판단, 생성, 검사, 출력 네 단계를 도는 봇 엔진이 이 프로젝트에서 가장 설명할 값어치가 있는 부분이고, 심사위원이 중간발표에서 남긴 지적에도 설문 기반 봇 개선이 들어 있었다. 다행히 오늘 짠 네 단계 틀(맥락과 문제, 대안, 선택과 근거, 효과)은 주제와 무관한 뼈대라 내용만 바꿔 끼우면 된다.

개발 히스토리 장의 수치도 낡았다. 파일 수와 커밋 수가 8월 19일 중간발표 기준이라 발표 직전에 다시 세야 한다. 오늘 코드리뷰가 SSG였던 게 묘했다. 미리 만들어 둔 페이지는 만든 순간부터 낡기 시작하고, 다시 빌드하기 전까지는 옛날 값이 그대로 나간다. 발표 자료도 정확히 같은 물건이었다. 오늘 만든 18장은 오늘의 스냅샷이고, 9월 8일까지 최소 한 번은 재빌드해야 한다.

## 5. 다음에 할 것

- 핵심 코드 리뷰를 봇 파트로 교체. 네 단계 틀은 그대로 두고 내용만 갈아 끼우기
- 시스템 설계도 단순화. 정확한 그림 말고 30초에 읽히는 그림으로 다시 그리기. 말로 짚을 세 곳만 남기는 방향
- 파일 수, 커밋 수 등 히스토리 장의 수치를 발표 직전에 재집계
- 시연 녹화본 촬영. 라이브가 막혔을 때 바로 전환할 4분짜리 백업
- 11분 35초를 실제로 소리 내어 재보기. 노트의 타임코드는 아직 추정치다

**오늘의 한 줄 정리:** SSG가 빠른 이유와 낡는 이유는 똑같이 "요청이 오기 전에 다 만들어 뒀다"는 한 문장에서 나온다. 오늘 하루 만에 세운 18장도 같은 물건이라, 다 만들어 둔 덕분에 12분을 초 단위로 나눌 수 있었고 동시에 그 안의 수치와 코드 리뷰 파트는 벌써 재빌드 대상이 됐다.
