웹개발 수업 31일차. 코드리뷰는 **문자열 불변성**: `replace()`를 불렀는데 왜 안 바뀔까. 팀 프로젝트 Zeteo는 이번 주 UI 담당(파트 C, 나)과 레이아웃 담당(파트 D)의 브랜치를 병합하는 단계인데, **미리 샌드박스에서 병합해보고 충돌 3건을 문서로 정리**했다. 그중 하나는 "지워야 할 파일이 되살아나는" 흔한 사고와 정반대의 함정이었다.

## 1. 코드리뷰 ⑨: replace()를 불렀는데 왜 안 바뀔까

댓글 금칙어 필터. 의도는 "바보"를 `**`로 가리는 것.

```js
function maskBadWord(comment) {
  comment.replace('바보', '**');
  return comment;
}

console.log(maskBadWord('이 바보야 답답하네'));
```

**기대:** `이 **야 답답하네` **실제:** `이 바보야 답답하네` (마스킹 안 됨)

### Q1·Q2. 원인은 반환값을 버린 것

```js
comment.replace('바보', '**');   // ← 반환값을 버림
```

**자바스크립트의 문자열은 불변(immutable) 값이다.** `String.prototype.replace()`는 원본을 직접 수정하지 않고, 치환이 적용된 **새로운 문자열을 반환만** 한다.

- `comment.replace(...)`를 호출해도 `comment`가 가리키는 값 자체는 안 바뀐다
- 이 줄은 `replace()`가 만든 새 문자열을 어디에도 담지 않고 **그냥 버린다**
- 그래서 `return comment`는 처음 받은 원본을 그대로 돌려준다

> 배열의 `push()`·`sort()`처럼 원본을 직접 바꾸는(mutate) 메서드에 익숙하면 `replace()`도 그럴 거라 착각하기 쉽다. **`replace()`는 그런 부류가 아니라는 게 이 문제의 핵심.**

### 수정: 반환값을 실제로 쓴다

```js
function maskBadWord(comment) {
  return comment.replace('바보', '**');
}
// 또는
function maskBadWord(comment) {
  comment = comment.replace('바보', '**');
  return comment;
}
```

**참고:** `replace('바보', '**')`는 **첫 번째로 매칭된 것 하나만** 치환한다. 여러 번 나오면 정규식 `g` 플래그가 필요하다: `comment.replace(/바보/g, '**')`.

### 어제 버그와의 대칭: "값이 그대로 있다고 믿은 게" 문제

30일차는 **값이 다른 타입인데 같다고 믿은** 버그(`'12000' + 3000`)였다면, 오늘은 **메서드가 원본을 바꿔줄 거라고 믿은** 버그다. 방향은 반대지만 뿌리는 같다. **JS의 어떤 동작을 "당연히 이럴 것"이라고 가정하는 순간 사고가 난다.** `push`/`sort`(mutate)와 `replace`/`slice`/`map`(non-mutate, 새 값 반환) 두 계열을 확실히 구분해야 한다는 걸 이번 기회에 정리했다.

## 2. 팀 프로젝트: layout ↔ game-ui 병합 가이드

이번 주 파트 C(내 화면)와 파트 D(레이아웃)가 8/10 시안 1을 각자 자기 파일에 반영했다. **병합하기 전에 샌드박스에서 미리 합쳐보고**, 충돌 지점을 문서로 정리해뒀다.

```
feat/game-ui (C): dev 대비 +5, PR 승인 대기
feat/layout  (D): dev 대비 +2, PR 미제출
```

`git merge` 결과 **충돌 3건**. 26일차에 배운 대로 `--diff-filter=D`로 조용히 사라지는 파일부터 확인했는데, 이번엔 **비어 있었다**. 다행히 몰래 지워지는 파일은 없는 병합이었다.

### 충돌 ① VoteScreen.tsx: 삭제를 "유지"해야 하는 함정

git이 이렇게 알린다:

```
CONFLICT (modify/delete): apps/frontend/src/VoteScreen.tsx
deleted in HEAD and modified in origin/feat/layout.
```

**여기서 "수정본을 남긴다"를 고르면, 이미 없앤 화면이 되살아난다.** 배경:

- 기획서 v3.0에서 **봇 지목 소유가 파트 D → C로 이관**됐고, 독립 화면 `VoteScreen.tsx`는 `screens/BotVote.tsx`(내 `GameScreen`의 5번째 팝업)로 흡수됐다
- 나는 `App.tsx`의 라우팅과 `types.ts`의 `VoteScreenState`까지 같이 정리해뒀다. **파일만 되살리면 타입도 라우팅도 없는 고아 파일**이 된다
- D가 그 파일에 남긴 수정(라디오 점 → `Avatar` 교체)은 **`BotVote.tsx`에 이미 같은 방식으로 들어가 있다**: 잃는 기능이 없다

```bash
git rm apps/frontend/src/VoteScreen.tsx
```

26일차에 겪은 사고(R8: 파일이 조용히 사라짐)와 **정반대 모양**이다. 그때는 "삭제된 걸 되살려야 하나"였는데, 이번엔 "삭제된 걸 **되살리면 안 되는**" 경우. 겉보기엔 같은 `modify/delete` 충돌이라도, **어느 쪽이 최신 설계를 반영했는지**를 알아야 올바른 선택이 갈린다. 문서에 D께 남긴 메모도 인상적이었다:

> D께: `VoteScreen.tsx`에 넣으신 Avatar 적용은, 그 파일이 이관으로 사라지는 걸 모르신 상태에서 하신 작업으로 보입니다. 같은 개선이 `BotVote.tsx`에 반영돼 있으니 결과물은 안 없어집니다.

27일차에 배운 "실수 같은데요"가 아니라 "이렇게 됩니다"로 말하기가 여기서도 그대로 적용됐다. **D의 작업이 헛수고가 됐다고 말하는 대신, 그 개선이 다른 곳에 살아있다는 사실을 먼저 알린다.**

### 충돌 ② Avatar.tsx: 둘 다 옳아서 둘 다 채택

`dev`에 없던 파일을 **양쪽이 각자 새로 만들어서** `add/add` 충돌이 났다.

| | `feat/layout` (D, 15:55) | `feat/game-ui` (C, 16:17) |
|---|---|---|
| 이니셜 추출 | **마지막 단어의 첫 글자** | 첫 글자 |
| `dead` variant | 있음 | **제거** |

**시각이 22분 차이.** 여기서 중요한 판단이 나온다:

> D가 C의 제거를 되돌린 게 아니라, **두 사람이 22분 사이에 각자 다른 것을 고친 것.** 두 변경은 충돌하지 않으므로 둘 다 채택한다.

- **이니셜 = 마지막 단어(D안)**: mock의 `"참가자 4"`가 전부 "참"으로 겹치던 문제를 D가 해결. 실서버 라벨은 한 글자라 두 방식 결과가 같아서, **손해 없이 mock만 좋아진다**
- **`dead` variant 제거(C안)**: *"생사 투표에서 처형되면 그 판이 즉시 끝난다, 탈락한 채 게임이 계속되는 상태는 없다"*가 8/10에 확정됐다. 이 게임에 없는 상태라 지운 게 맞다

수정 시각까지 비교해서 "누가 누굴 되돌린 게 아니다"를 확인한 게 핵심이었다. **git log의 타임스탬프가 판단 근거가 될 수 있다**는 걸 처음 실감했다.

### 충돌 ③ tokens.css: 소유자 기준으로 통째로 채택

이 파일은 **D 소유**다. 내가 넣은 값은 D의 확정값을 내 브랜치에 베껴 적은 것뿐이라, 사실상 D 버전의 부분집합이었다.

```bash
git checkout origin/feat/layout -- apps/frontend/src/styles/tokens.css
# 그리고 .avatar-dead { ... } 한 줄만 삭제 (충돌②의 결정과 짝)
```

여기서 5일차부터 계속 강조된 CSS 변수 설계가 실제로 값을 증명했다:

> **파트 C의 `game.css`는 손댈 게 없다.** 색·폰트를 전부 `var(--토큰, fallback)`으로만 참조하고 있어서, D가 폰트를 바꾼 게(Lora 제거) **자동으로 따라온다.**

25일차에 만든 `var(--토큰, fallback)` 패턴이 오늘 "소유자 파일을 통째로 갈아끼워도 내 CSS가 안 깨지는" 실질적 이유가 됐다. fallback을 지우는 게 아니라, **fallback이 있어도 실제 값이 우선 적용되는 CSS 변수의 기본 동작** 덕분에 병합이 매끄러웠다.

### 검증: 샌드박스에서 미리 다 돌려봤다

세 충돌을 해소한 병합본을 실제로 빌드까지 해봤다:

```
tsc -b apps/frontend      — 0 오류
eslint apps/frontend/src  — 0 오류
npm run build -w frontend — 성공
Playwright 1280px / 390px 양쪽에서 4개 화면 렌더 확인, 콘솔 에러 0건
아바타 이니셜이 실제로 4·1·7로 구분되는 것 확인
```

**진짜 병합 전에 가짜 병합으로 결과를 미리 확인**하는 절차다. 26일차에 세운 "시험 병합" 습관이 이번엔 문서로까지 남는 수준으로 발전했다. 심지어 "이 병합과 별개인 것들"이라는 섹션에서 **아직 못 정리한 것(낡은 주석 하나)까지 남겨뒀다**. 완벽을 기다리지 않고 병합하되, 뭐가 남았는지는 투명하게 적어둔다.

### 이 문서에서 반복된 패턴: "표시하지 않는 근거"

세 충돌 모두 결론 앞에 **왜 그런지의 근거**가 붙어 있다: 기획서 v3.0 커밋 번호, 인수인계 문서 4절, 커밋 타임스탬프. 20일차 조사 보고서의 `[확정]`/`미검증` 표기, 22·28일차의 "안 한 것도 보여준다"는 태도가 이번엔 **병합 결정의 각주**로 이어졌다. 결정만 적으면 "왜 그렇게 했는지" 나중에 또 물어봐야 하는데, 근거를 같이 적어두면 **다음 사람이 같은 질문을 안 해도 된다.**
