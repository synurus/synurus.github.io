웹개발 수업 21일차. 오전에는 **회원가입 폼 HTML 16줄로 코드리뷰 발표**를 준비했고, 오후에는 팀 프로젝트의 **주제와 기술 방향을 확정**했다. 공교롭게도 두 주제가 같은 결론에 도달했다 — **"클라이언트에서 하는 건 편의고, 책임은 다른 쪽에 있다."**

## 1. HTML 코드리뷰 — 16줄 회원가입 폼

CSS·JS 없는 순수 HTML 16줄(폼 하나, 입력 두 개, 버튼 하나)을 소재로 발표 대본을 만들었다. 구성은 **문서·폼 구조 → 제출 시 실제 동작 → 잘한 점 → 아쉬운 점 → 개선안**. 메시지는 하나 — **"짧은 코드에도 논의할 거리가 많다."**

### 폼의 심장은 세 개 — action, method, name

- `action` = 데이터를 보낼 주소 / `method` = 보내는 방식
- **`name` 속성이 서버로 가는 데이터의 키가 된다.** name이 없으면 값 자체가 전송되지 않는다 — 1일차에 배운 폼 태그의 진짜 핵심이 이거였다.

### 제출하면 실제로 무슨 일이 일어나나

사용자 입력 → 브라우저 검증 → HTTP 요청 생성 → 서버 처리. 그리고 만들어지는 요청 본문:

```
userId=sky&userPw=...
```

**비밀번호가 평문 그대로 실린다.** `type="password"`는 화면에서 ●●●로 **가려주기만** 하고 전송 시 암호화와는 전혀 무관하다. 이게 발표에서 가장 오해가 많은 포인트라 두 번 강조하기로 했다.

12일차에 Express로 `req.body`를 꺼내봤던 게 도움이 됐다. 그때 받던 그 body가 여기서 만들어지는 것이었다.

### 잘한 점 / 아쉬운 점

| | 내용 |
|---|---|
| ✅ 잘한 점 | POST 선택(GET이면 비밀번호가 URL·히스토리·서버 로그에 남음) · `type=password`로 어깨너머 방지 · `required`로 JS 없이 1차 검증 · `lang`·`charset` 명시 |
| ⚠️ 접근성 | **`<p>`를 label 대신 씀** → 스크린리더가 이 칸이 무슨 칸인지 모르고, 텍스트를 클릭해도 포커스가 안 감. `label` + `for`로 해결 · `autocomplete` 없음 · `minlength` 없어 1글자 비밀번호 통과 |
| 🔒 보안 | HTTP면 평문 노출 → **HTTPS는 전제 조건** · `required`는 **curl 한 줄로 우회됨** · **CSRF 토큰 없음** |

개선안은 자바스크립트 없이 마크업만 고쳤다 — `p` → `label`+`for`, `minlength`/`maxlength` 추가, `autocomplete` 지정. **1~2일차에 배운 태그만으로 접근성과 검증이 이만큼 올라간다**는 게 이 발표의 재미있는 지점이었다.

### 오늘의 세 줄 결론

1. 폼의 심장은 `action` · `method` · `name`
2. `label`과 입력 규칙은 **JS 없이 얻는 공짜 업그레이드**
3. **클라이언트 검증은 편의 기능, 최종 책임은 항상 서버** (HTTPS + 서버 재검증 + 비밀번호 해싱)

> 어제 팀 기획안에서 읽은 문장 — *"화면에서 버튼·메뉴만 숨기는 건 보안 기능이 아니다"* — 와 정확히 같은 이야기다. 이틀 연속 같은 교훈을 다른 각도에서 만났다.

## 2. 팀 프로젝트 — 주제 확정 & 기술 검토

### 확정된 주제: 시니어 디지털 동행 서비스

정부24·고용24 같은 공공·구직 사이트를 어려워하는 어르신을 위한 서비스. **4단계 흐름**으로 이어진다:

| 단계 | 내용 |
|---|---|
| ① 니즈 파악 | AI 대화로 무엇이 필요한지 파악 ("일자리 구하고 싶어", "등본이 필요해") |
| ② 서비스 연결 | 목적에 맞는 사이트를 골라 목적 페이지까지 연결 |
| ③ 실전 가이드 | 실제 화면에 마커·하이라이트로 사용법 안내 |
| ④ 결과물 생성 | 대화 내용으로 이력서·신청서를 AI가 작성, PDF 제공 |

**차별점:** 기존 서비스는 목록만 보여주거나 연습만 시키고 끝나는데, 이건 **니즈 파악부터 실제 제출 준비까지 한 흐름**으로 이어진다.

### 출발 질문 하나에서 시작된 기술 검토

> "웹사이트 안에 브라우저를 열고 다른 사이트를 불러와서 마커를 표시할 수 있나?"

이 질문 하나로 다섯 가지 방식을 검토했는데, 대부분 벽에 부딪혔다:

| 방식 | 결과 |
|---|---|
| **iframe** | ❌ 대부분 사이트가 `X-Frame-Options`로 임베딩 차단 + 동일 출처 정책으로 내부 DOM 접근 불가 |
| **서버 프록시** | △ 정확도는 높으나 구현 부담 크고 사이트가 복잡할수록 깨짐 |
| **스크린샷 + 오버레이** | △ 어떤 사이트든 되지만 스크롤 시 재캡처 필요 |
| **브라우저 확장** | △ 정확도 최고, 설치 장벽 |
| **CDP Screencast** | ○ 실시간 요구 충족 |

**CDP(Chrome DevTools Protocol) Screencast**가 유력해 보였다 — 서버의 헤드리스 크롬이 렌더링한 화면을 WebSocket으로 실시간 전송하고, 사용자 클릭 좌표를 받아 `page.mouse.click()`으로 원격 조작하는 방식. (참고로 크로미움 계열만 지원한다는 제약은 **서버 쪽 브라우저에만** 해당한다. 사용자는 이미지 스트림만 보니까 무관.)

### 그런데 진짜 벽은 기술이 아니었다

한계점을 정리하다 보니 **핵심 벽 3가지**가 드러났다:

1. **법적** — 공공사이트 대부분 약관에 **자동화(봇) 접근 금지** 조항. 캡차가 뜨면 자동화 차단
2. **개인정보** — 로그인 시 주민번호·인증서가 **중계 서버를 경유**
3. **유지보수** — 좌표 기반 마커라 사이트 UI가 바뀌면 가이드가 깨짐

문제의 원인이 딱 하나로 수렴했다 — **"서버가 사용자 대신 실사이트를 조작한다."** 캡차 우회는 리스크만 키우니 제외하고, **행위 주체를 서버에서 사용자로 되돌리는 방향**으로 재설계했다.

### 최종 채택: 화면공유 + 질문 시점 캡처 마커

```
① window.open()으로 정부24를 별도 창에 (좌우 반반 배치)
   ※ iframe이면 실패 — 품는 게 아니라 옆에 띄우는 구조
② 최초 1회 getDisplayMedia() 허용 → 스트림 계속 유지
③ 질문 시점에 drawImage로 프레임 1장 캡처
④ 현재 화면 판별
⑤ 우리 창 canvas에 스샷 + 마커 오버레이
⑥ 어르신은 실제 창에서 직접 클릭 (자동화 아님 ✅)
```

**우리 서비스는 대상 사이트에 단 한 건의 요청도 보내지 않는다.** 관찰만 한다. 화면공유는 최초 1회 허용받으면 이후 몇 번이든 캡처 가능하고, `drawImage`는 백그라운드 탭에서도 동작한다.

**난관 3가지와 대응이 이 설계의 핵심이었다:**

| 문제 | 대응 |
|---|---|
| **A. 마커 위치 판단** | 좌표 예측을 AI에 맡기지 말 것. 화면 판별은 Claude 비전(분류), **버튼 위치는 OCR(tesseract.js) 텍스트 탐색**, 안내 문구는 사전 시나리오 JSON. OCR 실패 폴백(문장+음성) 필수 |
| **B. 스샷 마커를 실제 창에서 다시 찾아야 함** (최대 UX 약점) | **Document Picture-in-Picture** — 항상 최상위 창이라 창 전환이 사라짐. 미지원 브라우저는 나란히 배치로 폴백 |
| **C. 개인정보** | OCR은 **클라이언트에서만**(서버 전송 0건), Claude 비전은 다운스케일+입력필드 마스킹 후, 캡처는 메모리에만 |

특히 A의 원칙이 인상적이었다 — **"좌표 예측을 AI에 맡기지 말 것."** 17일차에 OCR 결과를 눈으로 검증해야 한다고 배웠고, 13일차엔 AI 출력을 정규식으로 재검증했는데, 이번엔 아예 **AI에게 맡길 일(분류)과 맡기지 말 일(좌표)을 구분**하는 설계다.

### 4주 실행 계획 — 이원화 전략

기능을 다 넣는 대신 **시나리오 3개로 고정**(일자리 찾기 / 등본 발급 / 이력서 작성)했다. *"3개 완성 > 8개 반쯤."*

| 축 | 내용 | 상태 |
|---|---|---|
| **메인 축** | 샌드박스 클론 + 투어 엔진 (3개 시나리오) | **완성 보장 필수** |
| **도전 축** | 화면공유 + 캡처 마커 + PiP (1개 시나리오) | 3주차 수요일에 판단 |

**가장 좋았던 아이디어 — 두 축을 잇는 트릭:** 1주차에 **스텝 JSON 스키마를 두 축이 공유**하도록 설계해서, `anchor` 타입만 바꾸면(`data-tour` ↔ `ocr-text`) 시나리오를 재사용할 수 있다. 도전축의 추가 비용이 급감한다.

역할 분담도 이 구조를 따랐다 — B가 투어 스텝을 JSON으로 정의하고, C는 샌드박스 화면에 `data-tour="apply-btn"` 속성만 심으면 자동으로 마커가 찍힌다. **병렬 작업이 가능한 인터페이스 설계.**

기술 스택은 React + Vite + TypeScript · Tailwind(시니어 디자인 토큰) · Zustand · jsPDF · Web Speech API · tesseract.js · Claude API. 백엔드는 **API 키 숨김용 Vercel Serverless Function 하나**뿐 — 13일차에 배운 "키는 서버 금고에" 원칙의 최소 구현이다.
