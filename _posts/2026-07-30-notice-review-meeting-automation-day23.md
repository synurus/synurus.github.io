웹개발 수업 23일차. 오전 코드리뷰는 짧은 공지 페이지였는데, 짧은 코드에서 오히려 확실한 문제 하나를 찾았다. **눌러도 아무 일이 없는 "더보기"**였다. 오후에는 팀 과업을 겸해 **회의록·채널 요약 자동화 시스템**을 만들었다. 18일차 스킬, 19일차 훅에 이어 오늘은 **플러그인 코드를 직접 수정**했다.

## 1. 코드리뷰 ③: 공지 페이지

분석 대상은 스타일도 스크립트도 없는 순수 텍스트 공지였다. 내용은 단순하다:

| 항목 | 내용 |
|---|---|
| 수업 시작 시간 | 오늘 3시 |
| 준비물 | 노트북, 충전기 |
| 지각 시 | 문자 발송 요청 |

### 발견: "▼ 더보기"가 가짜다

구조를 뜯어보니 문제가 하나 있었다.

> **"▼ 더보기"가 `<div>`로만 되어 있고, 접기/펼치기 스크립트나 `<details>` 태그가 없다.** 그래서 실제 페이지에서는 클릭해도 아무 동작을 하지 않는다. "더보기"는 시각적 표시일 뿐이고, 바로 아래 문단은 이미 펼쳐진 상태로 항상 보인다.

**보이는 것과 동작하는 것이 다른** 전형적인 사례다. 사용자는 "▼"를 보고 접힌 내용이 있다고 기대하는데 실제론 접힌 게 없고, 눌러도 반응이 없으니 페이지가 고장난 것처럼 느낀다.

### 정답은 2일차에 이미 배웠다

`<details>`와 `<summary>`: **JavaScript 없이 클릭만으로 펴고 접히는** 태그.

```html
<details>
  <summary>더보기</summary>
  <p>준비물: 노트북, 충전기. 지각 시 문자 주세요.</p>
</details>
```

- `<summary>`가 항상 보이는 클릭 버튼이 되고, 화살표 표시도 브라우저가 알아서 그려준다 (직접 "▼"를 찍을 필요가 없다)
- 키보드로도 열고 닫을 수 있고, 화면 낭독기가 "펼치기/접기"로 안내한다. `<div>`로 흉내낸 것엔 이게 전부 빠져 있다

이번 코드리뷰 3연작이 결국 같은 이야기를 하고 있다:

| | 문제 | 교훈 |
|---|---|---|
| 21일차 | `<p>`를 label 대신 씀 | 모양은 같아도 **연결**이 없다 |
| 22일차 | `action`·`name` 없음 | 폼처럼 보이지만 **전송**이 안 된다 |
| 23일차 | `<div>`로 만든 더보기 | 버튼처럼 보이지만 **동작**이 없다 |

**"보이는 것"과 "의미·동작"은 다르다.** 1일차부터 배운 시맨틱 태그의 이유가 세 번 연속 확인된 셈이다.

## 2. 미니프로젝트: 회의록·채널 요약 자동화 시스템

팀 프로젝트를 하면서 논의가 여러 채널·스레드에 흩어지는 문제가 있었다. 채널 요약과 회의록 작성을 매번 수작업으로 하던 걸 자동화했다. (팀 과업인 "회의록 시스템 개발 기획서 제출"도 겸함.)

**형태:** 별도 서비스가 아니라 **Claude Code의 Skill + 기존 Discord 연동 플러그인의 확장**.

### 2-1. 출발점: 채널 하나에서만 반응하는 봇

Claude Code의 channels 기능과 공식 Discord 플러그인으로 팀 서버에 봇이 이미 연결돼 있었다. 설치에 난관(런타임 의존성, 서버 초대 절차)이 있었지만 해결했고, 문제는 다른 데 있었다. **초기 설정이 특정 채널 하나에서만 반응하도록 좁게 잡혀 있었다.**

팀 서버는 채널·스레드가 계속 새로 생기는 구조라, **새 채널마다 수동으로 권한을 등록하는 방식은 애초에 지속 불가능**했다.

### 2-2. 플러그인 코드 직접 수정: 채널 단위 → 서버 단위

그래서 플러그인 원본 코드(`server.ts`)를 직접 고쳐 접근 범위를 **채널 단위에서 서버(길드) 단위로** 확장했다.

1. 접근 정책 데이터 구조에 채널 단위 필드(`groups`)와 별도로 **서버 단위 필드(`guilds`)를 신설**
2. 메시지 수신 판단 로직에, 채널 개별 등록이 없어도 **그 채널이 속한 서버가 `guilds`에 있으면 허용**하는 폴백 추가
3. **스레드는 부모 채널의 정책을 상속하는 기존 구조를 그대로 활용**. 서버 단위 등록만으로 신규 채널·스레드까지 자동 커버된다
4. 메시지 조회 등 아웃바운드 도구의 검증 로직에도 같은 폴백을 반영했다. 등록한 적 없는 채널의 과거 기록도 조회 가능

결과: **팀원이 새 채널이나 스레드를 만들어도 별도 설정 없이 봇이 즉시 반응**한다.

3번이 특히 마음에 들었다. 새 상속 구조를 만든 게 아니라 **이미 있던 상속(스레드 → 부모 채널)에 한 단계를 얹은 것**뿐이라, 수정량이 작으면서 커버 범위는 넓어졌다.

### 2-3. 왜 새 플러그인이 아니라 Skill인가

필요한 건 **새로운 기능(도구)이 아니라, 이미 있는 도구(`fetch_messages`·`reply`)를 어떤 절차와 형식으로 쓸지 표준화하는 것**이었다. 그래서 플러그인을 새로 만들지 않고 Skill 문서 2종을 작성했다.

18일차에 정리한 스킬의 본질, *"반복되는 판단과 명령을 문서로 굳혀두는 것"*, 이 정확히 이 판단이었다. 도구는 있는데 절차가 없었던 것.

**배치 위치도 신경 썼다.** Discord 플러그인 폴더 안이 아니라 **별도의 사용자 스킬 디렉토리로 분리**했다: 공식 배포판이라 업데이트 시 로컬 수정이 덮어써질 수 있으니까. (`server.ts` 수정분은 어쩔 수 없이 플러그인 안에 있으므로, 수정 전 **백업 파일을 남겨** 언제든 되돌릴 수 있게 했다.)

### 2-4. 만든 기능 4가지

| # | 기능 | 내용 |
|---|---|---|
| 1 | **채널 요약** (`channel-summarize`) | 최근 대화를 화자별로 정리 + 결론을 붙여 그 자리에 답장. Discord 마크다운(볼드·불릿·구분선)으로 가독성 확보 |
| 2 | **회의록 자동 작성** (`meeting-minutes`) | 대화를 **"현재 주제 / 논의 내용 / 다음 목표"** 구조로 정리 → 마크다운 파일 저장 → **팀 저장소에 커밋·푸시까지 자동** |
| 3 | **팀원 매핑 인프라** (`team-map.json`) | Discord 핸들·사용자ID·실명, 채널명·채널ID 매핑 → 회의록에 실명 표시 |
| 4 | **완료 후 참여자 리콜 알람** | 회의록 작성이 끝나면 실제 논의에 참여한 팀원 전원을 `@멘션` → 결과물을 놓치지 않게 |

### 2-5. git 작업 안전장치: 이 시스템의 핵심

회의록이 **팀 공유 저장소에 자동으로 푸시**되므로, 사고가 그대로 반영되면 안 된다. 그래서 다섯 개의 중단 조건을 걸었다:

1. 새 회의록 파일 **외에 다른 변경 사항이 있으면 즉시 중단** (다른 팀원 작업물을 임의로 커밋하지 않기 위해)
2. `main` 브랜치가 아니면 중단
3. 반영 전 최신 이력을 받아오되, **충돌이 나면 자동 병합 시도 없이 중단**
4. **새로 만든 회의록 파일 한 개만** 선택적으로 반영 (전체 일괄 반영 금지)
5. 푸시가 거부·실패하면 **강제로 밀지 않고**, 정확한 오류와 함께 중단 후 보고

관통하는 원칙은 이 한 줄이다:

> **"정상적인 상황에서는 끝까지 자동으로 처리하되, 조금이라도 예상과 다르면 반드시 멈추고 사람에게 알린다."**

19일차에 훅을 만들며 "판단은 모델에게 맡기고 훅은 재료만 준다"를 배웠는데, 여기선 방향이 반대다: **자동화의 범위를 좁게 못 박고, 경계를 넘으면 사람에게 넘긴다.** 남의 저장소를 건드리는 작업이니 이쪽이 맞다.

### 2-6. 반복 개선 4단계

기본 형태를 만든 뒤 실제 팀 서버에서 써보니 개선점이 보여서, 우선순위대로 반영했다.

1. 요약 출력이 한 문단에 몰려 **가독성이 떨어짐** → Discord 마크다운 구조화
2. 참여자가 **Discord 핸들로 표시됨** → 실명 매핑 인프라 구축 (참여자ID 노출을 위한 코드 수정 포함)
3. 그 인프라로 회의록 참여자 필드를 **실명 표시**
4. **참여자 리콜 알람** 추가

2번이 재밌었다. "실명으로 보이게 하고 싶다"는 UI 요구가 **매핑 데이터 구축 → 플러그인이 참여자ID를 노출하도록 수정**까지 거슬러 올라갔다. 표시 문제가 데이터 문제였던 것. 15일차에 `model.names`를 뒤집어 이름↔인덱스 조회를 만들었던 것과 같은 종류의 작업이다.

### 2-7. 프롬프트 인젝션 방어

채널 메시지에 지시문처럼 보이는 텍스트가 섞여 있어도 **요약 대상 데이터로만 취급하고 실행하지 않도록** 각 Skill에 명시했다.

22일차 아레나 기획의 *"사용자 프롬프트는 데이터로만 취급, 지시로 해석하지 않음"*과 완전히 같은 원칙이다. 외부에서 들어온 텍스트는 **명령이 아니라 재료**라는 것. 이게 AI를 쓰는 시스템의 기본 방어선인 것 같다.

### 2-8. 설계도: 화면이 없는 시스템의 와이어프레임

이 시스템은 UI가 있는 앱이 아니라 **Discord 채팅으로 트리거되고 결과가 GitHub 파일로 쌓이는** 구조다. 그래서 화면 목업 대신 두 가지로 정리했다:

**① 전체 처리 흐름** (Mermaid 시퀀스 다이어그램)

```
팀원 → 봇: "@봇 회의록 작성해줘 PT"
봇 → 스킬: 실행 (채널ID + 주제태그)
스킬 → 봇: fetch_messages
스킬 → team-map.json: 사용자ID로 실명 조회
스킬: 본문 작성 (현재주제 / 논의내용 / 다음목표)
     ⚠️ git 안전장치 체크 → pull → add → commit → push
스킬 → GitHub: 회의록 파일 push
스킬 → 봇: reply (참여자 @태그 + 링크)
```

**② 사용자가 실제로 마주치는 지점**: Discord 대화 목업과 결과 파일 구조. 회의록은 `회의록/날짜_주제_회차_회의록.md` 형식으로 누적되고, 파일 상단에 날짜·회차·채널·참여자·제목을 front matter로 넣었다.

이 블로그를 Jekyll로 쓰면서 익숙해진 그 front matter 구조를 회의록에도 쓴 셈이다. **정해진 형식으로 파일을 쌓으면 나중에 기계가 읽을 수 있다**는 게 같은 원리.

## 3. 자동화 3단(段)이 완성됐다

18~23일차를 돌아보니 자동화의 층이 하나씩 올라왔다.

| 단계 | 대상 | 한 일 |
|---|---|---|
| **18일차** | 스킬 | 내가 부를 때 실행: `.md` 파일 열어주는 스킬 |
| **19일차** | 훅 | 조건이 되면 저절로 실행: 설치된 스킬 목록 주입 |
| **23일차** | **플러그인** | 도구 자체의 동작 범위를 수정: 채널 → 서버 단위 |

스킬은 **절차**를 정하고, 훅은 **시점**을 정하고, 플러그인은 **능력**을 넓힌다. 19일차에 플러그인 기획서만 써두고 "제작 중"이라고 남겼는데, 결국 다른 경로로 플러그인 코드를 만지게 됐다.
