## 1. 코드리뷰 ⑲: Debounce, 조용해질 때까지 기다렸다가 한 번

Debounce는 연속으로 들어오는 호출을 묶어서, 마지막 호출 이후 일정 시간 동안 추가 호출이 없을 때만 함수를 한 번 실행하는 기법이다. 엘리베이터 문이 닫히려다가 누가 타면 다시 열리고, 아무도 안 타야 비로소 닫히는 것과 같다.

원래는 하드웨어 용어다. 물리 스위치를 누르면 접점이 미세하게 튀면서 신호가 여러 번 들어오는데, 이걸 하나로 정리하는 회로를 de-bounce라고 불렀다.

브라우저 이벤트는 생각보다 훨씬 자주 발생한다. 타이핑은 글자 하나당 1회, 창 크기 조절은 끄는 동안 수십에서 수백 회, 스크롤은 한 번 굴릴 때 수십 회가 나간다. 여기에 그대로 API 호출을 붙이면 검색어 자동완성에서 `abcde`를 치는 동안 요청이 다섯 번 나가고, 심지어 응답 순서가 뒤집혀 `abc`의 결과가 `abcde`의 결과를 덮어쓰기도 한다.

구현은 짧다.

```js
function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);                       // 이전 예약 취소
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const onSearch = debounce((keyword) => {
  fetch(`/api/search?q=${keyword}`);
}, 300);
```

호출이 들어올 때마다 이전 타이머를 취소하고 새로 거는 것이 전부다. `timer`를 클로저에 가둬서 호출 사이에 상태를 유지하는 게 핵심이고, `fn.apply(this, args)`로 `this`와 인자를 그대로 넘긴다.

React에서는 여기서 한 번 걸린다. 렌더링마다 함수가 새로 만들어지면 타이머도 매번 새로 생겨서 debounce가 아예 동작하지 않는다. 참조를 고정해야 한다.

```jsx
// 렌더링마다 새 debounce 인스턴스가 생긴다
const handler = debounce(search, 300);

// 참조를 고정한다
const handler = useMemo(() => debounce(search, 300), []);
useEffect(() => () => handler.cancel(), [handler]);
```

### Throttle과 무엇이 다른가

둘 다 호출 횟수를 줄이지만 줄이는 방식이 다르다.

| | Debounce | Throttle |
|---|---|---|
| 기준 | 마지막 호출 후 delay 경과 | 일정 주기마다 1회 |
| 폭풍 입력 중 | 실행하지 않는다 | 주기마다 계속 실행한다 |
| 보장하는 것 | 마지막 값은 반드시 반영된다 | 중간 상태도 주기적으로 반영된다 |
| 쓰는 곳 | 검색어 입력, 자동 저장, 리사이즈 후 재계산 | 스크롤 위치 추적, 무한 스크롤, 마우스 이동 |

최종 결과만 중요하면 Debounce, 진행 과정도 중요하면 Throttle이다.

주의할 점 세 가지를 같이 정리했다. delay 값은 검색어 자동완성 기준 200에서 400밀리초 사이고, 500을 넘기면 사용자가 느리다고 느낀다. 중복 제출 방지처럼 첫 호출이 즉시 나가야 하는 경우에는 `leading` 옵션을 쓴다. 그리고 컴포넌트가 사라질 때 대기 중인 타이머를 정리하지 않으면 없는 컴포넌트에 setState가 일어난다.

마지막 하나가 제일 헷갈리기 쉬운 지점이었다. debounce는 race condition을 없애주지 않는다. 요청 수를 줄일 뿐이라 응답이 역전되는 문제가 남고, 그건 `AbortController`로 이전 요청을 취소해야 완전히 사라진다. 덜 보내는 것과 늦게 온 걸 버리는 것은 다른 문제다.

## 2. 발표 대본을 소리 나는 순서로 다시 썼다

45일차에 다음에 할 일 첫 줄로 적어둔 게 타임코드 전면 재산정이었다. 오늘 그걸 하면서 시간 구조부터 다시 잡았다. 발표 12분을 본문 8분과 시연 4분으로 나눴다. 44일차에 만든 11분 35초짜리 배분은 몸통이 통째로 바뀌면서 무효가 됐으니, 장표 옆에 초를 적어 넣는 대신 대본을 처음부터 다시 쓰는 쪽을 골랐다.

기준은 1초에 5.5자다. 또박또박 읽고 쉼까지 넣은 속도로 잡았다. 그렇게 재보니 12쪽까지가 이렇게 나왔다.

| 구간 | 장 | 배정 | 누적 |
|---|---|---|---|
| 표지, 흐름, 팀원, 기획 배경, 시나리오, 설계도 | 6장 | 2:42 | 2:42 |
| 핵심 코드 리뷰 (맥락, 대안, 선택과 근거, 효과) | 4장 | 2:30 | 5:12 |
| 활용 방안, 사업성 | 2장 | 0:56 | 6:08 |

대본을 쓰다 보니 시간을 재는 것보다 어려운 게 따로 있었다. 어느 문장을 뺄지 미리 정해두는 일이다. 실제로 읽었을 때 밀릴 걸 알고 있으니, 7쪽과 8쪽에는 지우고 읽어도 논리가 끊기지 않는 문장을 일부러 배치하고 대본에 표시해뒀다. 8쪽 세 번째 대안은 통째로 한 줄로 줄일 수 있게 써뒀다.

그 외에 대본에 넣은 규칙은 셋이다. 2쪽 목차는 항목을 하나씩 읽지 않고 05만 손으로 짚는다. 6쪽 설계도는 네 곳만 짚는다. 여기서 30초를 잡아먹는 게 가장 흔한 실패다. 속도를 늦추는 자리는 세 곳으로 정했다. 4쪽의 "스스로 나아지게 한다", 9쪽의 "사람이 하는 일은 마지막 승인 하나", 10쪽의 지침 전후 비교다.

호출은 여러 번 있어도 실행은 한 번이라는 게 오늘 코드리뷰의 내용이었는데, 대본 쓰는 일이 그 모양이었다. 같은 내용을 설명하는 방법을 네댓 개씩 써놓고 마지막에 하나만 남긴다. delay 값에 해당하는 게 12분이었다.

## 3. 사업성이 한 장에서 네 장이 됐다

44일차부터 사업성은 애드센스와 영어 버전 두 줄짜리 한 장이었다. 평가 배점이 10점인데 한 장으로 끝나는 게 계속 걸려서 오늘 세 장을 새로 만들었다.

수익화 로드맵은 0단계, 1단계, 2단계로 나눴다. 0단계는 트래픽이 0인 지금 상태에서도 할 수 있는 것들이고, 1단계는 보이스챗과 교사용 도구가 완성된 뒤 교육기관 판매와 개인 유료를 여는 구간, 2단계는 유저풀이 생긴 뒤 유료 홍보와 꾸미기 확장으로 간다. 유료 구조는 무료, 개인 유료 월 5,900원, 교육기관 연 30만원에서 70만원 세 갈래로 정리했다.

가장 오래 걸린 건 원가를 계산한 세 번째 장이다.

| 항목 | 값 |
|---|---|
| 판당 AI 원가 (현재 모델) | 70원 |
| 판당 AI 원가 (저가 모델 + 프롬프트 캐싱) | 1.75원 |
| 판당 광고 수익 추정 (국내 / 영어권) | 10.8원 / 32.8원 |
| 서버비 | 연 49만원 |

같은 판 5,000토큰을 기준으로 모델 등급과 캐싱만 바꾸면 판당 원가가 40배 차이 난다. 지금 쓰는 모델 그대로 가면 광고 수익의 여섯 배가 원가로 나가고, 저가 모델에 캐싱을 붙이면 그 6분의 1로 떨어진다. 사업성을 재려고 계산을 시작했는데 결론은 모델 선택이 흑자와 적자를 가른다는 기술 얘기로 나왔다.

자립 지점은 서버비를 덮는 최소 규모로 잡았다. 교육기관 2곳이거나, 개인 유료 회원 8명이거나, 하루 125판이다. 셋 다 같은 선을 다른 경로로 넘는 것이라 나란히 놓았다. 광고가 덮는 건 서버비까지고 그 위의 성장 비용은 유료 구조가 맡는다는 게 이 장의 결론이다.

단가표와 요금제 산정 근거는 부록 A와 부록 B로 뺐다. 45일차에 만든 디자인 부록에 이어 세 번째 숨김 장이다. 발표에서는 넘기지 않지만 질의응답에서 숫자를 물어보면 열 수 있게 해뒀다. 사업성이 10점인데 근거를 대지 못하면 곤란하고, 그렇다고 본문에 단가표를 붙이면 6분이 8분이 된다.

한 가지는 오늘 정리하면서 걸러냈다. 0단계 항목 중 실제로 진행한 건 애드센스 사이트 심사 신청 하나뿐이다. 교육기관 문의 발송이나 교원 커뮤니티 게시는 아직 계획 단계인데 장표에는 완료로 적혀 있었다. 심사위원 앞에서 하지 않은 일을 했다고 말하는 것만큼 위험한 게 없으니 발표 전에 문구를 실제 상태에 맞춰야 한다. 지금은 계획인 걸 계획이라고 적는 편이, 물었을 때 대답이 막히는 것보다 낫다.

## 4. 설계도에는 루프를 얹었다

45일차에 그린 설계도는 브라우저와 서버와 외부 API 세 덩어리였는데, 오늘 그 아래에 자가개선 루프가 도는 경로를 한 줄로 넣었다. Stop 훅에서 `/selfRefine`으로, 거기서 재현 스크립트를 거쳐 PR로, 마지막에 사람 승인과 dev 머지로 끝난다. 봇 모듈 안에서 루프가 실제로 고치는 파일 하나에만 별표를 남긴 건 그대로 뒀다.

이걸 넣은 이유는 대본을 쓰다 알았다. 7쪽부터 10쪽까지 네 장을 말로 풀어보니 루프 설명이 코드 리뷰 파트에서 처음 등장하는데, 그러면 듣는 사람이 그 순간에 시스템 어디쯤 얘기인지를 새로 이해해야 한다. 6쪽 설계도에서 경로를 한 번 보여주고 지나가면 뒤에서 다시 설명할 필요가 없다. 대본이 장표의 구멍을 찾아준 셈이다.

대본은 12쪽까지만 썼다. 오늘 사업성이 세 장 늘었으니 13쪽부터 16쪽까지 네 장이 남았고, 본문 8분 중 1분 52초가 남아 있다. 네 장에 1분 52초면 장당 28초라 지금 장표 그대로는 빠듯하다. 사업성 세 장을 발표에서 전부 넘길지, 원가 장 하나만 남기고 나머지를 부록으로 내릴지는 남은 대본을 쓰면서 정하기로 했다.

**오늘의 한 줄 정리:** Debounce는 연속으로 들어온 호출 중 마지막 하나만 남기고, 그 하나를 언제 보낼지는 delay 값이 정한다. 대본을 쓰는 일도 같은 모양이어서 같은 내용을 여러 번 고쳐 쓰고 하나만 남겼는데, 어느 문장을 남길지 정해준 delay는 12분이었다.
